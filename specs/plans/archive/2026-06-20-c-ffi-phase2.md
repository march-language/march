# C FFI — Phase 2 Implementation Plan (strings/bytes, Option/Result, ownership, RC-leak gate)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development or superpowers:executing-plans. Steps use checkbox (`- [ ]`) syntax.

**Goal:** A compiled March program can call a C binding that borrows a `String`/`Bytes`, constructs a `String`/`Bytes`/`Option`/`Result` to return, with the correct Perceus reference-counting behavior at the boundary (borrowed args freed by the caller, owned returns freed by March) — verified by an RC-leak harness that proves allocation counts stay flat.

**Architecture:** Build on Phase 1's `march_ffi.h`/`.c`. Heap values already cross the boundary as raw `ptr` (verified), so there is **no value-marshalling codegen** — the work is (a) ABI constructors for the C side, (b) a global live-allocation counter as the leak gauge, (c) a `__live_allocs` test intrinsic, and (d) the centerpiece: `borrow`/`consume` parameter modes so Perceus drops borrowed args after the call (today everything is implicitly *consume*, which leaks borrow-style bindings).

**Tech stack:** OCaml 5.3, menhir, C11, dune + alcotest.

**Grounded facts (verified 2026-06-20, do not re-derive):**
- Heap String/Bytes args pass as raw `ptr`; String returns are `ptr` (IR: `declare i64 @sym(ptr)`, `call ... (ptr %sl)`).
- `march_alloc` (`runtime/march_runtime.c:86`) uses `calloc` — it does **not** touch the per-heap `live_bytes`. The leak gauge must be a new global counter incremented in `march_alloc` and decremented in `march_decrc`'s free branch (`march_runtime.c`, `if (prev == 1) free(p);`).
- `march_decrc` aborts on RC underflow (double-free) — a buggy `consume`/`borrow` shows up as an abort, not silent corruption.
- ADT/tuple cell: 16-byte header `{rc;tag;pad}` + 8-byte fields at offset 16. `march_alloc(16)` → a no-field cell (tag 0). `march_alloc(16+8)` → one field.
- Tags: `Option` None=0 / Some=1; `Result` Ok=0 / Err=1 (matches runtime conventions in `march_runtime.c:441` and the http modules).
- `march_string_alloc(int64_t len)` (`march_runtime.c:275`) returns a `march_string*` with header filled (rc=1, tag=`MARCH_STRING_TAG`, len), data uninitialized.
- Current extern arg RC = **consume** (no `decrc` after the call). Phase 2 makes `borrow` the default and the consume path explicit.
- Adding a builtin touches: `lib/typecheck/typecheck.ml` (return type), `lib/tir/llvm_emit.ml` (`mangle_extern` + builtin emission + `builtin_ret_ty`), `lib/eval/eval.ml` (interpreter), and the builtin-name registry. Model on an existing 0-arg Int-returning builtin.

### Task 3: Global live-allocation counter (the leak gauge)

**Files:** Modify `runtime/march_runtime.c`, `runtime/march_runtime.h`, `test/test_ffi.c`.

- [ ] **Step 1: Add a failing C test** (counts go up on alloc, back down on free)

```c
    {
        int64_t base = march_live_allocs();
        void *a = march_alloc(16);
        void *b = march_alloc(24);
        assert(march_live_allocs() == base + 2);
        march_decrc(a); march_decrc(b);
        assert(march_live_allocs() == base);
    }
```

- [ ] **Step 2: Declare in `march_runtime.h`**

```c
/* Net count of live march_alloc objects (alloc + / free -). FFI/test leak gauge. */
int64_t march_live_allocs(void);
```

- [ ] **Step 3: Implement in `march_runtime.c`** — a global atomic counter, incremented in `march_alloc`, decremented in `march_decrc`'s free branch.

```c
static _Atomic int64_t march_live_alloc_count = 0;
int64_t march_live_allocs(void) {
    return atomic_load_explicit(&march_live_alloc_count, memory_order_relaxed);
}
```
In `march_alloc`, after the successful `calloc`, add:
`atomic_fetch_add_explicit(&march_live_alloc_count, 1, memory_order_relaxed);`
In `march_decrc`, inside `if (prev == 1) { ... }` before `free(p)`, add:
`atomic_fetch_sub_explicit(&march_live_alloc_count, 1, memory_order_relaxed);`
(Also add the same decrement to `march_decrc_freed`'s free branch and any other place that `free()`s a `march_alloc` object — grep `free(p)` / `free(` in `march_runtime.c` and `march_string` frees; ensure each alloc/free pair is balanced. `march_string_alloc` also allocates a march object, so it must `+1` too — route it through the same counter or add the increment there.)

### Task 5: `borrow`/`consume` parameter modes (the ownership centerpiece)

## Self-review notes

- **Spec coverage:** Tasks cover §4.5 (slices + str_new), §4.6 (Option/Result), §6.1 (borrow/consume ownership), §6.3 (string tier), §14.4 (RC-leak harness). The `march_env`/`march_raise` convenience (§4.9) is deferred — bindings build `Result` via `march_ok`/`march_err` directly, which needs no env; the env-routed `march_raise` and `march_str_new` UTF-8→`Err` validation land with a later increment.
- **Risk:** Task 5 (Perceus borrow semantics) is the highest-risk step — it touches reference-counting insertion, the area most prone to use-after-free/double-free. The RC-leak test (Step 2) is written *before* the change and is the gate; `march_decrc`'s underflow-abort surfaces double-frees loudly. Keep `consume` = today's behavior so only the new `borrow` default changes.
- **Leak gauge caveat:** `march_live_allocs` counts `march_alloc` objects globally and atomically; the interpreter returns 0 (leak tests are compiled-only). Document this in the intrinsic.
- **Type consistency:** `param_mode` (Task 5) extends `ef_params`/`ed_params` introduced in Phase 1; `__live_allocs`↔`march_live_allocs` mangle pair is fixed in Task 4; constructor names match `march_ffi.h` exactly.
