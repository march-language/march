## What "1.0" promises

A 1.0 is a promise, not a feature count. Proposed promise:

1. **Programs that compile on 1.x keep compiling and mean the same thing on every later
   1.x.** Language, stdlib (stable tier), `forge.toml`/lockfile formats.
2. **The four pillars below make claims we will defend as bugs.** Every claim is written
   down in one normative place, with its assumptions, and has a CI gate that goes red
   when it breaks.
3. **Compiled and interpreted March agree.** A divergence is a P1 bug, not a curiosity.

Note: forge's API-surface semver check is skipped for packages `< 1.0.0`
(`forge/lib/resolver_api_surface.ml:33`). 1.0 turns ecosystem enforcement on, so the
semver check must be precise before then (`todos/2026-07-31-forge-semantic-semver.md`).

## Pillar template

Every pillar is judged the same way:

- **Claim**: the one-paragraph guarantee, in a normative doc.
- **Holes**: known ways the claim is false today. All must be closed or the claim narrowed.
- **Gate**: the CI check that proves the claim continuously.
- **Unwritten**: gaps no todo tracks yet (new todos to file).

## Pillar 2: Capabilities

**Claim (proposed).** "A program's transitive reach is bounded by `main`'s grant; each
module's emitted code is bounded by its `needs`; `Cap` values cannot be forged or widened.
Under `--cap-sandbox` on a tier-1 platform, the OS enforces the grant for these
capabilities: …" Plus an explicit list of what is *not* claimed.

(R2–R4a, `ActorCap` split); per-role protocol grants; `forge audit --inferred`;
`forge cap run` (bwrap/SBPL) and `--cap-sandbox` (seccomp/`sandbox_init`).

**Holes.**
- Hot reload under `--cap-sandbox`: the unfiltered reload thread was fixed 2026-09-30, but
  the reload server's listener still races the sandbox install:
  `todos/2026-09-30-hcr-reload-listener-races-cap-sandbox-install.md` (**closed**, #1010).
- The new node shell does not yet declare caps a fragment reaches through library
  code: `todos/2026-10-06-shell-cap-manifest-library-caps.md` (**closed**, progress). A remote code-execution
  surface is exactly where the cap claim must hold; decide whether the shell is in 1.0.
- (Closed since the first draft: macOS NetListen split, both Check 4 ordering gaps.)
- Path scopes: `todos/2026-08-04-path-scope-followups.md` (`csv_open` atom bypass; not

- `Vault.open`/`whereis` turn any name string into a handle with a caller-chosen element type

### Pillar 2 — per-function bounds (option B, fallback A)

**A (fallback, already true):** a module can do at most its `needs`; the program at most
`main`'s grant. Functions inside a module share the module's authority.

**B (target):** a function may *declare* a bound, checked against its transitive reach,
with **no effect on callers** (callers stay bounded by their own module). This is what
stage C wanted, minus the parameter threading that got it removed on 2026-08-13: the
threading came from attaching the discharge point to `Cap(X)` *parameters*, not from the
check itself.

Most of the machinery survives: `Cap_rows.solve` (`lib/caps/cap_rows.ml`) still computes
a per-function row `{caps; deps; unknown}` for every function; only the check that read it
(`check_fn_grants`) was deleted. B = a declaration syntax + re-attach that check to it.

Semantics sketch:
- `caps(f) ⊆ declared(f)`, and `declared(f) ⊆ needs(module)`.
- Callbacks (`deps`): the bound means "my own authority, plus whatever you hand me". The
  caller that supplies the callback is charged for it, as today.
- Untraceable invocations (`unknown`: a function pulled from a record/list/ref and called):
  a declared narrow bound is **refused** with a pointer to the call, never silently granted.
- Actor spawns charge the handler's caps to the spawner (existing rule).

Decisions (2026-09-29):
1. **Syntax: header keyword** — `fn fetch(url) needs IO.NetConnect.TLS do`; `needs ()`
   for pure. (Parser work; the menhir conflict baseline is 11, keep it there.)
2. **Interfaces: yes.** Interface method signatures may carry a `needs` bound; every impl
   is checked against it. Optional per interface. Must land before 1.0 (adding later
   breaks impls).
3. **Semver: yes.** A declared bound is public API surface; widening it is a major bump in
   forge's semver check, and shows up in `forge audit` upgrade diffs.
4. **Hot reload may widen a bound, but never silently.** Proposed shape: a patch that
   widens any declared bound is refused unless the deploy explicitly authorises that
   widening (per function, alongside the existing `--grant-cap`), and the widening is
   recorded in the HCR audit log. Still capped by the running program's `main` grant —
   under `--cap-sandbox` the OS filter can't be loosened at runtime anyway.
   *Proposed, awaiting confirmation:* a reload may widen function bounds within module
   `needs`, and module `needs` within `main`'s grant, each behind its own explicit flag;
   widening `main`'s grant requires a restart (it is physically impossible under
   `--cap-sandbox`, and keeps "the grant bounds the program" true across deploys).

Still open: tooling — `forge fix` writes the tightest bound; LSP hover shows the inferred
row even for undeclared functions; `forge audit` reports per-function rows.

Precondition either way: the rows are only as good as `fn_refs`, so the
walk-completeness gate (above) is required before B's claim means anything.

**Fall back to A if:** `unknown` refusals or interface/impl bounds produce too much noise
on the stdlib + real apps to be usable. Measure by declaring bounds across a sample of
stdlib modules first.

**Claim (proposed).** Published, reproducible numbers on tier-1 platforms for a fixed
suite, with a CI gate that catches regressions. Compiled programs do not leak. Compile
time stays within stated budgets.

  **20x** behind OCaml; tree-transform lead shrinks to 2.3x. The two runs can't be
  reconciled (different box, date, load, commit).

- Clean compile 4.77 s for a 193-line program.

  un-applied closure leaks captures) and §B (`Array.set` ~3 objects/update);

- Allocator: zero-fill on every allocation, no bump path (`todos/2026-08-04-x86-benchmark-findings.md`).

- Strings: small-string optimisation not built (91.7% of allocs ≤ 23 bytes;

## Pillar 4: Refinement types

**Claim (proposed).** "Under `cap verified`, every refinement obligation in the module
is discharged by z3 or explicitly marked `@[trusted]`/`@[assume]`; the trusted base is
exactly: …". Outside `cap verified`, refinements report definite violations only.

**Solid today.** Definite-failure-only default (no false positives); `cap verified`
turns skips into errors with classified reasons (`lib/refinecheck/obligation.ml`);
measure soundness gate; counterexamples replayed before reporting (`witness.ml`);
hash-keyed VC cache that never caches `unknown`.

**Holes.**
- **Int overflow is not modelled** (verified: `lib/refine/refine.ml:61` "SMT integers
  are unbounded"; no overflow side conditions in the encoding). Runtime `Int` is
  **63-bit and wraps**. Since 2026-10-01 (`bed09ee0a`,
  `progress/2026-09-30-int-63-bit-overflow-parity.md`) this is *normative*:
  `specs/lang/type-system.md` "Int width and overflow" now says "Nothing traps on
  overflow", both backends agree, and the compiled path wraps via
  `Llvm_ctx.emit_wrap_int63` after every `+ - * /`. **That spec text conflicts with the
  trap decision below and must be revised when the trap lands.** The useful part: there
  is now one funnel to turn from "wrap" into "check and trap". JS backend still lacks
  63-bit semantics (`todos/2026-09-30-js-backend-int-63-bit-semantics.md` (**closed**, progress)). So `x + 1 > x` "proves", and a
  bounds contract like `i + len <= n` can be satisfied by a wrapped negative sum.
  **This is the most serious soundness issue found.** **Decided 2026-09-29: trap on
  overflow at runtime** (Swift-style: an overflow-flag branch after each tagged
  add/sub/mul, both backends), which makes the checker's unbounded model sound as-is.
  Explicit `wrapping_*` ops for hashing/checksums. Measure with a
  same-box A/B (fib, list-ops, index loops) to size the cost, not to decide whether.
  **Consequence to design for:** trapping turns every `+`/`-`/`*` into a panic site, so
  `cap no_panic` (and `panic_surface_by_proof`) must now *prove* no overflow on each
  arithmetic op, the same way `division_safety.ml` proves non-zero divisors. Overflow
  modelling therefore comes back, but only as no-panic obligations, not in every VC.
  Without it, either `cap no_panic` silently ignores overflow (unsound) or rejects all
  arithmetic (unusable).
- Caller discharge: a param contract is assumed in the callee; callers outside
  `cap verified` can be silently skipped and there are no runtime checks, so callee
  "proofs" are conditional.
- z3 is **not bundled or version-pinned** (`solver.ml:11` finds it on `PATH`; CI mixes

  `todos/2026-09-18-typecheck-annotated-tyvars-flexible.md` (**closed**, 613a06c26, rigid since 2026-10-11).

## Open decisions

Decided by the owner on 2026-10-30 unless marked otherwise.

1. Function-level cap bounds: **under discussion — option B (declared per-function
   bounds, no parameter threading), with A (module-level only) as the allowed fallback.**
   See "Pillar 2 — per-function bounds (option B)" above. Syntax, interface bounds and
   semver **decided**; reload-widening limits proposed.
2. ~~`--cap-sandbox`: opt-in or default-on?~~ **Decided: opt-in, and fail closed** when asked
   for on an unsupported platform or when the install fails (today's behaviour). The default 1.0
   claim is the compile-time one.
3. ~~Refinement `Int` overflow?~~ **Decided (2026-09-29): trap on overflow at runtime** (see Pillar 4).
4. ~~Bundle z3 or make it a component?~~ **Decided (2026-09-29): ships in the toolchain.**
5. ~~May user code use `@[assume]`?~~ **Decided: yes, visibly.** `cap verified` accepts it and
   lists every assumption in the trusted base (`--refine-audit`, `forge audit`); the soundness
   claim reads "verified modulo the listed assumptions".
6. ~~Tier-1 platforms?~~ **Decided: darwin-arm64, linux-x86_64, linux-aarch64.** Intel macOS,
   Windows and WASM are stated as tier 2/3 in the platform matrix.
7. Perf targets: which benchmarks, which competitors, what ratios? **Still open.**
8. ~~Small-string optimisation before or after 1.0?~~ **Decided: tune, then freeze.** The
   runtime already has an inline encoding (`MARCH_SSO_MAX`); its capacity is chosen by a
   same-box A/B on `bench/string_*`, HTTP and JSON (best median, no regression over 3%
   elsewhere), then documented and frozen as the 1.0 layout. This needs the perf A/B runner
   first, so that runner moves ahead of it.
9. ~~Artifact-signing trust root?~~ **Decided: Sigstore keyless** (GitHub OIDC in CI). The
   Sigstore bundle (signature, certificate, transparency-log proof) ships next to each artifact;
   `install.sh` and forge verify it offline against the pinned workflow identity.
10. ~~Target date / release count?~~ **Decided: gate-driven, no date.** 1.0 when Phases 2 and 3
    below are done, then `1.0.0-rc` cycles until a candidate has zero known P1s and flakes.
11. **The step-12 cluster control plane is in 1.0, stable** (this draft had first listed it as
    out of scope). Its promise: the release file format, the control API verbs and the
    node-to-node control messages stay compatible across 1.x, so a 1.x leader drives any 1.x
    agent. Gates: a mixed-version lab scenario (old agent with a new leader and the reverse) on
    every release candidate, and versioning on every change to those formats. The step-12a
    remainder and the lab-as-CI-gate join the critical path.
12. **First hot deploy onto a fresh base has no schema baseline (P1,
    `todos/2026-10-18-hcr-first-deploy-no-schema-baseline.md`): the reload server keeps the
    schemas.**
    - Every `--hot-reload` build embeds its schemas and manifest in the binary as constant data,
      in a deterministic encoding (it enters the CAS key and the determinism oracle).
    - The server answers a read-only `SCHEMAS` verb (owner-only socket and peer-uid check, as
      `ABI_QUERY`; not signed): the newest activated version per actor, naming the release it
      describes. It records each activated patch's `.schemas.json` in its state directory,
      pruned with the patch stack.
    - `forge deploy hot` asks the server first; if its local `.prev` disagrees, the server wins
      and forge warns that the local copy was stale.
    - A server built before this has no `SCHEMAS`: forge falls back to `.prev`, and with none,
      refuses ("restart on a current build or pass --old-schemas").
