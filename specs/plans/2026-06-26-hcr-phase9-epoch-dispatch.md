# HCR Phase 9 — Epoch-Tagged Dispatch

**Status:** Design. Prerequisite: Phase 8 complete (`20e54959`).

**Motivation:** Phase 8's coordinated gate requires every caller of a sig-changed function to be included in the same deploy batch. This works well for same-project deploys but breaks down in two real situations:

1. **Cross-binary callers.** Module C lives in a separate binary (separate CI, separate team). Its caller data is never recorded on the server, so Phase 8 conservatively allows sig changes involving C — but C's code on the server still calls old B.foo through the dispatch table, and after a sig change it will ABI-mismatch silently.

2. **Independent upgrade pace.** You want to ship B.foo v2 today and update A next sprint. With Phase 8 you must do both in one shot. With epoch dispatch, old A code naturally keeps calling old B.foo until A is redeployed.

Actors are already protected by migrate-before-run (Phase 5): the migration runs before the next handler, so old actor code never calls new B.foo between invocations. The remaining exposure is **plain (non-actor) cross-binary callers of sig-changed functions**.

---

## Core Idea: The Dispatch Ring Already Has Two Slots

The runtime already maintains a 2-slot ring per function. The Phase 9 insight: instead of always routing to the *current* slot, route to the slot that was *current when the caller's .so was deployed*. Old A code (deployed at epoch G) calls B.foo slot 0 forever. New B.foo lands in slot 1 at epoch G+1. Old B.foo (slot 0) is reclaimed once all old A handlers drain.

This requires three things:

1. **Each call site knows the epoch of its own .so** — so it can tell the runtime "I'm a generation-G caller; give me the G-compatible B.foo."
2. **The ring tracks which epoch is in each slot** — so `march_dispatch_enter_gen` can find the right slot for a given caller epoch.
3. **The server assigns epochs and stamps each deployed .so with its epoch** — globally monotonic, one epoch per deploy batch.

The key design constraint: the epoch is **not** known until the `forge deploy hot` run that activates the .so. The compiler runs locally before connecting to the server, so it cannot bake the epoch as a compile-time literal. Instead, the compiler emits a **file-static mutable cell** (`__march_hcr_epoch`) and an **init function** (`__march_init`) that the reload server calls after dlopen — before any function from the .so enters the dispatch table.

---

## Epoch Assignment

The reload server owns a `next_epoch` counter (starts at 1, incremented per deploy batch, persisted to `<cas_root>/next_epoch` across restarts):

```
GET_EPOCH
→ EPOCH <N>
```

The `forge deploy hot` flow with Phase 9:

```
1. SSH tunnel open
2. VERSIONS drift check
3. ABI_QUERY
4. Compile (--compile-so, no epoch flag needed)
5. Set-diff, coordinated gate
6. GET_EPOCH → N                  ← new step, after compile
7. CAS_CHECK + CAS_PUT
8. ACTIVATE ... epoch:<N> ...     ← extended; server stamps .so with N
```

`GET_EPOCH` happens after compile and before ACTIVATE. The compiled .so has `__march_hcr_epoch = 0` at rest; the server writes the assigned epoch via `__march_init` at activation time. **The forge compile/deploy flow is otherwise unchanged.**

All functions in a single deploy batch share the same epoch N (one `GET_EPOCH` per `forge deploy hot` run, before the ACTIVATE loop).

---

## How the .so Gets Its Epoch: `__march_init`

The compiler emits two things into every `--compile-so` output alongside the boundary functions:

```c
/* file-static: not exported from the .so, no global symbol collision */
static uint32_t __march_hcr_epoch = 0;

/* exported init: called by the server after dlopen, before any function
 * from this .so enters the dispatch table */
void __march_init(uint32_t epoch) {
    __march_hcr_epoch = epoch;
}
```

Because `__march_hcr_epoch` is `static`, it lives only in the .so's own data segment and is invisible to the dynamic linker's global symbol table. No collision between multiple deployed .so files. `__march_init` IS exported (no `static`) so the server can `dlsym(handle, "__march_init")` with a handle-specific lookup, which finds the right copy.

Each boundary call site reads the local cell:

```c
/* generated by llvm_emit for a boundary call to B.foo: */
void *fn = march_dispatch_enter_gen(NAME_ID, __march_hcr_epoch, &v);
r = fn(args);
march_dispatch_leave(NAME_ID, v);
```

Because the call site and `__march_hcr_epoch` are in the same .so, this compiles to a PC-relative load — no PLT, no symbol resolution, no RTLD interaction. The epoch read is fast and always correct regardless of RTLD flags.

When `__march_hcr_epoch == 0` (pre-activation or non-HCR build), `march_dispatch_enter_gen` falls back to the current ring slot — identical to today's `march_dispatch_enter`. This preserves backward compatibility.

## Runtime Changes

### `march_dispatch.h` additions

```c
/* Phase 9: epoch-aware enter.
 * Returns the fn_ptr from the newest ring slot whose epoch <= caller_epoch.
 * Falls back to current if caller_epoch == 0 or no matching slot exists. */
void *march_dispatch_enter_gen(uint32_t name_id, uint32_t caller_epoch,
                               uint32_t *out_version);

/* Publish with epoch. The existing march_dispatch_publish sets epoch = 0. */
int march_dispatch_publish_epoch(uint32_t name_id, void *fn_ptr,
                                 const char *impl_hash, const char *sig_hash,
                                 uint8_t kind, uint32_t epoch);
```

### `MarchFnVersion` struct addition

```c
typedef struct {
    void              *fn_ptr;
    _Atomic(uint64_t)  refs;
    char               impl_hash[65];
    char               sig_hash[65];
    uint8_t            kind;
    uint8_t            live;
    uint32_t           epoch;    /* Phase 9: epoch this slot was published at; 0 = pre-Phase 9 */
} MarchFnVersion;
```

### `march_dispatch_enter_gen` logic

```
Scan both ring slots. Find the slot s where:
  ring[s].live == 1
  AND ring[s].epoch <= caller_epoch (or epoch == 0 = "match anything")
  AND ring[s].epoch is the maximum such value

If caller_epoch == 0 OR no matching slot: return current (same as march_dispatch_enter).
```

On a 2-slot ring this is a 2-iteration scan with no locking (reads are atomic).

### `march_dispatch_publish_epoch`

Same as `march_dispatch_publish` but writes `ring[idx].epoch = epoch` after claiming the ring slot.

### Ring eviction

If the oldest ring slot still has refs > 0 when epoch G+2 tries to publish, the server responds `ERR all_slots_pinned` (unchanged from today). Phase 9 doesn't change eviction policy; it just adds epoch-tagged selection on the read side.

## Compiler Changes

**`lib/tir/llvm_emit.ml`**: when `--compile-so` is active, emit into the LLVM module:

```llvm
; file-local (private linkage — not exported)
@__march_hcr_epoch = private global i32 0

; exported init function
define void @__march_init(i32 %epoch) {
  store i32 %epoch, ptr @__march_hcr_epoch
  ret void
}
```

Boundary call sites (currently emit `march_dispatch_enter`):

```llvm
; today:
%fn = call ptr @march_dispatch_enter(i32 <NAME_ID>, ptr %vptr)

; Phase 9:
%epoch = load i32, ptr @__march_hcr_epoch
%fn = call ptr @march_dispatch_enter_gen(i32 <NAME_ID>, i32 %epoch, ptr %vptr)
```

**`bin/main.ml`**: no new flags needed. The `--compile-so` flag already triggers the boundary-call path in `llvm_emit`. Add a guard: only emit `march_dispatch_enter_gen` when `--compile-so` is set (baseline builds keep using `march_dispatch_enter` with epoch 0).

## Reload Server Changes

**`runtime/march_reload.c`**:

### `GET_EPOCH` handler (new)

```c
} else if (strcmp(line, "GET_EPOCH") == 0) {
    uint32_t e = atomic_fetch_add(&g_next_epoch, 1);
    persist_next_epoch(e + 1);   /* write next value to <cas_root>/next_epoch */
    char resp[64];
    int n = snprintf(resp, sizeof(resp), "EPOCH %u\n", e);
    write(fd, resp, (size_t)n);
```

`persist_next_epoch` writes atomically (tmp + rename) so crashes don't corrupt the counter.

On server start: read `<cas_root>/next_epoch` if present; otherwise start at 1.

### ACTIVATE handler extension

After dlopen succeeds, before `dlsym` for the function pointer:

```c
/* Phase 9: stamp the .so with its deploy epoch */
void (*init_fn)(uint32_t) = dlsym(handle, "__march_init");
if (init_fn) init_fn((uint32_t)epoch);   /* epoch parsed from "epoch:<N>" field */
```

Parse `epoch:<N>` from the ACTIVATE line the same way `callers:` is parsed (strstr + atoi). If absent, epoch = 0 (pre-Phase 9 .so; `march_dispatch_publish` sets epoch = 0 as before).

Call `march_dispatch_publish_epoch` instead of `march_dispatch_publish` when epoch > 0.

## Forge Changes

**`forge/lib/cmd_deploy_hot.ml`**:

```ocaml
(* After ABI_QUERY, before CAS_CHECK: *)
send_line conn "GET_EPOCH";
let hcr_epoch =
  match String.split_on_char ' ' (recv_line conn) with
  | ["EPOCH"; n] -> Option.value ~default:0 (int_of_string_opt n)
  | _            -> 0  (* old server: fall back to epoch 0 *)
in

(* In the ACTIVATE command (alongside the existing callers_suffix): *)
let epoch_field = if hcr_epoch > 0
  then Printf.sprintf " epoch:%d" hcr_epoch
  else ""
in
let cmd = Printf.sprintf "ACTIVATE %s %s %s %s %d%s%s"
  fm.fn_name fm.fn_impl_hash cas_hash sig_b64 migrate_required
  epoch_field callers_suffix
in
```

When the server responds `ERR unknown_command` to `GET_EPOCH` (old server without Phase 9), forge sets `hcr_epoch = 0` and continues with Phase 8 behavior. No other changes needed.

## Interaction With Phase 8

Phase 9 makes the sig_hash gate advisory rather than blocking:

| Situation | Phase 8 alone | Phase 8 + Phase 9 |
|---|---|---|
| Sig changed, all callers in batch | ✅ allowed | ✅ allowed |
| Sig changed, some callers missing | ❌ blocked | ✅ allowed — old callers see old B.foo via epoch routing |
| Sig changed, no caller data (cross-binary) | ✅ allowed (no data) but unsafe | ✅ safe — old callers route to old slot |

With Phase 9 active, the gate can downgrade from `Error` to `Warning`:

```
Warning: B.foo signature changed. Old callers (A.Worker_dispatch) will route
to the previous version until they are redeployed. This is safe — they will
call the new version after their next deploy.
```

Phase 8's `slot_callers` data is still useful in Phase 9 for generating this warning (it names the in-flight old callers). The hard block can be removed or kept behind `--strict-callers`.

## Phase 9 Does Not Require Phase 8 to Work

| Server supports epoch | Forge supports epoch | Result |
|---|---|---|
| No | No | Phase 8 gate only |
| Yes | No | Phase 8 gate (forge never calls GET_EPOCH) |
| No | Yes | Forge calls GET_EPOCH → `ERR unknown_command` → forge uses epoch 0 → Phase 8 gate |
| Yes | Yes | Full Phase 9: epoch-tagged routing, gate becomes advisory |

## What This Unlocks After Phase 9

- **Zero-downtime library upgrades.** Deploy B.foo v2; old A keeps calling old B.foo until A's next deploy.
- **Independent team deploy pace.** No cross-team coordination required for sig changes.
- **Expand-contract as a last resort, not the default.** Still valid and documented, but no longer the only safe path.

---

## Open Questions

1. **Epoch persistence across server restarts.** Write `next_epoch` atomically to `<cas_root>/next_epoch` on every `GET_EPOCH`. On restart, read it back; if missing, start at 1. A gap in epoch sequence is fine — the ring selection is "newest slot ≤ caller_epoch", so monotonic gaps don't break anything.

2. **Same epoch per deploy batch.** `GET_EPOCH` is called once per `forge deploy hot` run. All ACTIVATEs in that run carry the same epoch. This means all functions in a batch are co-versioned, which is correct — if A and B are deployed together, A callers should see the same-epoch B.

3. **`__march_init` called multiple times.** Multiple ACTIVATEs from the same .so (same CAS hash) will all call `__march_init(N)` with the same N. Idempotent. No problem.

4. **Non-.so (main binary) callers.** The server binary uses `march_dispatch_enter` (epoch 0 / always-current). If the main binary calls a hot-reloaded function whose sig changes, it will ABI-mismatch. Unchanged from today — this is outside the HCR contract. Changing a function the main binary calls directly requires a server restart.

5. **Clustering.** Each server's ring is independent. Server A might have B.foo at epoch 5; server B still at epoch 4. Requests land on either. Server A correctly routes epoch-4 callers to old B.foo (ring slot) until the slot is evicted. Server B routes everyone to epoch-4 B.foo. No cross-server coordination needed.

6. **Ring eviction timing.** With `MARCH_MAX_LIVE_VERSIONS = 2`, a third deploy (epoch G+2) cannot proceed until epoch G's ring slot has drained. The `ERR all_slots_pinned` error is unchanged. Operators should ensure old callers are redeployed before attempting a third consecutive sig change without restart.
