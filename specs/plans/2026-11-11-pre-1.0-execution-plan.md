# Pre-1.0 execution plan (everything but capabilities)

**Date:** 2026-11-11, written against `origin/main` at `cd4b47e96` (207 open todos).
**Status:** proposal. Nothing here is decided unless it cites a decision in
`specs/plans/2026-09-28-road-to-1.0.md`.

This plan turns the pre-1.0 checklist ("Status 2026-11-06" in
`specs/plans/2026-09-28-road-to-1.0.md`) into work packages: what each one changes, in which
files, how to tell it is done, what it waits on, and what can run at the same time. The checklist
says what is left; this says how to do it and in what order.

Todo references rot within days. Before starting a package, check that its todo is still in
`specs/todos/` on `origin/main`.

## Scope

**In:** the four open decisions, the non-capability base changes, the gates, deploy correctness,
the burn-down, and the freeze.

**Out (capability work, planned separately):**

- Object capabilities, phases 2b and 4-8 (`specs/2026-11-10-object-capability-design.md`).
- Per-function `needs` phases 3 and 4 (tooling and semver, hot reload).
- The capability walk-completeness test and the capability must-reject corpus.
- Capability loose ends: the ceiling, the dependency audit, the direct-runner root cap, path and
  host scope follow-ups, and the three gaps filed 2026-11-10.
- Registry capability notarization, and the topology role grant that is not enforced.
- The capability threat-model revision.

Two capability items still constrain this plan. Object capabilities are a breaking change, so the
freeze (wave 4) cannot start until they land. And the stdlib tier marking (B2) should wait for
object-capability phase 2, because handle types change the public API of `File`, `Socket`,
`Process` and the HTTP modules.

## How to read a package

Each package has an id, a size and a "done when". Sizes:

| Size | Meaning |
|---|---|
| S | One PR, one session, no design question. |
| M | Two to four PRs, or one PR that needs a measurement or an audit first. |
| L | Needs a short design note and an owner decision before code. |

"Done when" is the test a reviewer applies. A package that adds a gate is not done until the gate
has been seen to go red on a deliberate break (the repo's rule for oracles, and the reason: two of
three oracles once shipped unable to fail).

## Order

**Wave 0, owner decisions (D1-D5).** Each has a recommendation below. D1 blocks E8 and the
published numbers. D3 blocks B2. D5 decides whether "zero known flakes" (decision 10) can ever be
met. None of them blocks wave 1.

**Wave 1, start now, no dependencies between them:** G1, G2, G3, G5, B1, E1, the small E2 items
(E2b, E2d), the four harness-side flake fixes in E3, the failure-evidence capture in E3, the E6
triage, and the P3 design note.

**Wave 2:** G4 then E4. G6. P1. P2. The remaining E2 items. E5. E8 once D1 is decided. B2 once D3
is decided and the E6 triage has classified each module.

**Wave 3:** E6 fixes by module, E7, the flake soak (E3), P4.

**Wave 4, freeze:** F1, F2, release candidates. Starts only when object capabilities have landed.

**Running packages in parallel.** Most wave-1 packages touch disjoint code, with two exceptions:

- G2, G3, G4, G5 and G6 each add a job or a step to `.github/workflows/ci.yml` or `nightly.yml`.
  Land their workflow edits one at a time, or give each its own workflow file, and add each new
  job to `.github/workflows/README.md`.
- Every user-visible package adds a `CHANGELOG.md` bullet under `[Unreleased]`, so expect
  CHANGELOG-only conflicts between parallel PRs.

The org's runner budget is 20 concurrent Linux jobs and 5 macOS jobs
(`.github/workflows/README.md`). A new gate that costs more than about ten Linux job-minutes per
PR should run nightly and in the release gate (G1) instead of on every PR. G3, G4 and G6 each say
where they run.

## Wave 0: decisions

### D1. Decision 7: perf targets

**The question.** Which benchmarks, which competitors, what ratios.

**What exists.** `scripts/perf-ab.sh` races two March compilers on one box over a fixed set
(`DEFAULT_BENCHES`: `fib`, `tree_transform`, `binary_trees`, `list_ops`, eight string
benchmarks, `iolist_template`, two JSON streams) and `perf-ab.yml` runs it nightly against the
last release tag. The only idle-box competitor numbers are from 2026-08-04 on x86
(`specs/todos/2026-08-04-x86-benchmark-findings.md`): `fib` 430 ms against OCaml's 558;
`binary_trees` 526 ms against OCaml's 26.5, about 20 times behind.

**Recommendation.** Two kinds of target, because they need different machinery:

1. *No regression.* No benchmark in the fixed set is slower than the previous release outside
   noise (the runner's 3% threshold and its bootstrap interval). This is checkable today.
2. *Competitor ratios.* On each tier-1 architecture, every benchmark of a short competitor set
   (`fib`, `tree_transform`, `binary_trees`, `list_ops`, one string benchmark, one JSON
   benchmark) is within a stated factor of OCaml. Proposed factor: 2. `binary_trees` misses that
   by ten times today, so either the allocator work in E8 is in scope for 1.0 or the factor for
   allocation-heavy code is stated separately and honestly.

Competitor ratios need a quiet dedicated machine; a GitHub-hosted runner is too noisy for them.
The owner decides whether to keep a box for this (the 2026-08-04 GCP host is the precedent) or to
publish ratios measured by hand at each release.

**Done when:** the targets and the machine are written on a performance page (see D2) and E8 has
a list of benchmarks that miss.

### D2. The claim pages

**The question.** `specs/lang/claim-{deploys,capabilities,performance,refinements}.md` were
deleted on 2026-11-05. Bring back one page per pillar, or treat the existing chapters as the
claims.

**Recommendation.** Do not bring back four pages. Deploys, capabilities and refinements each have
a chapter that states what is promised (`specs/lang/compatibility.md`,
`capability-threat-model.md`, `refinement-types.md`). Performance has none, so add one page,
`specs/lang/performance.md`: the D1 targets, the method, the machine, the compile-time budget
from G5 and a link to the per-release results page (F1). Add a short "what 1.0 promises" list to
`compatibility.md` that links the four.

**Done when:** the page exists in `specs/lang/`, `scripts/gen-lang-docs.py` has regenerated its
`docs/` copy, and the road-to-1.0 plan's open decision is struck.

### D3. Stability tiers

**The question.** How a module is marked stable or experimental, and whether a stable module may
use an experimental one. `specs/lang/compatibility.md` leaves both open.

**Recommendation.**

- Mark tiers in one file, `stdlib/stability.toml` (module name to tier), not with an attribute
  on each module. One file is reviewable in one diff, needs no parser change, and the docs
  generator and a test can both read it.
- Rule: a stable module may call an experimental one internally, but no experimental type or
  function may appear in a stable module's public signatures. That keeps the promise about the
  stable surface without forcing every helper module to be stable.
- A use of an experimental module from user code is not a warning. The generated docs carry a
  badge, and `forge audit` lists the experimental modules a project imports.

**Done when:** the rule is written in `compatibility.md` and B2 can start.

### D4. `String.split(s, "")`

**The question.** Today every backend splits into bytes, which cuts a multi-byte character into
invalid one-byte strings (`specs/todos/2026-10-14-string-split-empty-separator-bytes.md`).

**Recommendation.** Split into one string per Unicode codepoint, with no empty strings at the
ends. It never produces invalid UTF-8, and it is cheap. Graphemes would be more correct for
display but need the segmentation tables on every backend. The change touches the C runtime, the
interpreter and the JS target, with one doctest pinning all of them.

**Done when:** the todo is closed and `String.split("héllo", "")` gives five strings on the
interpreter, compiled, the native REPL and the browser.

### D5. When an unreproduced flake counts as closed

**The question.** Decision 10 says a release candidate needs zero known flakes. Six of the ten
flake todos have never been reproduced (60,000 local runs for one of them). Without a closing
rule they stay open forever and 1.0 never ships.

**Recommendation.** A flake todo closes when either its cause is found and fixed, or all of:

- every sighting's evidence (log archive, core, binary) is attached to the todo;
- the fixture has run a stated number of consecutive iterations with no failure on the platform
  where it was seen (proposed: 20,000 iterations on amd64 Linux, or 30 consecutive green nightly
  loop runs);
- the failure-evidence capture from E3 is in place, so the next sighting cannot be lost.

A todo closed this way moves to `specs/progress/` marked "not reproduced, closed by soak", and
reopens on the next sighting.

## Base changes

### B1. `@[deprecated("use X instead")]` (M)

**Why.** The deprecation policy in `specs/lang/compatibility.md` promises this attribute. It does
not exist.

**Changes.**

- `lib/parser/parser.mly`, `fn_attr`: accept a string literal as an attribute payload.
  `fn_attr_args` already carries expression payloads for `decreases`, so the AST may need no
  change. Accept the attribute on `fn`, `type` and `mod`.
- `tree-sitter-march/grammar.js`: the same payload, in the same PR (CI's `tree-sitter` job
  enforces it).
- `lib/typecheck/`: record deprecated declarations in the environment; emit a warning with the
  code `deprecated` at each use, carrying the message. A use inside the deprecated declaration's
  own module does not warn.
- A `specs/lang/errors/deprecated.md` page; `test/errors/deprecated_1.march` and friends through
  `scripts/seed-error-corpus.sh`.
- The docs generator (`forge doc`, `scripts/gen-stdlib-docs.sh`) shows the message on the item.
- The LSP marks the diagnostic with the `Deprecated` tag so editors strike the name through.
- `specs/lang/compatibility.md`: change "planned" to the real syntax, then regenerate `docs/`.

**Done when:** a program that calls a deprecated function compiles, prints one warning per use
with the message, and exits 0; `--check-json` carries the code; the errors corpus pins the text.

### B2. Mark the stdlib tiers (M; waits on D3, the E6 triage and ocap phase 2)

**Changes.**

- `stdlib/stability.toml` listing every stdlib module.
- A test in the `stdlib` suite that fails when a module is missing from the file, and when a
  stable module's public signature names an experimental module's type.
- The generated stdlib pages show the tier.

**How to classify.** A module starts stable only if all of these hold: it has no open
wrong-answer bug from the E6 triage; its public items are documented (E7); it is not about to
change under object capabilities; its API has not changed in the last two releases. Everything
else starts experimental. Expect the first stable set to be small (`List`, `Map`, `Set`,
`String`, `Option`, `Result`, `Int`, `Float`, `Enum`, `Sort` if its stability bugs are fixed).

**Done when:** every module has a tier, the test is in CI, and `compatibility.md` no longer says
"the tiers don't exist yet".

## Gates

### G1. Release only from a commit with green CI (S)

**Today.** `release.yml`'s `publish` job has `needs: build` and nothing else. A tag on a red
commit ships.

**Changes.**

- A script, `scripts/release-gate.sh SHA`, that asks the GitHub API for `ci.yml` and
  `doc-lint.yml` runs with that head SHA on `main` and exits 0 only if each has a completed
  `success`. `nightly.yml`'s `gate` job already contains this query; share the code.
- A `gate` job in `release.yml` that runs it for the tag's commit, with `build` depending on it.
  The `workflow_dispatch` path (rebuilding an existing release's archives) skips the gate.
- Pushes to `main` share one concurrency group, so a commit in the middle of a burst of merges
  gets no CI verdict. `ci.yml` has no `workflow_dispatch` trigger; add one, so the release
  procedure can run CI on the exact commit to be tagged. The gate's error message says to do that.
- Later packages extend the same script: G6 adds "a green lab run on this commit".

**Done when:** the script exits non-zero for a known red `main` SHA and zero for a known green
one (both recorded in the PR), and the release ritual in the steward skill mentions it.

### G2. Refinement must-reject corpus (M)

**Today.** The refine oracle's corpus contains no violated obligation, so a change that made the
checker accept everything would stay green on the oracle. The typechecker has the model to copy:
`specs/lang/types/reject/` (289 fixtures) with `check_types.sh`.

**Changes.**

- `specs/lang/refine/reject/`: one small program per obligation kind, each of which must be
  reported violated with a counterexample: precondition, return refinement, division safety, Int
  overflow, element demand, fold invariant, termination metric, lemma, two-state handler
  guarantee, protocol payload refinement.
- A second group, one fixture per soundness bug already fixed, taken from `specs/progress/`
  entries that mention a false proof (the reflection reviews, the constructor registry, the
  element-flow reviews).
- `specs/lang/refine/known-accepted.txt`: reject fixtures the checker wrongly accepts today. It
  starts with the two gaps in E5 and may only shrink.
- A runner in CI's `conformance` job. Each fixture runs from a fresh working directory, because a
  warm VC cache replays a stored counterexample and can mask a regression. A fixture passes only
  if the verdict is "violated"; "skipped" or "unknown" fails.
- Add the directory to `scripts/refine-oracle.sh`'s corpus so the oracle pins the diagnostic text.

**Done when:** temporarily making `Refine_check` report every obligation proved turns the job
red, and the PR shows that run.

### G3. Differential runner over every conformance program (M)

**Today.** The golden corpus (48 programs) is checked interpreted against compiled. The property
oracle covers generated programs. Nothing runs the rest of the hand-written corpora on both
backends, and the one sweep that did (2026-10-12) found the payload-atom crash.

**Changes.**

- `scripts/differential.sh`: for every program with a `main` in `specs/lang/types/accept/` (205),
  `specs/lang/grammar/parse/`, `test/native/` (427 with an expected output), `examples/` and the
  golden corpus, compare stdout and exit status interpreted against `--compile`. Fan out over
  processes under a private `HOME`, as the oracles do.
- `test/differential-skip.txt`: programs excluded, each with a reason and a todo. Rules for
  whole classes (needs the network, needs a second node, prints an address or a time) are written
  once in the script. The file may only shrink.
- Where it runs: nightly in full, plus the release gate. Per PR, only when `lib/tir/`,
  `lib/eval/` or `runtime/` changed, through a rule in `scripts/affected.sh`.

**Done when:** the two payload-atom fixtures (`t12`, `p14`) show red before they are added to the
skip file, and the skip file's first version is reviewed line by line.

### G4. Leak gate (M)

**Today.** New leaks are filed about as fast as old ones close. `scripts/native-sanitize-sweep.sh
-l` (LeakSanitizer, Linux) reports on 70 of 355 fixtures, and the TIR verifier's leak check
(`MARCH_VERIFY_TIR_LEAKS=1`) reports seven findings in distributed stdlib code.

**Changes, three layers, cheapest first.**

1. *Live objects at exit.* For `bench/tree_transform`, `list_ops`, `binary_trees` and the string
   benchmarks, build with `--rc-trace` and assert `scripts/gc-trace-report.py` finds nothing live
   at exit. Runs on every platform in the existing `bench-gate` job.
2. *Verifier.* Run the corpus with `MARCH_VERIFY_TIR_LEAKS=1` and an allowlist of the seven known
   stdlib findings. A new finding fails.
3. *LeakSanitizer ratchet.* `test/native/lsan-known-leaks.txt` lists the fixtures that report
   today. The job fails when an unlisted fixture reports, and when a listed fixture is clean (so
   the list shrinks as E4 proceeds). Runs in the `sanitize-gate` shards if it fits their time,
   otherwise nightly and in the release gate.

**Done when:** a deliberately dropped `march_decrc` in a scratch branch fails layers 1 and 3, and
the known-leaks list is the work queue for E4.

### G5. Compile-time budget (M)

**Today.** `scripts/compile-time-bench.sh` and `bench/compile_time.py` measure where a compile
spends its time. Nothing fails when it gets slower. Absolute milliseconds do not work as a
baseline on these machines (`specs/benchmarks.md`).

**Changes.**

- *Scaling tests, per PR.* Generate programs of size N and 2N for each shape that has been
  superlinear before or plausibly could be: functions in a module, arms in a `match`, roles in an
  `@[endpoints]` protocol, fields in a record, nested modules, refinement obligations. Assert the
  time ratio is under 3. A ratio is stable on a noisy runner where a time is not.
- *A/B rows, nightly.* Add cold-compile rows to `scripts/perf-ab.sh` for a fixed set (hello
  world, the 193-line program from the road-to-1.0 plan, `examples/lab_app`, a refinement-heavy
  stdlib module with `--check`), last release against `main`, flagged beyond 10%.
- *Published budgets.* The numbers on the performance page (D2) come from the dedicated box, if
  D1 keeps one.

**Done when:** re-introducing a quadratic scan (the `Alloc_contract.decl_of` one fixed on
2026-10-07 is a ready example) turns a scaling test red.

### G6. Multi-host lab as a gate, with mixed versions (M)

**Today.** `scripts/lab/` deploys `examples/lab_app` to four containers over ssh and through the
control plane, with scenarios `deploy`, `failover`, `hot_role`, `restart_persist` and an opt-in
soak. It runs by hand. Its prerequisite, the missing two-node golden passes, closed 2026-11-07.

**Changes.**

- A `mixed_version` scenario (decision 11): a leader from the last release with agents from this
  commit, and the reverse. It deploys, hot-reloads and rolls back. It needs the last release's
  archive, fetched the way `install.sh` does.
- A `lab` workflow that runs every scenario but the soak nightly on `main` and on demand, and
  uploads each host's logs. `scripts/lab/run.sh` exits 3 when the machine was too loaded to trust
  the result; the workflow reruns once on 3 and fails on a second 3.
- `scripts/release-gate.sh` (G1) requires a green lab run on the commit being tagged.
- Not per PR: four containers and an ssh mesh cost too many runner minutes.

**Done when:** the nightly has been green for a week, and a deliberately incompatible change to a
control message makes `mixed_version` fail.

## Deploy correctness

### P1. Static output Stage 5 and the musl allocator measurement (M)

Design: `specs/2026-09-23-static-compile-output-design.md`, Stage 5 and §4.4. Stages 0-4 and 6
are in.

- Measure first. Run `bench/binary_trees`, `list_ops` and one HTTP benchmark as a glibc build and

  allocator shows directly. Record the ratio in the design.
- If musl is more than a stated factor slower (propose 1.5), decide between documenting it and
  linking a different allocator into static builds. That is an owner decision; the measurement
  frames it.
- Then build `--target linux/<arch>-musl` as the design describes, add it to the cross-linux
  oracle job, and close `specs/todos/2026-09-02-march-compile-output-is-not-static.md`.

**Done when:** a binary cross-built on macOS runs in a bare `scratch` container on both Linux
architectures in CI, and the allocator numbers are published.

### P2. Control plane remainder and format versioning (L)

Decision 11 puts the cluster control plane in 1.0 and promises that the release file format, the
control API verbs and the node-to-node control messages stay compatible across 1.x. So anything
that changes those formats must land before the freeze, and each format needs a version.

**Do before the freeze (format-affecting).**

- *Version audit.* Confirm the release file, each control API verb and each `Ctl` message carries
  a version field, and add a test that pins the encoded bytes of each (a golden file per format).
  A change to a pinned encoding then shows up in review.
- *Builds per target.* A release names one patch per build, so a cluster whose hosts span two
  targets is refused (`specs/todos/2026-09-28-dd-step12a-control-wiring.md`). Lifting that
  changes the release format. Either do it now, or reserve the field now and implement it in 1.x.
  Recommendation: reserve the field.
- *A `NODE` line or `DETAIL` verb in `STATUS`* carrying live sessions, hot slots and the patch
  stack, so plans on the cluster backend see what plans over ssh see. This adds to the control
  API; additions are compatible, so it can also wait for 1.x.

**Do before 1.0 (not format-affecting).**

- Move `Ctl` and `CtlFetch` into `stdlib/control.march` (the todo has the four steps and says it
  was tried on a copy and passed).
- Remove the two record-update workarounds in the wiring; the bugs they avoided are fixed.
- Persist the agent's replay floor for certificate releases (`Control.cert_floor`), which is lost
  on restart today (`specs/todos/2026-09-22-dd-step12-control-plane.md`).
- Clear a node's old failure from `STATUS` once a later release succeeds on it.
- A test that provokes a skipped-gate report.

**Recommend leaving out of 1.0, in writing:** step 12c (self-restart, an external lease), the
deferred issuer design, the `k8s` generator and `replicas`
(`specs/todos/2026-09-22-dd-step07-topology-file.md`). The owner confirms; the platform and
compatibility pages then say so.

**Done when:** the golden-bytes tests exist, the todos for 12a, 12 and 07 are closed or trimmed to
items explicitly marked post-1.0, and G6's `mixed_version` scenario is green.

### P3. Sigstore signing of release artifacts (L)

Decision 9: Sigstore keyless, with GitHub OIDC in CI; the bundle ships next to each artifact;
`install.sh` and forge verify it offline against the pinned workflow identity. Nothing signs
today.

**Write a short design note first.** The open point is the verifier. Signing in `build.yml` with
`cosign` is routine. Verifying is not: `install.sh` is a shell script that cannot assume `cosign`
is installed, and forge is OCaml with no Sigstore library. The options are: require `cosign` and
fail closed without it; verify in forge only and have `install.sh` verify a checksum that forge
later confirms; or implement bundle verification in forge. The note picks one and says what
"offline" means for the trusted root.

**Then.**

- `build.yml`: sign each archive, upload the bundle as a release asset.
- `install.sh` and `forge toolchain`: verify against the pinned identity (this repository, the
  release workflow, a `v*` tag ref). A missing or bad bundle is an error, with a flag to install
  an older unsigned release.
- A CI check that a tampered archive fails verification.
- Decide how this relates to `specs/todos/2026-08-03-forge-wide-artifact-signing.md` (ed25519
  signing of forge-built artifacts). They cover different artifacts and can stay separate.

Registry notarization follows this but is capability work and is not planned here.

**Done when:** a release candidate's archives verify with the published identity, and a modified
archive is refused by both installers.

## Burn-down

### E1. P1: a user type named like a built-in or stdlib type is that type (L)

Todo: `specs/todos/2026-11-02-typecheck-conflates-same-short-named-types.md`. A user
`type CancelToken = Tok(Int)` unifies with the built-in `CancelToken`; interpreted it takes the
wrong match arm, and compiled it emits invalid LLVM. Nested-module collisions were fixed by #1235
and function and module collisions by #1241. This half is separate because the typechecker
decides a type's identity by its bare name before lowering sees anything.

**Steps.**

1. *Audit.* Add a temporary warning when an entry-level type's name is in
   `Typecheck_builtins.builtin_type_names` or is a stdlib type's name. Run it over `test/`,
   `examples/`, `specs/lang/` and the stdlib. The count decides step 2.
2. *Choose.* Either give the colliding user type its own identity (register built-in and stdlib
   type names as declared at a pseudo path in `Typecheck_nominal`, as the todo sketches), or
   reject the declaration. Recommendation: its own identity, consistent with #1235; reject only
   names the runtime hard-codes, as #1222 did for `DownReason`.
3. *Fix, tests first:* reject fixtures in `specs/lang/types/reject/` for `A.g(B.ZB)`-style misuse
   against a built-in, a golden program on both backends, the `CancelToken` probe compiled.
4. *Relax the workaround.* The refinement checker resolves no constructor for a datatype whose
   short name two declarants share. Remove that rule for the cases now distinct and re-run the
   refine oracle.
5. The types oracle and the Lean re-checker (`march-lean-dispatch.yml`) must both agree.

**Done when:** the todo moves to `specs/progress/` and there are no `[P1]` todos.

### E2. P2 miscompiles and crashes

### E3. Flakes and SIGSEGVs (M)

### E8. Perf to the targets (L; after D1)

The work depends on which benchmarks miss the D1 targets. The known candidates:

- *Allocation.* `march_alloc` zero-fills every object and has no bump path
  (`specs/todos/2026-08-04-x86-benchmark-findings.md`). This is what `binary_trees` measures.
- *Index loops.* About four calls and a volatile load per iteration
  (`specs/todos/2026-08-11-march-index-loop-per-iteration-overhead.md`).
- *Session message framing.* One cons cell and one tagged Int per byte on the wire. A byte
  payload type for sessions fixes it and lets `CtlFetch` return to the control-plane wiring (P2).

Every change is measured with `scripts/perf-ab.sh` and run compiled, never interpreted.

**Done when:** the nightly A/B shows no regression against the last release and the competitor
ratios on the performance page meet the D1 targets, or the page states which do not and why.

## Freeze

Starts when object capabilities have landed, every gate is green, and there are no `[P1]` todos.

### F1. Results page per release (S)

`release.yml` generates a page from data the gates already produce: the perf A/B table, the
compile-time rows, the leak lists (ideally empty), the differential skip file, the refinement
known-accepted list, the lab scenarios run and the platforms built. It publishes under `docs/` and
is linked from the release notes. Its purpose is that each 1.0 claim points at a measurement.

### F2. Release-candidate procedure (S)

- `scripts/rc-check.sh`: exits non-zero if any `[P1]` todo exists, any flake todo is open, any
  ratchet file (`lsan-known-leaks.txt`, `known-accepted.txt`, the differential skip file) holds
  a line without a post-1.0 reason, or `scripts/release-gate.sh` fails for the commit.
- Tags are `v1.0.0-rc.N`. Check that `scripts/check-version-tag.sh`, `forge`'s version resolver
  and `install.sh` order a prerelease below `1.0.0` and that `march = "~> 1.0"` does not select
  one.
- Each candidate soaks for a stated period (propose two weeks) with the lab soak scenario running
  and the nightly gates green. A P1 or a flake found during the soak resets the count with a new
  candidate. This is decision 10.
- The stdlib tiers are marked (B2), `compatibility.md` has no "planned" left, and the CHANGELOG's
  `[Unreleased]` becomes `1.0.0`.

**Done when:** a candidate completes its soak with `scripts/rc-check.sh` green. That candidate is
1.0.

## Risks

- **The flake policy.** Without D5, decision 10 cannot be met. With it, 1.0 may ship with a rare
  crash that was never understood. The evidence capture in E3 is what makes that an acceptable
  trade.
- **`binary_trees`.** A twenty-fold gap against OCaml on an allocation benchmark will be the
  first thing a reader of the performance page sees. D1 has to either fund the allocator work or
  state the gap.
- **The Sigstore verifier.** P3 is the package most likely to grow. If offline verification in
  forge proves large, signing can ship first with verification through `cosign`, and the
  installer's built-in check can follow in 1.x; that weakens decision 9 and needs the owner.
- **Runner budget.** Five new gates on a 20-job Linux budget. The plan moves three of them to
  nightly and the release gate; if PR queue times still grow, G3's per-PR subset goes first.
- **Coupling to object capabilities.** B2 and the freeze wait on it. If it slips, the
  non-capability work here finishes first and waits.
