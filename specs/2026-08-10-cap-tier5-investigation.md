# Tier 5 investigation: registry notarization and Linux seccomp/Landlock

Both items were characterized as "genuinely blocked" in
`specs/2026-08-09-cap-loose-ends-plan.md`. That's still true for the actual
network round-trip and for Landlock specifically — but the investigation
below narrows both scopes materially, and finds one of the two items thought
to be about-equally hard (`IO.NetListen`) is not hard at all, just unbuilt.

No Linux machine was available to verify anything below at runtime (this
session ran on Darwin). Nothing here should be read as "shipped" — it's a
precise scoping, with one piece of code sketched to the point of being
almost a patch, flagged as unverified.

## Registry notarization — narrower than filed

The todo (`specs/todos/2026-08-03-registry-capability-notarization.md`)
lists `cmd_publish.ml: cap_set_of_project` as a client-side TODO, with a
2026-08-03 measurement that a naive per-file `march caps` invocation
under-reports badly (conduit 9/43 files analyzable, 0/25 if `MARCH_LIB_PATH`
is set to the package's own `lib/`).

**That function already exists**, just not under that name and not in
`cmd_publish.ml`. `Cap_package.of_package` (`forge/lib/cap_package.ml`,
added after this todo was filed) does exactly what was asked:
- passes ALL of a package's `.march` files (`Cmd_build.find_march_files`) to
  ONE `march caps` invocation, not one call per file
- uses the real per-project `Cmd_build.lib_path_env` prefix, not a
  self-referential `MARCH_LIB_PATH`
- fails LOUDLY (`Error` with the compiler's stderr) on any nonzero exit,
  never silently falls back to "no capabilities"

Confirmed by grep: it's currently called from exactly one place,
`cmd_audit.ml`'s `inferred_caps_of_dir`. `cmd_publish.ml`'s own
`Registry_client.run_action` call passes `~extra_env:[]` — no capability
data flows into a publish today at all.

**What's actually left, precisely:**
1. Wiring: `cmd_publish.ml` calls `Cap_package.of_package
   ~root:proj.Project.root ~env_prefix:(Cmd_build.lib_path_env proj)` and
   passes the result through `extra_env` to the embedded march client
   process — small, mechanical, no new analysis. Not done in this
   investigation; see "why not" below.
2. `forge/tasks/forge_registry.march` (the todo's file reference,
   `forge/tasks/registry.march`, is itself stale — the file is named
   `forge_registry.march` today; fix that pointer while touching this)
   reads the env var and includes it in the publish multipart body.
3. **The forgepm server** accepts and stores a `caps` field, and returns it
   from the metadata endpoint. External repo, no path around it.
4. `forge cap inspect --notarized` compares a binary's measured caps
   against the registry record via `Cap_lattice.cap_subsumes` (not string
   equality — a binary needing `IO.FileRead` is consistent with a
   registry record of `IO`), with `registry-unreachable` never rendering
   as a match.

**Why item 1 isn't wired in this investigation despite being unblocked**:
sending an unverifiable field is exactly what the todo's own caution is
about — "do not land a client that sends a field the server silently
drops." Wiring `extra_env` now, with `forge_registry.march` still not
reading it, is harmless (an inert env var), but wiring `forge_registry.march`
to actually put it on the wire before the server contract is confirmed would
produce a payload nobody can verify is received or stored correctly — that's
the part worth waiting on real server coordination for. Items 3+4 are
unavoidably external.

**Recommendation**: when forgepm work starts, steps 1-2 are now roughly a
half-day of plumbing, not a design problem — the hard part (correct,
non-under-reporting capability extraction) is already solved and load-bearing
in production (`forge audit --inferred` uses it today).

## Linux seccomp/Landlock — the two items are NOT the same size

The existing filter is `runtime/march_runtime.c` (~line 1782,
`march_sandbox_install`), a hand-built seccomp-bpf program gated by four
`-D` flags (`MARCH_CAP_DENY_NET/EXEC/WRITE`, derived in `bin/main.ml` from
the program's own capability set the same way the macOS SBPL profile is
built — one decision, two backends, per that code's own comment). Read the
whole function before touching it; the BPF program is hand-assembled
(`sock_filter`/`BPF_JUMP`/`BPF_STMT` macros), not generated by a library, and
every existing `DENY_NR` is a two-instruction pattern with fixed jump
offsets — get an offset wrong and the filter doesn't fail loudly, it
silently permits or denies the wrong thing.

### `IO.NetListen` is a ~20-line extension of the EXISTING pattern, not a new mechanism

Traced precisely why it's unenforced today: `holds klass` in `bin/main.ml`
(~line 3431) is bidirectional — `cap_subsumes klass c || cap_subsumes c
klass` — so a program holding only `IO.NetConnect` makes `holds "IO.Network"`
true (NetConnect is a descendant of Network), which clears
`MARCH_CAP_DENY_NET`, which allows `socket()` outright. Since `socket()` is
the ONE syscall both `connect()` and `bind()`+`listen()` need, and nothing
denies `bind`/`listen` specifically, a NetConnect-only program (the common
case — an HTTP client) can currently also listen on a socket, with nothing
in the current filter able to tell the two apart.

Closing it needs exactly the same shape as the existing `WRITE` class: a
new `MARCH_CAP_DENY_LISTEN` flag, derived in `bin/main.ml` from
`not (holds "IO.NetListen")`, and two more `DENY_NR` calls in
`march_sandbox_install`:

```c
#ifdef MARCH_CAP_DENY_LISTEN
    DENY_NR(__NR_bind);
    DENY_NR(__NR_listen);
#endif
```

placed inside the existing `#ifdef` structure (after the `EXEC` block, say —
order doesn't matter, each `DENY_NR` is independent). The `bin/main.ml` side
mirrors the existing three:

```ocaml
^ deny "LISTEN" (holds "IO.NetListen")
```

**This is a correctness fix for an existing feature, not new machinery.**
The `MAX_FILTER` bound (96) has headroom — the current filter uses well
under half that even fully expanded. Genuinely low risk of the kind of
mistake this codebase has repeatedly hit elsewhere (two independently
duplicated decision points drifting) because it slots into the SAME
single decision point (`bin/main.ml`'s `deny_flags` construction) the other
three classes already share.

**Not implemented here** — no Linux machine to verify against, and this is
exactly the kind of change where "I wrote plausible BPF and it compiled"
is worth nothing without an actual `bind()`/`listen()` call observably
returning `EPERM` under the real filter, while `connect()` on the same
program still succeeds. See the CI gap below — that's the blocker for
actually landing this safely, not the code itself.

### `IO.FileRead` via Landlock is a genuinely different, larger piece of work

Landlock (Linux 5.13+, unprivileged via `landlock_restrict_self` +
`PR_SET_NO_NEW_PRIVS`, same unprivileged-sandboxing philosophy as seccomp)
is a *path-based* LSM, structurally unlike seccomp-bpf: instead of a BPF
program inspecting syscall args, it's three syscalls
(`landlock_create_ruleset`, `landlock_add_rule` — called once per allowed
path, with an access-rights bitmask — `landlock_restrict_self`), and the
kernel enforces path resolution against the ruleset from then on. This is
NOT an extension of the existing BPF-assembly code; it's a new subsystem
with its own header (`linux/landlock.h`, only in recent enough kernel
headers — build-time availability needs a feature-test, not just a runtime
one, since the header may not exist on the build host at all) and its own
runtime-availability check (Landlock can be MAC_LSM-disabled at the
distro/kernel-config level even on a 5.13+ kernel — `landlock_create_ruleset`
with the `LANDLOCK_CREATE_RULESET_VERSION` flag is the documented way to
probe for this, and the fallback behavior when it's unavailable needs a
decision: fail closed like seccomp already does, or degrade to today's
advisory behavior with a printed warning — the two backends currently
disagree here in spirit, since the existing seccomp filter fails closed on
install failure specifically because "running uncontained after the
operator asked for containment is the worst outcome," and Landlock
unavailability on an older-but-supported kernel would need the same
judgment call made explicitly, not by accident).

The bigger design question: `IO.FileRead` scoping needs to know WHICH paths
to allow, which the seccomp model never needed (it only ever made
all-or-nothing per-syscall-class decisions). `forge cap run` already solves
an analogous problem externally via a bwrap mount-namespace allow-list
(`forge/lib/cap_sandbox.ml`'s `bwrap_args`, the `loader_paths` list) — that
existing design is probably the right model to port: an explicit path
allow-list (`@[scope("...")]`-declared paths, mirroring how `IO.FileWrite`
scoping already works via `declared_cap_scopes`/`Cap_scope.normalize` in the
current SBPL/seccomp write path) rather than trying to infer "the paths this
program might read" automatically.

**Scope estimate, relative to the NetListen fix above**: at minimum a new
runtime C file (or a substantial addition to `march_runtime.c`) for the
Landlock ruleset construction, a design decision on the scoping-declaration
surface (reuse `@[scope]` or need something new for read-scopes
specifically — today only write is scoped), a kernel-version/availability
probe with an explicit fallback policy, and real Linux testing across at
least two kernel versions (a 5.13-era minimum and something current) to
verify the availability probe actually degrades correctly rather than just
working on whatever kernel happens to be in CI. This is a multi-day design +
implementation project on its own, not a follow-on to the NetListen fix.

## The finding that matters most: none of this is verified in CI today

Grepped the whole test suite and `.github/workflows/ci.yml`: **no test
anywhere actually runs a `--cap-sandbox` binary under seccomp and checks
that a denied syscall returns `EPERM`, or that an allowed one succeeds.**
`test/test_cap_sandbox_profile.ml` and `test/test_cap_strip.ml` verify the
embedded SBPL/seccomp-flag STRINGS are correct and consistent between the
two builders (that's what #240's stack shipped) — nothing verifies runtime
enforcement, on either platform. The `IO.Network`/`IO.Process`/
`IO.FileWrite` seccomp deny classes that have been shipping since before
this session started have never had their actual kernel-level behavior
checked by CI.

This is a bigger and more urgent gap than either `IO.NetListen` or
Landlock specifically — it means the sandbox's core claim ("this syscall is
actually denied") rests entirely on the BPF assembly being correct by
inspection, with no regression protection if a future refactor breaks an
offset. **Recommend building this before extending the filter further**:
a Linux-only CI job (the `ubuntu-24.04` runners already exist in the matrix)
that compiles a tiny program with each deny class individually, runs it,
and asserts the syscall it tries actually fails with EPERM while an
unrelated allowed syscall still succeeds. This would also be the natural
place to add the `IO.NetListen` connect-vs-listen assertion once that fix
lands, and would catch a broken BPF offset the way `test_cap_symbols.ml`'s
drift test catches a broken capability-table entry — the same "test the
actual mechanism, not just its stringified description" principle this
session's #240 fix was built on.

## Recommendation

- Registry notarization: wait for forgepm coordination; the client-side
  extraction risk is already retired.
- `IO.NetListen`: small, well-scoped, low-risk — but land it TOGETHER with
  the runtime-enforcement CI job above, not before, so it ships with actual
  proof it works rather than a plausible-looking BPF diff.
- Landlock: needs its own design doc before any code, scoped as its own
  project, not bundled with the NetListen fix.
- File a todo for the CI verification gap specifically — it's independently
  valuable even if nobody touches NetListen/Landlock for a while.
