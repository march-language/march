✅ **Typed JSON decoding plan, Task 2 — `to_json` dispatches through `impl_tbl`, fixing nested/cross-type shadowing (2026-07-31, `lib/eval/eval.ml`, `test/stdlib/test_json_typed.march`).** Investigation (mandated by the task brief before any edit) found the premise had partly moved on since Task 1: `lib/desugar/desugar.ml`'s `"Json"` branch already generates a `DImpl` per type (pseudo-interfaces `"JsonTo"`/`"JsonFrom"`, not a bare top-level `DFn` as Task 1's writeup implied), and `lib/eval/eval.ml` already has a `to_json`/`from_json` builtin pair that reads `impl_tbl ("JsonTo"/"JsonFrom", type_name)` — this machinery has existed since March 2026, well before Task 1. Direct-call cross-type dispatch (`to_json(flat_val)` then `to_json(shape_val)` in one module) already worked correctly on both backends. The REAL bug, confirmed with a fresh repro (`type Inner = {id:Int}` nested as a field of `type Outer = {label:String, inner:Inner}`, both `derive Json`): `to_json(outer_val)` panicked `record has no field 'label'`. Root cause: `is_type_dispatched_method` (gates whether a `DImpl` method is bound as a plain builtin-dispatching closure vs. eval'd through the ordinary `DFn` path) listed only `Show`/`Eq`/`Ord`/`Hash`, not `to_json` — so the `DImpl` eval's catch-all branch bound `to_json` via `eval_decl`'s `DFn` case, which builds a **self-recursive** closure. `encoder_for_ty`'s recursive-call fallback for any non-primitive field (`EApp (EVar "to_json", [value_expr])`, desugar.ml ~1496) then resolved, inside that self-recursive closure, back to the SAME enclosing type's encoder instead of dispatching by the field value's runtime type via `impl_tbl` — reproduces with exactly two types, independent of the flat multi-type case Task 1 actually demonstrated (which was already working). **Fix:** added `("JsonTo", "to_json")` to `is_type_dispatched_method` (eval.ml ~300) — one line, plus doc-comment updates explaining why and correcting a stale claim that non-builtin ifaces "don't get read by value" from `impl_tbl` (Json's `to_json` builtin already did). No `desugar.ml` change was needed or made. `from_json` is untouched and deliberately excluded (its cross-type/nested-panic bugs remain exactly as documented in Task 1 — no value of the target type to dispatch on at a `from_json` call site; tracked in `specs/2026-07-31-json-from-json-dispatch-design.md`). Compiled (LLVM) backend: same nested-field `to_json` shape still fails to LINK (`undefined symbol _to_json`) — a distinct, pre-existing gap in the general-interface static-dispatch path (`lib/tir/lower_state.ml`'s `resolve_iface_method`, keyed by AST span; desugar's Json-derive nodes all carry `dummy_span`, so span-keyed type lookups collide) — confirmed present identically before this change; explicitly out of scope for this task (the brief scopes "to_json only," not "to_json on every backend," and fixing it needs either unique spans on derived nodes or a structural per-ADT codegen path analogous to Eq/Show/Ord/Hash, a separate task). Two new tests added to `test/stdlib/test_json_typed.march`'s new `"to_json cross-type dispatch (fixed)"` describe block: the brief's Flat/Tag direct-dispatch case (was already passing pre-fix; kept as a regression pin) and a new `Nested`/`NestedHolder` case pinning the nested-field panic fix. `test_json_typed` 137→149 tests (interpreted), all green; `run_compiler` 620/620; `test_derive_json`/`test_island_bridges` unchanged (their pre-existing `from_json`-only failures reproduce byte-identically on both pre- and post-fix builds, confirmed by a file-swap control).
