- ✅ **Static capture-free closures — one immortal global per top-level function value instead of a per-materialization heap allocation (2026-07-28, `lib/tir/llvm_ctx.ml` `intern_static_closure` + `static_clos` memo, both closure-materialization sites in `lib/tir/llvm_emit.ml`).** A top-level function materialized as a first-class value (`let f = some_fn`, passed as a callback, stored in a list/tuple, …) whose closure captures nothing was allocated fresh via `march_alloc(i64 24)` at *every* materialization, every time it executed, and never freed via normal RC — an unbounded per-materialization leak in any loop that repeatedly took a function value. Fixed by emitting one `internal global` per top-level function used as a value (`@<fn>$static_clo`, LLVM type `{i64,i32,i32,ptr}` = refcount, tag, `march_hdr.pad`, code pointer, refcount pre-set to `MARCH_RC_IMMORTAL` = 1099511627776), memoized by function name so repeated materializations resolve to the same global and distinct functions get distinct globals. Ordinary RC inc/dec code at call sites still executes against the global (e.g. `march_incrc_local` directly against `@<fn>$static_clo`) — those are atomic read-modify-writes on a now module-wide-shared cache line that never drive the refcount to zero, i.e. **never-freeing, not no-ops** (no evidence of contention: an 8-task `Task.async` workload over a shared closure showed correct results, 0.33s, 52 allocs, no RC underflow, but the multi-thread-contention question is not foreclosed by this fix). Declared mutable (`internal global`, not `constant`) because those routine RC stores must remain valid; a `constant` global would make them undefined behavior. **Measured** (4,000,000 materializations of a named function value, compiled `--opt 2`): `obj_allocs` 4,000,000 → 0, peak RSS 125.4 MB → 2.9 MB, wall 0.09s → 0.01s — matching a control that calls the function directly with no value materialization at all. **Gated OFF** (via a shared `static_closure_ok` predicate) for the REPL/JIT (`ctx.repl` — each REPL eval compiles/links a fresh module, so a baked-in global can't be safely shared or discarded across the incremental-compilation lifecycle) and hot-reload boundary functions (`ctx.hr_config` + `Hot_reload.is_reloadable` — defensive, not a fix for a demonstrated staleness bug: the fresh-alloc fallback bakes in the identical `@<fn>$clo_wrap` pointer, and `clo_wrap_define` already emits a hardcoded direct `call @<fn>` that bypasses the versioned HCR dispatch table regardless of path — a pre-existing, already-documented HCR gap this change doesn't touch; the exclusion keeps this change strictly non-regressive for HCR rather than claiming to fix that gap). **Does NOT cover capturing closures** — see the new open item below, found during this same work and deliberately left unfixed here since it needs a genuine `perceus.ml`/`borrow.ml` ownership fix, not a codegen change. **At the time of this entry, also did not cover capture-free LAMBDA values** (as opposed to top-level named functions) — since fixed, see the "Static capture-free LAMBDA values" Done entry above. Verified via `llvm_builtins_preamble_golden` (static-global-replaces-alloc, REPL-mode exclusion via `emit_repl_expr`, and REPL-mode exclusion via `emit_fns_fragment ~repl:true`), a compiled/interpreted parity fixture proving function-value semantics are unchanged (`test/native/static_closure_semantics.march`) plus the runtime-live-allocs growth assertion in `test/test_codegen.ml` (`test_static_closure_materialization_no_leak_compiled`), and a compiled/interpreted parity fixture proving no cross-function global collision (`test/native/static_closure_semantics.march`, 3 distinct `$static_clo` globals for 3 distinct functions). Benchmark controls (`bench/list_ops.march`, `bench/binary_trees.march`, neither of which materializes a named top-level function as a value) ran clean, no measurable before/after difference — see `specs/progress.md` for the numbers.
