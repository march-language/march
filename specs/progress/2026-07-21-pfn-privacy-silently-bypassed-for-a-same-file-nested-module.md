- ✅ **`pfn` privacy silently bypassed for a same-file nested-module member whose bare name collides with an unrelated global — typechecked clean, ran correctly interpreted, produced a garbage value compiled (2026-07-21, `lib/typecheck/typecheck.ml`, `test/test_compiler.ml`).** Found auditing `docs/cookbook/basics.md`'s claim that `pfn` cross-module calls are rejected — TRUE in general (the `c0570d16`/`96ec5969` gates below still hold for every plain repro), but `mod Main do mod Auth do pfn hash(s) do ... end fn verify(...) do hash(plain) == stored end end fn main() do println(Auth.hash("x")) end end` typechecked clean, printed the correct `"x-hashed"` interpreted, and printed a garbage 64-bit value (e.g. `-5808529385363204345`) when compiled — a privacy violation that ALSO corrupts the value, not just a missing diagnostic. **Root cause is DISTINCT from the `opaque type` constructor-hiding gap** (see the RESOLVED P2 entry above — that one was an ungated Pass-1 registration path in `prebind_mod_members`, now fixed separately; this one never reaches Pass-1's or Pass-2's registration at all — both correctly refuse to bind `Auth.hash` for a private member, confirmed by tracing and by a non-colliding-name variant (`Auth.totally_unique_secret_name`) already rejecting correctly pre-fix). The actual bug: `EVar`'s "final fallback" in `infer_expr` (`:3556-3568` pre-fix), meant only to resolve multi-component **interface-method** paths like `"Conduit.Storage.workflow_load"` down to their shorter registered form `"Storage.workflow_load"`, has no floor — it strips a failed qualified lookup ALL the way down to a bare, unqualified name and retries `lookup_var` on that. For `"Auth.hash"` this bottoms out at bare `"hash"`, which IS bound globally (the `Hash` interface's built-in method scheme, `typecheck.ml:1342`) — so the fallback silently resolves the call to the wrong, unrelated global instead of ever reaching the private-member check, and typecheck happily assigns the WRONG type to the call site. Codegen still calls the REAL (private) `Auth.hash` by name (eval's and TIR's own module-qualified name resolution are independent of `env.vars` and correctly find it), so the compiled binary computes with a representation mismatch between what typecheck inferred and what's actually invoked — hence the garbage output. Both defects (missing rejection, garbage compiled value) share this one root cause and both are fixed by the same change. **Fix:** new `is_confirmed_private_qualified` helper (checks `env.local_mods` for an in-file nested module and the module registry's `ex_public` for a cross-file one, factored out of `qualified_error_msg`'s existing detection) is consulted BEFORE the dot-suffix fallback in `EVar`'s resolution; a confirmed-private qualified reference now reports `` Function `hash` is private to module `Auth`. `` immediately instead of falling through. The legitimate interface-method suffix case is untouched (it isn't a confirmed-private qualified reference, so the fallback still runs for it).
