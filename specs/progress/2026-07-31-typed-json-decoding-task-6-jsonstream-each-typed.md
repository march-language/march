✅ **Typed JSON decoding plan, Task 6 — `JsonStream.each_typed` decodes NDJSON to typed records and attaches each record's byte offset (2026-07-31, `stdlib/json_stream.march`, `test/stdlib/test_json_typed.march`).** A new driver on top of the existing (frozen) tokenizer/event API — `feed`/`finish`/`go` and the `JsonStreamError`/`JsFrame`/`build_step` machinery are untouched — modeled on `each_value` but decoding each completed top-level value with the caller's `derive Json`-generated `from_json` before invoking `cb`. **Key design point:** `from_json` is called bare, not `Json.from_json` — `derive Json for T` binds it as a plain name in the environment (it cannot dispatch on argument type the way `to_json` does, since every call site's argument is the same `JsonValue`; see `lib/eval/eval.ml`'s `is_json_iface` handling and `specs/2026-07-31-json-from-json-dispatch-design.md`), so a bare `from_json` call written inside `stdlib/json_stream.march` resolves, at the CALLING test's runtime, to whichever type that caller's module last derived Json for — confirmed empirically with a two-module experiment (a helper module with no `derive Json` at all, calling bare `from_json`, correctly reached the entry module's decoder) before relying on it. **Byte-offset mechanism:** unlike `each_value` (64KB chunks, agnostic to record boundaries), `each_typed` feeds the tokenizer one line at a time via `File.with_lines` — NDJSON is one record per line, so the running count of bytes fed so far, captured just before each line's `feed` call, is exactly that record's start offset; this is independent of (does not read) the tokenizer's own internal `StOk` offset field. A decode failure (`from_json` returns `Err`) gets that offset attached via `Json.decode_error_at`; a tokenizer-level failure (malformed JSON) is converted to a `Json.DecodeError` using the tokenizer's own more-precise reported offset instead. Type: `each_typed(path, cb) : Result(Int, Json.DecodeError)`, returning the record count on success, or the FIRST failure (tokenizer or decode). Verified the byte-offset arithmetic against actual output rather than trusting it: `File.write(path, "{\"id\":1}\n{\"id\":\"nope\"}\n")` (record 1 is 8 bytes + `\n` = 9) produces `Json.decode_error_to_string(e) == "$.id (byte 9): expected Int"` exactly, confirmed by running the test and reading its printed message. Final review independently hand-counted a 3-good-then-1-bad NDJSON file (27 bytes for 3 valid records) and confirmed the offset lands exactly at byte 27, ruling out both "stuck at first record" and "off by one record" failure modes specifically. New `"each_typed carries the record's byte offset"` describe block, 2 tests. `test/stdlib/test_json_stream.march` (phase 1/2's frozen tokenizer suite, 239 tests) re-run unchanged and green — confirms this task touched nothing the tokenizer's own guarantees depend on. **Known caveat found at final review (not fixed, documented):** the offset arithmetic (`off + string_byte_length(line) + 1`) hardcodes an LF-only line terminator — correct today only because the interpreter's `File.with_lines` leaves a stray `\r` counted in a CRLF line's length, while the C runtime backend strips both `\r` and `\n` explicitly and would undercount by 1 byte/line on CRLF input. Currently unreachable (compiled `from_json`/`each_typed` calls fail to link at all — see the compiled-backend link gap below); would need revisiting if that gap is ever closed.
