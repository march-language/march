- ✅ **Tuple projection forwarding (`lib/tir/cprop.ml`, extends P13, 2026-07-28).** `let t = (a, b) in t.$fv0` now folds to `a`, exactly like the existing record case (`let r = {x=a,y=b} in r.x → a`) — closing the gap the original SCC-inliner/single-use-inlining assessment flagged as still open. Tuple field lists are keyed by `Tir_names.fv_field i` (0-based), matching `lib/tir/lower.ml`'s existing tuple-destructure lowering (`let (a, b) = rhs` desugars to that exact `EField` shape), so ordinary `let`-pattern tuple destructuring benefits automatically with no lowering change. Field-name collision with closure-capture struct fields (`defun.ml`, also `$fvN`, 1-based) is impossible by construction — `field_env` is populated purely from a binding's own shape (`ETuple`/`ERecord`/`EUpdate`/alias), never from the field-name string, and a closure-capture struct is built via `EAlloc`, never `ETuple`. DCE removes the now-dead tuple binding in the same `Opt` fixed-point iteration with no changes to `dce.ml`/`opt.ml`. **Discovered, deliberately NOT fixed here (separate, pre-existing issue):** `lib/tir/perceus.ml`'s `dup_field_results` (escape-safety dup for a field returned bare in result position) matches only `Tir.TRecord`, never `Tir.TTuple` — orthogonal to this change, filed as a follow-up. 7 new tests (`cprop` group: `field_fold_tuple`, `field_fold_tuple_second_element`, `field_fold_tuple_alias`, `field_fold_tuple_non_literal_element`, `no_tuple_field_collision_with_closure_capture`, `tuple_field_result_escape_unchanged`, `tuple_dce_removes_allocation_from_llvm`) plus a native golden (`tuple_destructure_dce`). No benchmark under `bench/` exercises this pattern directly (confirmed by inspection); `list_ops`/`binary_trees` run clean as no-regression controls.
