- ✅ **`int_div_euclid` native codegen — the last of the four `int_div`/`int_mod` family missing from the LLVM backend (2026-07-10).** The builtin existed in the interpreter (`lib/eval/eval.ml`, Euclidean quotient) and had a JS-target mapping (`march_int_div_euclid` in `runtime/march_runtime.mjs` via `lib/tir/js_emit.ml`), but had **no native codegen mapping**: compiling any caller failed at link time with `Undefined symbols: _int_div_euclid`. It was already correctly listed in `defun.ml`'s `builtin_names` (and `policy_dce.ml`/`purity.ml`), so it stayed an `EApp`/`ECallPtr` rather than being defunctionalized — the gap was purely the emit + runtime symbol. Fix mirrors its siblings `int_mod`→`march_checked_imod`, `int_div`→`march_checked_idiv`, `int_mod_euclid`→`march_checked_umod`: (1) new `march_checked_ediv(i64,i64)` in `runtime/march_runtime.c` implementing eval.ml byte-for-byte (`q=a/b; r=a-q*b; if r<0 then (b>0 ? q-1 : q+1) else q`), with the same `march_div_by_zero("int_div_euclid")` panic on a zero divisor; (2) the mapping added to **both** `llvm_emit.ml` call-path sites (the `EApp` guard/helper ~1600-1613 and the `ECallPtr` twin ~2090-2103, per the "builtin multi-site" gotcha); (3) the `declare`/`PDeclare` added to `lib/tir/llvm_builtins.ml`'s preamble (string table + `PDeclare` list). Named `march_checked_ediv` (Euclidean) rather than a "u"-prefixed sibling of `umod` because it is signed throughout — commented as such at the def. New parity test `test_compiled_int_div_euclid_parity` (`test/test_codegen.ml`, `iface_impl_mono_codegen` group) exercises all four sign quadrants (`[3, -4, 4, -3]`) via `assert_compiled_interp_parity`. Verified manually: interpreter and compiled both print `[3, -4, 4, -3]` and both panic `int_div_euclid: division by zero` on a `/0`.
