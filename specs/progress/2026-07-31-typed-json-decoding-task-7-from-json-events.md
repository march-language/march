✅ **Typed JSON decoding plan, Task 7 (final) — Phase B: `from_json_events` decodes straight from `JsonStream`'s `Event` list, no `JsonValue` tree (2026-07-31, `lib/desugar/desugar.ml`, `lib/typecheck/typecheck.ml`, `test/stdlib/test_json_typed.march`).** `derive Json for T` (record types) now also generates `from_json_events(events) : Result((T, List(Event)), Json.DecodeError)` alongside the existing tree-based `to_json`/`from_json`. Generated as: one `Option` slot per field, all `None`; a local recursive loop (`ELetFn`, scoped inside the one `from_json_events` body — NOT an extra top-level `pfn`, so two types deriving Json in the same module never collide on an internal helper name) that dispatches `EvKey(k)` to the matching slot, decodes that field's value off the following events, and recurses with the slot filled; `EvObjEnd` builds the record, erroring `"missing field"` (with a `JPathField` path, same as the tree decoder) for any slot still `None`; a nested derived-Json field recurses into ITS OWN `from_json_events`, threading the remaining-events tuple through on success and composing the path via `Json.decode_error_under` on failure — same mechanism Task 4 built for the tree decoder. **`from_json_events` needed NO special-casing in `eval.ml` or `typecheck.ml`:** the DImpl iface name `"JsonFromEvents"` starts with `"Json"`, so both files' existing `is_json_iface`/`is_json_derive` string-prefix checks (originally written for `to_json`/`from_json`) already treat it identically. The one REQUIRED addition: `typecheck.ml`'s base env needed a `("from_json_events", poly2 (fun a b -> TArrow (a, b)))` entry (mirroring the pre-existing `to_json`/`from_json` entries) — without it, `is_json_derive`'s "don't re-bind the polymorphic scheme" skip would leave the name completely unbound after the first derive processed. As a direct consequence, `from_json_events` inherits the SAME cross-type-shadowing caveat as bare `from_json`/`to_json` (last-declared type's derive owns the bare name in a multi-type module) — a known, already-documented issue, not a new one.

**Unknown-field subtree skipping uses EXPLICIT depth counting**, generated as a second local `ELetFn` (`skip(events, depth)`): `EvObjStart`/`EvArrStart` increment depth, `EvObjEnd`/`EvArrEnd` decrement, and skipping stops only when depth returns to 0 — this is the highest-risk piece in the whole plan, because counting only "the next event" instead would desynchronize the stream SILENTLY (the decoder then reads a nested value as a sibling — a wrong value, no error, not a crash). A duplicate key (whether of a known field already filled, or a genuinely unknown field) shares this exact same skip path — first-occurrence wins, matching the tree decoder's `Json.get_field`/`Json.parse` policy (recorded in the capability map), so the two decoders keep agreeing on duplicates. **One real bug caught and fixed before landing:** the first version of the per-field decode-and-recurse branch passed the newly-decoded field value BARE into the loop's next-iteration slot argument instead of wrapping it `Some(...)` — every decode of a fresh field crashed with "no branch matched" the moment the finish-chain's `Some`/`None` check ran against a raw value instead of an `Option`. Found via `--emit-core-ast` on a minimal one-field type, comparing the printed generated code against the intended shape.

**Differential oracle (written FIRST):** `test_json_typed.march` computes `render_tree`/`render_events` (each rendering `from_json`/`from_json_events`'s verdict as one comparable string, re-encoding a success value via `to_json` so VALUES are compared, not just verdicts) over a 7-document corpus (happy path, unknown field, reordered object, wrong type, missing field, non-object, duplicate key) via `agree_all`. All 7 agree.

**Dedicated depth-counting tests, independent of the oracle:** an unknown field whose value is a nested object, a nested array, an array of objects, and an empty object, each immediately followed by `Flat`'s four normal fields (`name`/`age`/`active`/`score`) — every test asserts the actual DECODED VALUE of all four following fields (not merely that decoding succeeded, which a silently-desynchronized skip could still produce by accident on some inputs). All four pass with every field correct. **Independently re-verified at final review**, which hand-traced the depth-counting logic itself (confirming depth returns to exactly 0, never negative, before the next sibling key) and additionally wrote its own 5-level mixed array/object nesting probe (not in the original suite) — passed on the first try, zero leftover events, correct field values throughout.

**Scope, by design:** `from_json_events` generation is TDRecord-only; `TDVariant`/`TDAlias` keep only the existing tree-based `to_json`/`from_json`, unchanged — extending the event path to variants was not asked for and not built. Number decoding assumes `JsonStream`'s default (non-`with_raw_numbers`) mode (`EvNum(Float)`); `EvNumRaw` is not handled by the generated decoder, matching what the oracle's corpus and `each_typed` both exercise. `each_typed` (Task 6) deliberately still calls the tree-based `from_json`, not `from_json_events` — no production caller of the event decoder exists yet; wiring it up is future work once a bounded-memory-per-huge-object driver is wanted.
