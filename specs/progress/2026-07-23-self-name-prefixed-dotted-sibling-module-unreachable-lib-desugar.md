- ✅ **Self-name-prefixed dotted sibling module unreachable (`lib/desugar/desugar.ml`, `lib/resolver/resolver.ml`, `lib/typecheck/typecheck.ml`, 2026-07-23).** A module could not reference a same-name-prefixed sibling dotted submodule in a multi-file (`MARCH_LIB_PATH`) project — exactly the layout `specs/lang/modules.md`'s "Multi-File Projects" section documents as standard: entry `mod MyApp do ... end` in one file, sibling `mod MyApp.Router do ... end` in another, `MyApp.Router.dispatch(1, 2)` called from `MyApp.main`. Failed with `Unknown module \`Router\`.`; the ONLY previously-working spelling was `alias MyApp.Router as R`. Referencing an unrelated-named sibling (`Other.Router`) always worked, isolating the trigger to the referencing module's own name being a PREFIX of the target's dotted name. **Root cause (three independent bugs, all on this exact path):** (1) `lib/desugar/desugar.ml`'s `strip_entry_self_qual` — which strips a self-qualifying `EntryMod.` prefix so `Foo.bar` inside `mod Foo` converges on TIR's unwrapped-entry bare emission — matched by STRING PREFIX ONLY: `MyApp.Router.dispatch` starts with `MyApp.` so it got mangled to `Router.dispatch`, which resolves to nothing (`Router` is a different top-level module, not a member of `MyApp`). Fixed by checking that the segment right after the stripped prefix actually names something the entry module itself declares (a direct fn/let, or a nested `DMod` — so genuine nesting like `Outer.Inner.wrapped` inside entry `mod Outer` still strips correctly) before stripping. (2) `lib/resolver/resolver.ml`'s `import_refs` took only the FIRST segment of a `use`/`alias` path as the module to load — correct for a submodule nested inside one file (`use Bastion.Channel` where `Channel` nests inside `bastion.march`) but wrong for the documented one-mod-per-file dotted convention (`use MyApp.Router` needs to load `my_app/router.march`, not `my_app.march`). Fixed by trying every dotted prefix of the path, longest (most specific) first, and loading whichever one maps to a real file. (3) `lib/typecheck/typecheck.ml`'s `DUse`/`Ast.UseSingle` case was a pure no-op for ANY dotted `use A.B` (pre-existing, not specific to the name-collision case — confirmed via an unrelated-name control `use Other.Router` + bare `Router.dispatch` failing identically pre-fix): a single-segment `use Foo` needs no bindings (`Foo.bar` already matches the qualified key directly), but a dotted `use A.B` never re-exported `A.B.bar` under the natural bare-last-segment form `B.bar`. Fixed by re-exporting under the last path segment, mirroring how `alias A.B as C` already re-exports under `C` (a same-segment no-op for single-segment paths, so existing behavior is preserved exactly). Verified: the reported repro now typechecks and runs (interpreted and compiled, prints `3`) via fully-qualified `MyApp.Router.dispatch(...)`, via `use MyApp.Router` + bare `Router.dispatch(...)`, and via the pre-existing `alias` workaround; the unrelated-name sibling case (regression control) still resolves correctly. New regression tests in `test/test_compiler.ml`'s module-system group. Full suite: no new failures.
