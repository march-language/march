- ✅ **Fix lib-module type errors silently swallowed when MARCH_LIB_PATH is relative (user_files canonical-vs-as-given mismatch)** — the resolver (since the LSP/CLI unification, commit 2545039) registers loaded files in `loaded_paths` under their **realpath-canonicalised** spelling, but parses them under the **as-given** path — diagnostic spans carry the as-given string, so with a relative `MARCH_LIB_PATH` (or a relative entry importing source-dir siblings) `is_user_file`'s `List.mem f user_files` failed for every lib-module diagnostic and the errors were tolerated as "stdlib-internal". Ill-typed programs then compiled into corrupt binaries or died at link time with undefined pattern-binder symbols (the depot repro: **70 swallowed type errors**, surfacing only as `use of undefined value '@$f27180'` from clang — an `Ok(v)` binder of an `ECase` whose Bool-typed scrutinee took the integer-switch path that never binds `br_vars`). The pre-existing `entry_imports_ill_typed` fixtures were live failures after the canonicalisation landed. Fix in `lib/resolver/resolver.ml`: `user_files` now records **both spellings** (`record_user_path` at the entry pre-mark, the explicit-import `load` path, and auto-discovery phase 2, which now threads the as-given path through from phase 1); `loaded_paths` stays canonical-only for dedup. Regression fixture: `test/imports/lib_path_ill_typed/` (relative `MARCH_LIB_PATH`, ill-typed lib module, entry never calls the broken fn — `--check` and `march test` must both exit 1).
