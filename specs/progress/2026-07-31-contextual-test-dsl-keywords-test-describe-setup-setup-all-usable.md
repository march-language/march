- ✅ **Contextual test-DSL keywords (`test`/`describe`/`setup`/`setup_all` usable as identifiers)** — These were hard lexer keywords, so `fn describe(...)`, a `setup` parameter, etc. were parse errors ("I got stuck here"). They are only ever keywords in a fixed position — `test`/`describe` immediately before a `STRING`, `setup`/`setup_all` before `DO` (March calls always use parens, so a `STRING` can never follow an identifier except in the DSL). Fix in `lib/parser/token_filter.ml`: a one-token-lookahead demoter wraps the base lexer inside `Token_filter.make` (covers every parse entry point), emitting `LOWER_IDENT` for these tokens unless they're in keyword position, with lexbuf position save/restore so spans stay correct. The test DSL is unchanged in its real position. (`assert` stays reserved — it's a genuine expression keyword.) +2 tests (idents + DSL-still-parses). Note: this unmasked a latent stdlib-collision in an LSP fixture (`type Color` vs stdlib `Color`) that had been vacuously passing because its `fn describe` never parsed — fixture renamed to `Hue`.
