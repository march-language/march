- ✅ **B5 — `EUpdate` on a type-erased record wrote past the allocation (llvm_emit.ml + runtime)** — when `get_record_fields` returns `[]` (record shape unknown at compile time — e.g. `record_from_list`/`record_put` results flowing through generic code), the old codegen still allocated a header-only cell (`emit_heap_alloc ctx 0 0`) and wrote every update at `field_index_for`'s `(0, TVar "_")` fallback offset, corrupting memory past the cell. Fixed with a new variadic runtime function `march_record_update_dyn` (`runtime/march_extras.c`, modeled on `march_record_field_dyn`): ONE call per update expression, one allocation, base fields copied, named fields overwritten, and a **runtime panic on any update name missing from the base shape** — the typechecker cannot validate names against an erased base (its TVar branch builds a partial record constraint from the update's own names), so `{ record_from_list([("a",1)]) with z: 99 }` typechecks; routing through `march_record_put` would have silently fabricated field `z`, and a per-field put-chain would have leaked N−1 intermediate cells (invisible to Perceus). Surface trigger confirmed reachable. 10 new checks in `test/imports/record_native/rn_entry.march` (compile-and-run fixture, now 28 checks) + 3 tests in `test/test_codegen.ml` (`erased_record_update_codegen`: IR asserts exactly one `march_record_update_dyn` call and zero chained `march_record_put` calls; compiled missing-field update panics with "no field" and exit 1; compiled 3-field update values match interpreter). Known divergence (documented): the interpreter's `ERecordUpdate` still silently appends missing update fields (eval.ml) — compiled fail-loud is the safer contract; aligning eval is a follow-up.
