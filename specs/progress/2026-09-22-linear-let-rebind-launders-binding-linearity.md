# A plain `let` rename no longer launders a binding-linear value

Filed and landed 2026-09-22. The named-binder twin of
[[2026-09-21-linear-wildcard-discard]].

## The hole

```march
fn rebind(linear h : Res) : Int do
  let h2 = h      -- accepted, no diagnostic
  0
end
```

`h` is linear only because of its BINDING (`linear h : Res`, a plain ADT; the
same holds for `linear p : a` and a `linear let x = 5` local): its type is plain,
and the linearity lives only in its `env.lin` entry. `ELet`'s auto-promotion
(`auto_lin` in the `ELet` arm of `infer_block`, `lib/typecheck/typecheck.ml`)
decided the new binder's linearity from the RHS **type** alone (`TLin`, or
`holds_linear`). So the read of `h` was recorded as `h`'s one use and `h2` was
bound Unrestricted: droppable (and, in principle, duplicable) with no error.
`drop_it(linear h : Res) = 0` and `let _ = h` were both already rejected; only
the named rebind got through.

## The fix

`rebound_binding_lin` (next to `discarded_linear_binding`, which does the same
expression-shape recognition for `let _ = e`) returns the `effective_lin` of the
tracked entry when the RHS IS a tracked binding (a variable, a linear field's
`r#f` sentinel, or either under an annotation). `auto_lin` falls back to it for a
single-variable pattern when the type says nothing, so `h2` is bound at `h`'s
linearity (Linear or Affine) and checked at the `let`'s scope close.

Session channels are excluded, the same exclusion the L8 `TLin` promotion
makes: a `Chan` endpoint (typed `TLin(_, TChan _)` or bare `TChan`) keeps its
own must-close accounting, and promoting a rebound endpoint to strict-linear
would regress the create-and-drop leniency.

Destructuring patterns are untouched: they already bind each component by its
own type (`inherits_linearity`).

already rejected before the fix (consuming `h2` through a `linear` parameter
tracks it), so it witnesses nothing.
