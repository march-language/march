- ✅ **`run_check_cmd` never stripped a stdlib module shadowed by a user file, silently corrupting unrelated typecheck state (`bin/main.ml`, `forge/test/test_build_check.ml`, 2026-07-06).** Found while trying to fully clean up a real dependency (`depot`) via the batched multi-file `march check`: two of depot's constructors (`PgTarget`/`SqliteTarget`) resolved fine when depot was checked alone, but became unresolvable — with no diagnostic pointing at the real cause — as soon as a large downstream consumer project's files were checked alongside it. Bisected (by halving the file set repeatedly) down to a single trigger file whose ONLY relevant property was declaring `mod Crypto do`, shadowing stdlib's own `Crypto` module by name. **Root cause:** the single-file `--check`/`--compile` path (`compile` in `bin/main.ml`) already strips a stdlib module from the combined declaration list when a project file shadows it by name (`extern_mod_names`, added specifically for this exact `mod Crypto do` scenario per its own doc comment) — but the multi-file `check` subcommand (`run_check_cmd`, batched onto by the `forge build`/`forge check` fix above) never had the equivalent guard, so two DMods both named `Crypto` ended up in the same combined module, corrupting unrelated global typecheck state badly enough to make a completely different file's own constructor unresolvable. **Fix:** `run_check_cmd` now filters `stdlib_decls` against the set of module names the checked files actually define (already computed by the dedup pass added in the fix above), mirroring `compile`'s existing `extern_mod_names` logic. New regression test `test_check_stdlib_shadow_does_not_corrupt_unrelated_module` in `forge/test/test_build_check.ml` — minimizing the real repro down to a 3-file case was itself informative: a same-file constructor build+match didn't reproduce it, only a shape where a separate file builds the value via a qualified call and a third file consumes it via a bare (unqualified) constructor pattern, exactly mirroring the real `depot_url.march`/`depot_db_repo.march` shape. Verified against the live repro: fixing this made BOTH `depot`'s `PgTarget`/`SqliteTarget` errors AND several of the downstream consumer's own unrelated errors (`ActionResult`/`ActionOk`/`ActionError`/`PathDep`, previously misattributed as real bugs in that project) disappear — they were all downstream victims of the same stdlib-shadowing corruption, not independent bugs.
