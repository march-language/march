- ✅ **`Parallel.preduce`/`preduce_n`/`psum_float` compiled with a Float accumulator: LLVM type mismatch (`'%cvN' defined with type 'i64' but expected 'double'`) — FIXED (2026-07-21, `lib/tir/llvm_emit.ml`).** Root cause: `task_await_unwrap`/`task_await`'s codegen had no `inner_ty = "double"` case for a `Task(Float)`'s inner type at all — it fell into the generic `else` fallback, mislabeling a raw i64-typed SSA value as `"double"` without converting it, so whatever downstream code consumed the mislabeled value hit an LLVM type error (the closure ABI's generic `"double"->"ptr"` coerce, `march_alloc_float`, is what surfaced it, at whichever call site happened to run next). `task_await`'s big comment block had already flagged `"double"` as "ABI-broken through the void*-returning trampoline, separate follow-up" when the sibling i64/ptr bugs were fixed — this closes that follow-up. **Fix:** both builtins gained a `"double"` branch. No runtime changes needed and no new box type: the float-boxing Stage-2 flip (see this file's "open-items master plan... Stage 2 atomic flip" entry) had already extended the closure apply-fn ABI to box a `Float` return value via `march_alloc_float` before handing it to the trampoline, so the pointer `task_spawn`'s thunk hands the trampoline is ALREADY a genuine heap address — the tag/untag round trip through `task[3]` was already lossless, exactly like the existing `"ptr"` case; `task_await_unwrap`/`task_await`'s `"double"` branch just needed to recover that pointer the same way the `"ptr"` case does and then unbox it with the paired `march_unbox_float`. (An earlier version of this fix, written before the float-boxing Stage-2 work was rebased in, invented its own dedicated `march_task_spawn_thunk_float`/`march_float_task_box` boxing mechanism — dropped once rebasing revealed it duplicated the now-canonical infrastructure.) Verified: the exact reported repro (`Parallel.psum_float(RRB.from_list([1.5, 2.5, 3.0]))`) compiles cleanly; a raw `task_spawn`/`task_await_unwrap` round trip over `2.75`/`100000000.25` (values that would trip the PRE-float-boxing lossy bit-shift this bug was originally diagnosed against) prints and sums correctly. `RRB.push`/`Array.push` on `Float` elements — which crashed compiled on the second push while this fix was originally being developed, and looked like a second, separate bug — turned out to *also* already be fixed by the same float-boxing Stage-2 work once rebased onto it. **`Parallel.psum_float`'s actual practical repro and `docs/cookbook/parallel-data.md`'s example are STILL BROKEN compiled, but not by this bug:** verifying end-to-end surfaced a third, more severe, pre-existing bug (also independent of this fix, also reproduces on unmodified `origin/main`) in `RRB.fold`'s own TCO'd loop — see this section's new P0 entry ("A tail-recursive function with a `Float` accumulator that also carries a heap-pointer parameter...").
