- ✅ **`@[vectorize]` / `@[vectorize(warn)]` function attribute — the compiler's previously-silent `NativeArray.map_int`/`map_float`/`map2_int`/`map2_float` auto-vectorization eligibility heuristics are now a checked compile-time contract (2026-07-31, `lib/parser/parser.mly`, `lib/tir/vectorize_mark.ml` + `vectorize_check.ml` new, `bin/main.ml`).** `@[vectorize]` on a function is a hard compile error (exit 1) if the optimizer's own inliner (`lib/tir/native_map_inline.ml`) would not actually vectorize its `NativeArray.map`/`map2` calls; `@[vectorize(warn)]` reports the same violation as a warning and lets the build continue. Two real gates, checked by reusing `native_map_inline.ml`'s own matching helpers so the diagnostic can never disagree with what the optimizer does: the **reuse gate** (Int and Float — the callback closure must be used exactly once, passed directly as the map/map2 call's closure argument; `"<fn> cannot vectorize — this callback isn't safe to inline"`) and the **generic-signature gate** (Float targets only — the callback's resolved signature must be concretely `Float`, not a leftover `TVar`, since that's what unlocks the zero-boxing unboxed clone; `"<fn> cannot vectorize — callback type is still generic"`). A third **misuse** category is always a hard error even under `(warn)`: the attribute on a function with zero `NativeArray.map`/`map2` calls, to catch a typo'd/misapplied annotation. Worth recording: the informal prose in `docs/simd-vectorization.md`/`stdlib/native_array.march` describes the bar as "non-capturing or single-capture," but the actual implementation gates on reuse and (Float-only) concrete typing — capture count is not a gate, since `native_map_inline.ml`'s Phase 2 (0 captures) and Phase 2c (1+ captures) both get inlined; the checker follows the code, not the prose, hence two gates rather than three. **Pipeline shape:** `lib/parser/parser.mly` gained an `fn_attr` alternative for the `@[name(value)]` bracket-with-argument form (the grammar previously had `@[name]` and bare `@name(value)` but not the combination), encoded as `"vectorize:warn"` following `@compat(full)`'s convention. `lib/tir/vectorize_mark.ml` (new) runs immediately after `Lower.lower_module`, before `Mono` — the one pipeline point where a TIR function's name is still exactly its source name — and injects a compiler-internal sentinel call (`__vectorize_marker_hard`/`__vectorize_marker_soft`) at the head of each annotated function's body, carrying the source name and declaration span as literal arguments. `lib/tir/vectorize_check.ml` (new) runs late, immediately before `Native_map_inline.run` (so it sees the same pre-rewrite TIR shape the optimizer peephole consumes), scans for sentinels, runs the gates, and strips every sentinel back out. Both insertion points in `bin/main.ml` are gated on `not is_js_target`. **Design lesson — why a sentinel, not name matching:** the first implementation matched AST attributes to TIR functions by name at the late check point, stripping everything after a TIR name's first `$` on the assumption `$` only marks a monomorphization suffix. Review found that unsound two ways, both confirmed empirically: Defun independently produces `<fn>$apply$<uid>` for every lifted lambda, so a stdlib local `fn scale` becomes `scale$apply$1803` and a user's own `@[vectorize] fn scale` would fire a spurious hard error against it; and the check runs after Opt, where a small annotated wrapper can get inlined into its caller and no longer exist as its own `fn_def` — silently missing the exact reuse-gate violation the feature exists to catch (confirmed via a post-Opt TIR dump showing `fn scale` entirely absent). The sentinel survives both mangling and inlining because Mono's record-update duplication and Opt's inliner preserve body contents wherever they land — which also fixed, for free, that diagnostics now name the user-written source name (not `scale$Float`) and that `@[vectorize]` inside a nested `mod` no longer silently no-ops (the mark pass qualifies names the same way `Lower` does). **Known limitation:** if two separately-annotated functions both get inlined into the same caller, their sentinels merge and can't be attributed call-by-call; `combine_markers` widens (joins the names, takes Hard if any is Hard) rather than silently mis-attributing. **Verified** via `scripts/run-tests.sh -q`: `run_compiler` 619 (+1 parser test), `run_eval` 256 (unchanged), `run_codegen` 535 (was 520, +15 — the new `vectorize_check` group: eligible Float/Int/map2, `(warn)`-silent-on-eligible, reuse-gate hard fail plus under `(warn)` plus on map2 plus caught-after-inlining, generic-signature pass/hard-fail/`(warn)`, misuse hard-fail plus still-hard-under-`(warn)`, a module-loads smoke test, and an end-to-end CLI test driving the real `march --compile` binary), `run_stdlib` 780 (unchanged), all suites exit 0. **Out of scope:** fixed-width SIMD vector types (`f32x4`, `f32x8`, `i32x4`, `i32x8`) were part of the original feature request but remain a separate later increment — they don't depend on this attribute; tracked as an open TODO below.
