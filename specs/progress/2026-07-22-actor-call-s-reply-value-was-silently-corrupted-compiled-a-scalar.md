- ✅ **`Actor.call`'s reply value was silently corrupted compiled — a scalar reply came back as its raw tagged bit pattern, not the real value (`lib/tir/llvm_emit.ml`, 2026-07-22).** Found auditing `specs/lang/actors.md`'s "Synchronous request/response" section against its own pinned golden: `test/native/actor_counter.march` compiled printed `value=11` where both the interpreter and the golden (`test/native/actor_counter.expected`) say `value=5` — `11 = (5<<1)|1`, the standard tagged-immediate encoding of `5`, read back raw. **Root cause:** `Actor.call`'s `Result('a, String)` return type is deliberately left as an unresolved type variable in TIR — the reply's payload type genuinely can't be known statically (any handler can reply with anything), so pattern-matching `Ok(v)` correctly extracts the field generically as `ptr`, and `march_actor_reply`'s call site (already special-cased in `llvm_emit.ml`) correctly tags a scalar reply into that uniform `ptr` representation before it crosses the mailbox's `void*` boundary. The bug was one step further downstream: the general `EApp` call-emission path only coerces an argument to its callee's declared LLVM parameter type for *user-defined* functions (via `ctx.top_fn_param_tys`) — every other scalar-consuming builtin (`int_not`, the bitwise ops, …) works around this with its own dedicated match arm that calls `emit_atom_as` explicitly, but `int_to_string`/`bool_to_string`/`float_to_string` had none. So the `ptr`-typed extracted value flowed straight into `call ptr @march_int_to_string(ptr %v)` against a `declare ... (i64 %n)` signature — a declared-type mismatch LLVM's parser doesn't reject and that "works" at the ABI level (`ptr`/`i64` share a register), silently handing the C function the raw tagged bits instead of the untagged integer. Confirmed via `--emit-llvm` on the failing golden (showing the exact mismatched call) and by checking that `int_to_string`'s normal (non-erased, concretely-typed) call sites were unaffected (their argument is already natively `i64`, so the missing coercion is a no-op there). **Fix:** added dedicated `EApp` match arms for `int_to_string`/`bool_to_string`/`float_to_string`, each calling `emit_atom_as ctx "i64"/"double"` before the C call — mirroring the existing `int_not`/bitwise-op pattern exactly. Scoped to these three builtins (the only scalar-consuming ones with no existing dedicated arm); the general per-builtin argument-coercion gap this exposes is broader but out of scope for this fix. Verified: `test/native/actor_counter.march` compiled now matches `.expected` (`value=5`); the other wired `Actor.call` golden, `test/native/actor_call_timeout.march`, is unaffected (still matches `timeout_ok`); normal `int_to_string`/`bool_to_string`/`float_to_string` calls smoke-tested unchanged. Full suite green: compiler 527 / eval 238 / codegen 438 (including the LLVM IR validity gate over the full native corpus) / stdlib clean.
