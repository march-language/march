- ✅ **`check_post`'s path conditions resolve in the BODY's namespace, not through the return binder (`lib/refinecheck/refine_check.ml`, 2026-07-24).** `check_post` translated the path conditions with the same `resolve_var` as the return predicate, in which the binder denotes the RETURN value. A path condition comes from the function BODY, so every name in it is a body name; when a parameter shared the binder's spelling the fact was re-pointed at the returned expression — the same caller/callee conflation already fixed for `check_call`'s path conditions. Live repro, confirmed against the built compiler BEFORE the fix: `fn f(v : Int, k : Int) : {v : Int | v > 0} do if v < 0 do k else 1 end end` reported "does not satisfy its return type constraint" with counterexample `k = -1` — the guard `v < 0` is about the PARAMETER, misread as `k < 0`, which makes `v > 0` (i.e. `k > 0`) definitely false. The same conflation ALSO suppressed genuine violations: with the tail `0` instead of `k`, `v < 0` became `0 < 0`, a contradictory assumption under which the goal discharges vacuously — that shape is a second new test and it was silent before the fix. Path conditions now go through a `path_resolve_var`/`path_resolve_field` pair that resolves through the enclosing scope (`var_const` / `scope_field_resolver`); `_` is left pointing at the return term, since it is not a legal variable in body code and would otherwise declare a constant named `_`. Four tests in `post_suite`: the false positive, the suppressed-violation control, a control that a non-colliding named binder still denotes the return value in the PREDICATE, and one that a guard on the colliding parameter still discharges when the tail IS that parameter.
