- ✅ **Multi-arm `with ... else` failed to parse entirely (`lib/parser/token_filter.ml`, `test/test_compiler.ml`, 2026-07-06).** Any monadic `with pat <- e do body else ... end` with **two or more** else-arms was a hard parse error — the caret landed on the second arm's `->` — no matter the arm shape (nullary ctors, payload ctors, infix-operator bodies); a single else-arm always worked. This made the entire multi-arm error-handling form documented in `docs/pattern-matching.md`'s "With (Monadic Pattern Matching)" section (including its 3-arm `Err(AuthFailed)`/`Err(NotFound(kind))`/`Err(Timeout)` example) unwriteable. **Root cause:** the grammar parses else-arms with `separated_nonempty_list(arm_sep, branch)` — the same rule as `match` branches, needing NL/PIPE arm separators — but `token_filter.ml` only emitted arm-separator newlines inside a `Match` context. A monadic `with`'s `do` pushed a plain `Block`, so the newlines between else-arms were swallowed as insignificant whitespace (a single arm needs no separator, hence only multi-arm broke). **Fix:** a new `With` context variant marks the with-block — recorded when a `do` follows a `<-` (`GETS`, unique to with-bindings; multiple bindings of one `with` dedup to one pending entry keyed by paren-depth, mirroring `pending_match_depths`) — and at the `else` keyword the `With` context is promoted to `Match`, so the arms are newline-separated exactly like a `match` body; the single `end` pops it. Composes cleanly with the same-day cond-form/when-guard token-filter change (the promoted arms are ordinary pattern arms → `ms_is_cond = false`; verified `match do` boolean-operator arms still parse). The with-body itself stays block-style. `if ... else`, record-update `{ e with ... }` (uses `WITH` but no `GETS`), and `else if` chains are untouched (their `do` pushes `Block`, not `With`, so the `else` handler is a no-op for them). **Known pre-existing limitation (verified identical on base via file-copy revert — NOT a regression; mirrors the `match`-scrutinee case):** a *bare* unparenthesized `do`-block expression (`if`/`with`) as a with-binding RHS steals the pending marker — parenthesize the RHS (a bare `match` RHS works, since `match` has its own pending mechanism). 4 new parser regression tests in `test/test_compiler.ml` (single-arm guard, two nullary-ctor arms, three payload/nested-payload arms, infix-operator arm bodies). **Verification (six runners):** 420 compiler (+4) / 231 eval / 391 codegen / 804 stdlib (full, with Slow) / 29 snapshots exit 0; `test_stdlib_march`'s `global_registry` group (18/18) fails **pre-existing on clean main** (unbound `GlobalRegistry.*`, a module-resolution issue unrelated to this parser-only change — that module has zero `<-` tokens; confirmed by reverting the change and re-running). The `docs/pattern-matching.md` 3-arm example now compiles and runs.
