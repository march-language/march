- ✅ **`Cli` stdlib module — Task 2: `Cli.parse` flag/value/positional parsing loop + basic accessors (`stdlib/cli.march`, `test/stdlib/test_cli.march`, 2026-07-05).** Second task of the argument-parsing `Cli` module plan (follows Task 1's types/constructors). New in `stdlib/cli.march`: `Cli.parse(specs, argv) : Result(ParsedArgs, CliError)` — a single left-to-right recursive `parse_loop` that classifies each token via `flag_name` (strips a leading `--`/`-`; `None` means positional), resolves it against `specs` by long or short name (`resolve_spec`/`find_by_long`/`find_by_short`), consumes a following value for `ValueFlag` specs (`Err(MissingValue(long))` if none), records `"true"` for `BoolFlag` specs, accumulates unmatched tokens as positionals, and at end-of-input checks every `required: true` spec got a value (`Err(MissingRequired(long))` via `find_missing_required`) before returning `Ok({values, positional})` (both accumulators reversed once, not consed in output order). Plus 4 accessors: `Cli.get_string`, `Cli.get_string_or`, `Cli.get_bool` (absent → `false`), `Cli.positional`. 9 new tests in `test/stdlib/test_cli.march` under a `describe "Cli.parse"` block (long/short/bool flags, default fallback, unknown flag, missing value, missing required), all green. **Three deviations from the brief, all required for the code to actually parse/run:** (1) the brief's `sample_specs()` test helper was written nested inside the `describe` block — March's grammar does not allow `fn`/`pfn` declarations inside a `describe do...end` body (confirmed against `test/stdlib/test_array.march`'s `pfn make_vec`/`test/stdlib/test_http.march`'s `pfn make_test_req` pattern) — hoisted to a module-level `pfn sample_specs()` before the `describe` blocks instead. (2) the brief's `flag_name` used a 2-branch `if/else if/else` chain closed with a single `end` — March requires one `end` per `if` in an `else if` chain (each `else` branch is a `block_body` that can itself contain a full nested `if...end`, so an N-`if` chain needs N `end`s; confirmed against `stdlib/base64.march`'s existing 3-way `else if` chain) — added the second `end`. (3) the brief's `find_missing_required` and `get_string` used `pair.0`/`pair.1` tuple-index field access on a `(String, String)` tuple — March's grammar has no numeric tuple-index production at all (`lib/parser/parser.mly`'s `expr_field` only accepts `DOT lower_name`/`upper_name`; no `DOT INT`), so `pair.0` fails to parse in any context, not just this one — rewrote both as `match pair do (name, value) -> ... end` pattern destructuring instead (the established March idiom per `stdlib/array.march`/`stdlib/bigint.march`'s existing `let (a, b) = tuple` usage). **All three are language-level constraints, not implementation choices** — the parsing/accessor *logic* itself (loop structure, error cases, accumulator order) matches the brief exactly. **Doctest note (pre-existing, not a regression):** `Cli.parse`'s own one-line doctest passes; but the 6 doctests using the brief's two-line `let parsed = Cli.parse(...)` / `match parsed do ... end` pattern (`Cli.get_string`, `Cli.get_string_or`, `Cli.get_bool`, `Cli.positional`, plus Task 1's carried-over `Cli.flag`/`Cli.value_flag`/`Cli.flag_with`) fail with "doctest parse error" — confirmed identical to the pre-existing `RRB.fold`/`RRB.chunk` doctest failures on a clean checkout of Task 1's commit (`f16cecf2`, via an isolated `git worktree add`), i.e. the doctest runner's single-expression `expr_eof` parser cannot handle a bare `let` as one `march>` line, regardless of module. Not introduced by Task 2, out of scope to fix here. **Verification gotcha:** `dune exec march -- test ...` intermittently ran a stale/wrong `main.exe` in this session (typecheck passed but eval reported "unbound variable: Cli.flag"/"Cli.parse" for functions that demonstrably exist and work when invoked directly) — switched to `./_build/default/bin/main.exe test ...` (the direct-binary invocation this repo's `CLAUDE.md` already recommends for reliability) and all 9 tests passed cleanly; root cause not pinned down further since the direct-binary path is the documented correct invocation anyway.
