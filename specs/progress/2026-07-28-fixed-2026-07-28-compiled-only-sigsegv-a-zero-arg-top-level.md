- ✅ **FIXED (2026-07-28): compiled-only SIGSEGV — a zero-arg top-level function materialized as a first-class value, then invoked through that value.** Minimal repro:
  ```march
  mod Main do
    fn answer() : Int do 42 end
    fn main() : () do
      let zf = answer
      println(int_to_string(zf()))
    end
  end
  ```
  Compiled `--opt 2`: exit 139 (SIGSEGV), no output (reproduced 2026-07-28). Interpreted: prints `42`, exit 0. Calling `answer()` directly (no `let` alias) works fine both compiled and interpreted — the crash is specific to materializing a *0-arity* named function as a value and then calling through the value; multi-arg named functions used the same way (`let af = add; af(7, 8)`) are unaffected. **Bisected to predate the static-closure work**: reproduces identically at `fbea848b` (the parent commit of the static-closure change) and at current HEAD, and independently corroborated by a diff read of the static-closure commit, which only touches the `Tir.TFn _` arm of the function-value materialization path in `lib/tir/llvm_emit.ml` and leaves the zero-arg fallback arm (the `| _ ->` "0-arg function / module-level constant" branch that calls the function to obtain its value) byte-identical. This is why `test/native/static_closure_semantics.march` (the Task 3 parity fixture) deliberately omits a zero-arg function-value case — including it would crash the build. Full bisection detail in `.superpowers/sdd/2026-07-28-static-capture-free-closures/task-3-report.md`.

  **Root cause:** typechecker gap, not codegen — codegen agrees with (and faithfully compiles) the typechecker's answer. March's zero-param T-Abs convention collapses a `fn`'s type to its bare return type (no `TArrow` wrapper), so `answer` referenced bare is genuinely typed `Int`; `--dump-tir` confirms `let zf : Int = answer`. `zf()` — calling a plain non-arrow-typed value — was then silently accepted by `infer_app`'s `| [], t -> t` base case (needed so a genuine zero-arg `fn()` call still works), which can't distinguish "callee is a disguised zero-arg fn" from "callee is a plain value" once no args remain to unify against. The exact same hole independently allowed `let x = 5; x()` to pass `--check` and crash — see `root_cap()`'s scope note (above, 2026-07-22) which first identified and deliberately left this open pending a safe general fix.

  **Fix (`lib/typecheck/typecheck.ml`):** generalized the `root_cap()`-only `noncallable_error` check in `Ast.EApp`'s handler to a positively-scoped signal rather than trying to negatively infer "not a known function" (which was the blocker noted in the `root_cap` scope note). New env field `plain_let_names : StringSet.t`, populated at exactly ONE site — the `Ast.ELet` case of `infer_block`, when the pattern is a simple `Ast.PatVar` and the binding is non-linear — marking that the name currently refers to a plain `let`-introduced value. `EApp`'s handler now rejects a zero-arg call `f()` when `f` is `EVar name` with `name ∈ env.plain_let_names` and its resolved type is a *concrete* non-arrow (excluding `TVar`/`TError`). `bind_var`/`bind_linear` clear the marker on any rebinding of the same name (mirrors `fn_arities`'s existing shadow discipline). Two exclusions were required to avoid false positives, both caught by the full suite before landing:
  - **`fn_arities`-absence was tried first and rejected as unsafe**: it's cleared by `bind_var` on ANY same-name rebinding (deliberate, for its own arity-check purpose), but a bulk `import Mod` rebinds every imported name via `bind_var` too — at multi-file scale (`test_large_multi_file_check_is_not_quadratic`, 2500 files importing one shared module), one importing module's `import Shared` wiped the global `fn_arities` entry for `helperN`, and EVERY later module's plain `helperN()` call misfired. `plain_let_names` is immune since it's only ever added to, never used as a negative/absence signal.
  - **A local zero-arg LAMBDA LITERAL bound via `let`** (`let g = fn -> body; g()` — real, tested behavior, `test/native/unit_callback_zero_arg.march`) collapses to its body's type under plain inference for the identical structural reason a top-level zero-arg `fn` does (`ELam`'s inference arm folds `TArrow` over zero params = no-op). Excluded by never marking `plain_let_names` when the `let`'s RHS is itself `Ast.ELam _` — a lambda literal is never a "disguised alias", so the AST shape (not the collapsed type) is the safe discriminator.
  - Local named functions (`fn helper() do ... end`, i.e. `Ast.ELetFn`) collapse to their return type the same way top-level `fn`s do; these are exempted by extending `env.fn_arities` registration (previously top-level-`fn`-only) to also cover `ELetFn` bindings, so `arity_error`'s existing direct-call machinery (unrelated to the new check, which only fires for `plain_let_names` members) keeps working for them, and aliasing one through a plain `let` (`let g = helper; g()`) is correctly still rejected.
  - Qualified cross-module calls (`Dep.bar()`) and bare cross-module builtin calls (`pmap_threshold()`, `self()`, etc.) are unaffected because they never flow through `Ast.ELet`, so they're never in `plain_let_names` to begin with — no denylist/allowlist needed for them at all (simpler than the `root_cap`-era design anticipated).
