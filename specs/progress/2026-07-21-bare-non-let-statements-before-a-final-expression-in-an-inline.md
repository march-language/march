- ✅ **Bare (non-`let`) statements before a final expression in an inline-lambda call argument (2026-07-21).** Found auditing `docs/cookbook/dom.md`/`concurrency.md` — two independent subagents each hit the same parser bug and worked around it (wrapping the bare statement as `let _ = ...`) rather than filing it. Root cause: `lambda_body` (`fn params -> ...`) only accepted `LET`/`linear let`/`let?` bindings before the final expression (unlike `block_body`, which accepts any bare expression statement via `block_expr`'s `e = expr` fallback) — so `fn x -> let a = 1  println("hi")  if a > 0 do 1 else 2 end` swallowed `println(...)` as the lambda's whole body and left `if ... end` as unparsed trailing tokens ("I got stuck here" at `if`). A naive fix (make `lambda_body` a general `nonempty_list` of `let`-or-bare-expr statements, mirroring `block_body`) is UNSAFE: unlike `block_body` (always bounded by a matching `END`), a bare arrow-form lambda body has no closing delimiter, so when the lambda appears anywhere the enclosing statement sequence is *also* still open (e.g. `let f = fn n -> n` as one statement of a bigger `do...end` block), the parser cannot tell where the lambda's body ends and the enclosing sequence resumes — it silently swallows subsequent statements into the lambda (confirmed regression: `let f : (Int)->Int = fn n -> n` followed by more code became mis-typed, caught by the pre-existing `test_let_annot_poly_instance_accepts`). Fixed by scoping the relaxation to call-argument position only, where the argument is always unambiguously bounded by `,`/`)`: new `call_arg` / `call_arg_lambda_body` / `call_arg_lambda_stmt` nonterminals used only in `expr_app`'s two call-argument-list productions (function calls and `Con(...)` constructor calls), with a companion `expr_no_bare_lambda` (a copy of `expr` minus its own top-level bare-lambda alternatives) as `call_arg`'s fallback so there's exactly one way to parse a bare lambda argument — avoiding ambiguity with `expr`'s own (unchanged, still LET*-then-final-expr) lambda-body rule used everywhere else. Zero new parser conflicts beyond the grammar's pre-existing 7 states / 59 shift-reduce (one of the same pre-existing kind — a match/if-scrutinee-vs-`WITH` ambiguity — now also reachable through constructor-call args). 2 new parse tests in `test/test_compiler.ml` (`test_parse_lambda_bare_stmt_before_if`, `test_parse_lambda_consecutive_bare_stmts`); full suite green (453 compiler / 231 eval / 396 codegen / snapshots unaffected).
