- ✅ **REPL JIT parity — 5 remaining test failures resolved** — Three root-cause bugs fixed: (1) `ptr 0` in LLVM string equality call (`march_string_eq`) — occurs when one operand is an i64 literal (e.g. bool false as `"0"`); fix: coerce both operands to `ptr` via `coerce ctx` before formatting the call instruction in `llvm_emit.ml`. (2) `%List.length.addr` undefined — polymorphic REPL globals (free vars with `TVar "_"` type) caused `build_subst` in `mono.ml` to return `[]` for `EApp` calls, silently skipping worklist addition; the function was never emitted, defun converted it to `ECallPtr`, and LLVM emitted an invalid alloca load; fix: in the `EApp` branch of `rewrite_calls`, when `subst = []` add to worklist (matching the existing `ECallPtr` behavior). (3) Bool `v` displayed as `"1"` — when evaluating a REPL global with `TVar "_"` return type, the `Int64.to_string` path was used instead of the bool formatter; fix: added `global_tir_tys : (string, Tir.ty) Hashtbl.t` to `repl_jit` context, populated on each global store, and used in the `TVar _` display branch to look up the actual TIR type via body inspection. Also added `string_length` to `is_builtin_fn`, `mangle_extern` (→ `march_string_byte_length`), and `builtin_ret_ty` in `llvm_emit.ml` — it was registered in typecheck and defun but missing from LLVM emit, causing `@string_length` undefined errors.
