✅ **Typed JSON decoding plan, Task 3 — `Json.DecodeError` with a JSONPath and an optional byte offset (2026-07-31, `stdlib/json.march`, `test/stdlib/test_json_typed.march`).** Stdlib-only, no compiler changes. Defined `Json.JsonPathStep = JPathField(String) | JPathIndex(Int)` (one step of a path, outermost-first) and `Json.DecodeError(String, List(JsonPathStep), Int)` (message, path, absolute byte offset or `0 - 1` if unknown). `Json.decode_error_under(step, e)` prepends a step (used as a decoder recurses into a field/element); `Json.decode_error_at(off, e)` sets the offset; `Json.decode_error_to_string(e)` renders JSONPath-style — `"$.users[3].id: expected Int"`, or `"$.id (byte 4096): expected Int"` when an offset is known. **Fix round 1:** the first version's `render_path`/`decode_error_to_string` called bare `to_string(i)`/`to_string(off)` on plain `Int`s, which resolved (same-module shadowing) to `stdlib/json.march`'s own `JsonValue`-only `to_string(jv)` instead of `int_to_string` — 2 of 5 new tests failed with "no branch matched" (on `JPathIndex` paths and non-negative offsets specifically, since those are the only two new tests calling `to_string` on an `Int`). Root-caused independently by review (the implementer's own diagnosis of "a March interpreter limitation" was checked and found wrong) and fixed with two `int_to_string` substitutions. `test_json_typed` 149 → 154 assertions, all green (interpreted).
