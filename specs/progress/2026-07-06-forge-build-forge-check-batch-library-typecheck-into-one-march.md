- ✅ **`forge build`/`forge check` batch library typecheck into one `march check` subprocess instead of one-per-file (`bin/main.ml`, `forge/lib/cmd_build.ml`, `forge/lib/cmd_check.ml`, `forge/test/test_build_check.ml`, 2026-07-06).** Second half of the compile/typecheck-speed opportunity sweep. `Cmd_build.check_all` previously invoked `march --check <file>` as a separate subprocess per `.march` file in a library project, each independently re-parsing and re-typechecking the whole ~108-module stdlib plus any shared imports (e.g. a `common.march` imported by two sibling files got parsed/typechecked twice). Batched onto the compiler's existing combined-module `march check f1 f2 ...` subcommand instead — one process, one stdlib load, one typecheck across all files. Two wrinkles handled: (1) that subcommand (`run_check_cmd`) silently dropped warning diagnostics (only printed errors) — fixed to print both, in the same `file:line:col: <severity>: msg` format `count_diagnostics` already parses; (2) the single-file `--check` path had a compiler-side CAS cache making a repeated no-op rebuild near-instant, which the batched subcommand lacks — added a small forge-local cache (`.forge/check-cache/<hash-of-sorted-file-contents+lib_path_env>.clean` marker files) so an unchanged repeat `forge build`/`forge check` short-circuits before invoking `march` at all, rather than regressing relative to the old per-file behavior. Known limitation (documented in code): the cache key does not hash the *contents* of `MARCH_LIB_PATH` directories, only the env-var string, so editing a local `path = "../foo"` dependency in place without touching forge.toml/forge.lock won't invalidate it. 2 new Alcotest cases in `forge/test/test_build_check.ml` (warning surfacing from the combined module; cache-marker existence + mtime-unchanged-on-repeat-check).
