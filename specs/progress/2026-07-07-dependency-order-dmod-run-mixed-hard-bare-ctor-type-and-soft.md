- ✅ **`dependency_order_dmod_run` mixed hard (bare ctor/type) and soft (qualified-reference) dependency edges into one DFS, letting a soft-edge reference cycle silently reorder a hard edge — FIXED (`lib/typecheck/typecheck.ml`, `forge/test/test_build_check.ml`, 2026-07-07).** Found checking a real downstream project (`conduit`) whole-program: `Conduit` qualified-delegates to `Conduit.API`, which qualified-calls `Conduit.Worker`, which bare-pattern-matches `WorkerError` — a constructor `Conduit` itself declares. `march check` reported `` I don't know a constructor called `WorkerError` `` despite the declaration being correct. **Root cause:** `dependency_order_dmod_run` topologically orders sibling DMods over the UNION of `module_refs_in_decls` (qualified `Mod.fn`/`Mod.Ctor` references) and `unqualified_module_deps` (bare ctor/type references) — but the two are not equally load-bearing. Qualified references are pre-bound as pass-1 Mono placeholders regardless of check order (`prebind_mod_members`), so ordering by them is a precision nicety only (the rationale `0799c745` introduced this edge kind for — avoiding a caller pinning an under-generalized placeholder). Bare references have no such placeholder — the name is only visible once the defining sibling's DMod is actually processed by `check_decl` — so ordering by them is a hard correctness requirement. Real modules commonly form legitimate reference cycles through qualified calls alone (a facade delegating to an internal module that calls back into a module the facade depends on) — previously harmless, since qualified refs tolerate any order. Mixing both edge kinds into one DFS meant a soft-edge cycle could non-deterministically reorder a hard edge: whichever edge type the traversal reached an already-in-progress ancestor through "won", independent of which one actually mattered. **Fix:** compute the existing combined-edge DFS order unchanged (zero behavior change for the common case — every existing regression fixture, including the `0799c745` "dotted sibling module order" precision test, still passes byte-identically), then validate it against the hard edges alone; only when a hard edge is actually violated does it fall back to Kahn's algorithm restricted to hard edges, using the original order purely as a tie-break. New regression test `test_check_qualified_cycle_does_not_break_bare_ctor_ordering` in `forge/test/test_build_check.ml`, minimized to the same three-module facade/worker/core shape (file naming is itself load-bearing there — `Cmd_build.find_march_files` walks sorted-ascending but prepends, so the actual file list handed to `march check` is sorted DESCENDING; the hard dependency's definer has to be discovered first through the real `forge check` path for the bug to reproduce, hence `zcore.march`). Verified against the live repro: `conduit`'s `WorkerError` error is gone; standard runners unaffected (424 compiler / 231 eval / 391 codegen, all exit 0; `forge/test/test_build_check.exe` 12/12).
