# `[P2]` Compiler: Capabilities/effects (found during Core March widening slice 5)

- [ ] **F1 — body-scanned IO caps are WARNING-only, not error; "absence of `needs` = machine-verified purity" holds only when authors thread `Cap(X)` through signatures.** Found and pinned by `specs/lang/core-march-types.md` §2.8.6 (capabilities widening, Task 2, 2026-07-07). Check 1b (`typecheck.ml:5588-5605`, `Err.warning_with_fix` at `:5596`) — a function BODY calling a `builtin_cap_table` builtin (`file_read`, `tls_connect`, `vault_set`, …) without a covering `needs` — is WARNING-only, not an error: `--check` exits 0. Contrast Check 1 (signature `Cap(X)`), Check 4 (transitive `use`), and Check 5 (extern `Cap(X)`), which are all true ERRORs, exit 1. So a module that calls IO builtins directly in a function body, never threading `Cap(X)` through any signature, is *warned*, not *rejected* — the guarantee "no `needs` declared ⇒ the function is pure" only holds at the ERROR-level signature/transitive/extern-cap surface, not at the body-call surface. `specs/lang/capabilities.md` overclaims this: `:69` ("The compiler enforces this transitively... the build fails"), and the prose framing around `:142`/`:312` ("There are no false positives"; "the type checker already enforces `needs` as an error") describes the body-call case as effectively error-level when it is warning-level in the actual implementation (the example text in those sections does correctly say "Warning"/"hint", but the surrounding claims overstate the guarantee). Verified live, both sides reproduced side by side: a `Cap(IO.FileRead)` signature with no `needs` rejects (`` `Cap(IO.FileRead)` used in module `Reader` but `IO.FileRead` is not declared in `needs`. ``, exit 1); a body call to `file_read` with no `needs` only emits a HINT + WARNING (`` function body calls a builtin that requires `Cap(IO.FileRead)` but `Reader` does not declare `needs IO.FileRead`. ``, exit 0). This is a design/enforcement gap, not a mechanical bug — Checks 1/4/5 themselves are sound and precise over the `builtin_cap_table` domain. Filed here (not fixed — docs-only widening slice); reconciling `capabilities.md`'s wording against this reality is deferred to Task 7 of the widening plan. See `specs/lang/core-march-types.md` §2.8.6 for the full three-tier table and both live transcripts.
