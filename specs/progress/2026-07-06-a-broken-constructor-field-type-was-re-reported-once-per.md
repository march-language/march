- ✅ **A broken constructor field type was re-reported once per instantiation instead of once (`lib/errors/errors.ml`, `test/test_compiler.ml`, 2026-07-06).** Found while triaging the diagnostic output from the `run_check_cmd` fix above on the real ~85-file bastion project: one genuine typecheck error (`type Fallback = Fallback(Conn -> ActionResult -> Conn)` where `ActionResult` doesn't resolve) was printed 4 times, all citing the exact same file/line/column. **Root cause:** `instantiate_ctor` (`lib/typecheck/typecheck.ml:2464`) re-resolves a constructor's stored surface argument types via `surface_ty` on every instantiation (needed for fresh per-use type variables on polymorphic constructors) — but when one of those argument types fails to resolve, `surface_ty` re-emits the identical `(span, message)` diagnostic on every instantiation (pattern match, constructor call) instead of just the first. **Fix:** `Errors.report` (the single choke point every diagnostic passes through) now skips a diagnostic that exactly matches an already-reported `(severity, span, message)` triple — a byte-identical repeat at the same source location can only be the same fact re-derived, never two independent issues coinciding. New regression test `test_broken_ctor_field_type_reported_once` in `test/test_compiler.ml` (a 3-instantiation repro asserting the bogus-type error is reported exactly once). Verified against the live bastion repro: `router.march:46:35`'s `ActionResult` error dropped from 4 occurrences to 1; project-wide diagnostic count dropped from 54 to 46.
