Rewritten as two-line `let`-then-field doctests, matching the pattern in `stdlib/rrb_vec.march`; those `let`-as-doctest-line examples are known to fail the doctest runner's single-expression `expr_eof` parse (pre-existing gap — `RRB.fold`/`RRB.chunk` doctests fail identically on unmodified `main`), so `Cli.flag`/`Cli.value_flag`/`Cli.flag_with`'s doctests currently report as failing for the same pre-existing infra reason; not introduced by this task and out of scope to fix here. — `let ((a,b),(c,d)) = ...` emitted references to undefined global functions (`lib/tir/lower.ml`, `test/test_codegen.ml`, `specs/lang/golden/`, `specs/lang/core-march.md`, 2026-07-05).** Found by the Core March golden corpus (Phase 1 Task 2, tuples). A nested tuple destructured in a block-`let` — e.g. `let ((a, b), (c, d)) = ((1, 2), (3, 4))` — ran correctly interpreted (prints `10`) and compiled fine as the equivalent `match ((1,2),(3,4)) do ((a,b),(c,d)) -> … end`, but `--compile` on the `let` form emitted `%gl = call ptr @a()` for every leaf var and clang rejected the module (`error: use of undefined value '@a'`, exit 1). **Root cause:** the block-`let` `PatTuple` lowering (`EBlock (ELet … :: rest)` arm) bound only *direct* `PatVar` tuple elements — its inner fold had `| Ast.PatVar n -> …bind field… | _ -> inner`, so any non-var element (crucially a NESTED `PatTuple`) hit the `| _ -> inner` catch-all and was **silently dropped**. The nested tuple's leaf vars (`a`/`b`/`c`/`d`) were therefore never bound; later uses fell through `resolve_use_alias` and were rewritten into global function references (`@a()`), which don't exist → clang error. (`collect_pat_names` DID recurse — so the names were registered in `_fn_param_types` and typechecked — but the value-binding fold flattened only one level, which is why the failure surfaced at codegen, not typecheck.) **Fix:** replaced the one-level fold with a recursive `bind_subpat scrut scrut_ty pat inner` helper (local to the `PatTuple` arm) that mirrors the match path's `compile_matrix` decomposition — it handles `PatWild` (skip), `PatVar` (bind field directly, preserving the original RC-friendly single-level shape when the element is a leaf), `PatAs` (bind outer name + recurse), and nested `PatTuple` (bind a fresh var to the field via `EField`, then recurse into it, threading each element's concrete type from the parent tuple type so nested scalar fields untag correctly). Records / refutable sub-patterns keep the prior no-decompose behaviour (unchanged; they fall to the outer catch-all `let`). Interpreter and flat-tuple / direct-`PatVar` lowering are unchanged (flat `let (a,b) = …` produces byte-identical TIR — the 29 TIR snapshots stay green with no regeneration). **Regression:** new `nested_tuple_let_codegen` group in `test/test_codegen.ml` (2 compile-and-run tests: the exact repro → `10`; a deeper 3-level-nesting + wildcard-element + interior-nested-tuple program → `15`) — both RED pre-fix with the `@a` clang error, GREEN post-fix. New golden program `specs/lang/golden/g10_nested_tuple_let.march` (output `10`), added to the §5 corpus table in `specs/lang/core-march.md` (the corpus's 10th program — `g09_float_show` is the concurrently-added float golden merged from main; `verify.sh` 10/10 MATCH) so the fix runs in the `@oracle` conformance lane. **Gates (six runners + golden + oracle):** 400 compiler / 230 eval / 387 codegen (+2) / 773 stdlib-quick / 53 stdlib_march / 29 snapshots — all exit 0; golden `verify.sh` 10/10.
