- ✅ **Cross-module typeclass dispatch — record-typed impls** — Follow-up to the above: a typeclass `impl` on a **record** type was invisible to a call site in a different module ("`T` does not implement `Iface`"), even with the impl co-located with its type. Root cause: two paths register an impl into `env.impls` and disagreed on record representation — `check_decl`'s `DImpl` handler uses `surface_ty`, which **expands a record type name to its structural form** (`TRecord [...]`), but the forward-reference pre-pass `register_impl_shape` used a lenient converter that mapped `TyCon "T"` → nominal `TCon "T"` and never consulted `env.records`. So when a dispatch in module A is discharged *before* the impl's own `DImpl` is reached in pass 2 (the cross-module / multi-file order the resolver produces, `extra_decls @ entry_decls`), only the nominal pre-pass shape was registered, and `impl_matches_ty(TCon "T", TRecord […])` failed. Variant impls were unaffected (both paths produce `TCon`). Fix (`lib/typecheck/typecheck.ml`): `register_impl_shape`'s `lenient_ty` now expands a record type name structurally via `env.records`, mirroring `surface_ty`, so the forward-ref shape matches. +1 test (`interface cross-module record dispatch`). Verified end-to-end on the **compiled** path (TIR/native dispatches correctly by type). Two separate, deeper limitations were noted at the time: (a) the tree-walking **interpreter** dispatches a user interface by last-impl-wins rather than by type — even within one module — so user typeclasses only dispatch correctly when compiled (`forge build`); (b) the **LSP's per-file** analysis couldn't see an interface declared in a different file from an `impl`. **(b) is now fixed** (next entry); (a) remains.
