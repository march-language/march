- ✅ **`Regex` compiler allocated ~5.82 heap strings per PATTERN BYTE, and the matcher ~1.2 per INPUT BYTE per match attempt; both rewritten as byte-index scanners (2026-07-28, `stdlib/regex.march`).** Different shape from the data-format parsers: `compile()` used `string_chars(pattern)` plus per-character `RAClass` range expansion (parser-shaped, same fix as Json/Toml); the matcher's `atom_matches` tested every position via a `char_at` helper doing `string_slice(s, pos, 1)` on every byte probed, including every backtracking retry (not char-at-a-time accumulation, but the same underlying "materialise a string where an int would do" mistake). Fixed by making `RALit`/`RAClass` carry `Int` byte codes instead of 1-char `String`s, and rewriting `parse_atom`/`parse_class_body`/`parse_items`/`compile`/`atom_matches` to use `string_byte_at`. Measured compiled `--opt 2`: compile phase (49-byte pattern, 20,000 iterations) **5.82 → ~0 allocs/pattern-byte** (285 → 4 total allocations across all iterations); match phase (`find_all`+`replace_all` with `\d+` against a 265-byte input, 5,000 iterations) **1.215 → 0.064 allocs/input-byte** (a ~19x reduction; residual allocation is the unavoidable `string_slice`/`string_join` materializing actual match substrings). Verified via the existing `test_regex.march` suite (18/18 passing) plus a 62-case round-trip corpus (literals, classes, escapes, anchors, quantifiers, all 5 public functions, edge cases including empty matches and boundary positions), interpreted and compiled.
