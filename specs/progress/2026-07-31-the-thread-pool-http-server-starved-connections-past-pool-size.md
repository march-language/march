- ✅ **The thread-pool HTTP server starved connections past `pool_size` — fixed (2026-07-31, `runtime/march_http.c` `pool_grow_if_starved`).** A worker owns a connection for its entire keep-alive lifetime, so a fixed pool of N workers served at most N concurrent connections and the rest were accepted by the kernel and never read — at 256 offered connections with the default `ncpus*2` = 28 workers, 228 sat with unread bytes in `Recv-Q` indefinitely. The pool is now elastic: `size` is a floor, and a worker about to park starts one more if it was the last idle one, up to `max_size` (from `HttpServer.max_connections`, which until now was accepted and discarded). `threads` is allocated at `max_size` upfront so growth never reallocates a live array, and `pool_stop` joins a `size` snapshot taken under the queue lock that `pool_grow_if_starved` also holds. **Measured at c=256, order-swapped and repeated: 228 unread → 0, in-flight 27.7 → 253.7.** Reported latency rises 0.90 → 8.67 ms, which is the honest number: the old average covered only the 28 connections being served. Throughput −5% (30,774 → 29,261) because the box's ~30k rps ceiling is client/kernel-side, so 9× the connections buys no throughput and costs scheduler overhead. Above a few hundred concurrent connections the event loop (`MARCH_HTTP_EVLOOP=1`) remains the better answer at 15–17% less CPU per request.
