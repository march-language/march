- ✅ **LSP cross-file interfaces — per-file analysis resolves a sibling-module interface** — An `impl` in one project file referencing an `interface` declared in another reported a spurious "Unknown interface" in the editor, even though whole-program `forge build` was clean. Root cause: the LSP's per-file path uses the **incremental** checker `check_module_with_env`, whose own pre-pass `prebind_mod_members_inc` handled `DFn`/`DType` for sibling `DMod`s but **silently dropped `DInterface`/`DImpl`** (`_ -> e`) — unlike `check_module_core`'s `prebind_mod_members`, which registers them. So sibling functions and types resolved cross-file but interfaces never reached `env.interfaces`. (The siblings were correctly discovered and loaded — `with_deps.interfaces` had the interface — the incremental pre-pass just ignored them when checking the user file.) Fix (`lib/typecheck/typecheck.ml`): extracted the interface-prebinding (register the name qualified + bare, and each method) into a shared top-level `prebind_interface_decl ~prefix` used by **both** pre-passes so they can't diverge again, and registered sibling impls in the incremental `DMod` handler. Now cross-file interfaces resolve in the editor across lib subdirectories, matching `forge build`; a genuinely-undeclared interface still errors. +2 LSP tests (`cross-file`: interface-resolves, unknown-still-errors), using a real temp forge project with the impl in `lib/sub/` and the interface in `lib/`. This is the last of the four cross-file-typeclass layers (typecheck dispatch, record impls, native codegen, LSP) — only the tree-walking interpreter's last-impl-wins dispatch remains, a separate eval-backend change.
