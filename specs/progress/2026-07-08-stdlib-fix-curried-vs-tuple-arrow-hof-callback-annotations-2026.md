# Stdlib fix — curried-vs-tuple-arrow HOF callback annotations (2026-07-08)


- ✅ **Root-caused and fixed a real (previously invisible) stdlib typecheck bug, NOT the module-scoping bug it was originally reported as.** Investigation started from a report of a bogus `prelude.march:129:33: expected (a, b) but got a` error surfacing only in a (not-in-this-worktree) browser live-compile pipeline, hypothesized to be caused by `lib/typecheck/typecheck.ml`'s pass-1/1b bare-name registration leaking a same-named sibling module's binding (`fold_left` exists in both `prelude.march` and `list.march`) into an earlier module's own body-check. That hypothesis was **falsified by direct reproduction**: `stdlib/prelude.march` typechecked completely alone (`check_module_core`, no siblings, no `list.march` in the merge at all) reproduces the identical error — so no cross-module scoping is involved, and `lib/typecheck/typecheck.ml` itself needed no change.
- ✅ **Real root cause: `fold_left`'s `f` callback param was annotated as a TUPLE-arrow (`f : (b, a) -> b`, parses to `TArrow(TTuple[b;a], b)`) but is CALLED with N-ary uncurried call syntax (`f(acc, h)`).** `infer_app` (`lib/typecheck/typecheck.ml`) is purely curried — it peels one `TArrow` layer per call argument with no auto-tupling special case — so a 2-arg call against a 1-arg tuple-taking function checks the FIRST arg against the whole tuple type and fails. The correct annotation for an uncurried-call-style callback is a curried arrow chain (`f : b -> a -> b`), matching how every value-level lambda passed to it (`fn (acc, x) -> ...`) is itself typed, and matching `stdlib/list.march`'s ALREADY-correct `List.fold_left` signature.
- ✅ **Why this was invisible for the entire lifetime of the bug: `bin/main.ml`'s `is_user_file` diagnostic filter (both the single-file `--check`/`--compile` path and `run_check_cmd`'s multi-file `forge build` path) drops every diagnostic whose span points into a stdlib file** — by design, to keep stdlib-internal typecheck noise out of user-facing output. This silently swallowed the `fold_left` error (and 5 other files with the identical typo) on every `march --compile`/`--check` for as long as the annotations were wrong; nothing in the normal CLI path ever surfaced it. A downstream pipeline that does NOT apply that same filter (the browser live-compile target that originally reported this) surfaced it as a user-visible failure.
- ✅ **Same tuple-vs-curried annotation typo found and fixed in 5 files** (grepped the whole stdlib for `: (a, b, ...) -> c`-shaped HOF-callback annotations and checked each call site's actual arity convention): `stdlib/prelude.march` (`fold_left`'s `f`), `stdlib/iterable.march` (`fold`'s `f`), `stdlib/ordered_map.march` (`cmp` — 13 occurrences across free fns + the `{cmp:_, tree:_}` record type literal repeated per accessor — plus `tree_fold`'s `f`, `tree_map`/`tree_filter`'s `f`), `stdlib/sorted_set.march` (same `cmp` pattern + `tree_fold`'s `f`), `stdlib/range.march` (`reduce`'s `f`). `stdlib/tuple.march`'s superficially-similar `apply(t : (a,b), f : (a,b) -> c) : c do f(t) end` was investigated and is NOT a bug — `f` is genuinely called with the packed tuple `t` as a single argument, matching its tuple-arrow type; left unchanged.
- ✅ **One additional, unrelated pre-existing bug found and fixed while verifying the above end-to-end via the real CLI:** `stdlib/range.march`'s `reduce` called `List.fold_left(acc, to_list(r), ...)` with the collection and accumulator arguments SWAPPED (`List.fold_left`'s real signature is `fold_left(xs, acc, f)`, collection first per the stdlib's uncurried-collection convention) — masked until the `f`-annotation fix above stopped it from failing one step earlier. Fixed to `List.fold_left(to_list(r), acc, ...)`.
- ✅ **Verified end-to-end via the real `bin/main.exe --check` CLI** (not just the isolated-file harness used for root-causing): a small program calling `fold_left`, `Iterable.fold`, `OrderedMap.new`/`put`, `SortedSet.new`/`add`, and `Range.reduce` — all with literal 2-arg lambdas, the normal user-facing calling convention — now typechecks with zero errors/exit 0; previously (pre-fix) `fold_left` alone produced a user-visible `` `(<error>, Int)` does not implement Num `` cascading error (the tuple-arrow mismatch corrupting the accumulator's inferred type before the `+` operator's `Num` constraint discharge, all attributed to the CALLER's own span — user-visible in real programs, not just hidden stdlib noise, contrary to the initial assumption that this was purely invisible).
- ✅ **Regression tests added to `test/test_compiler.ml`** (`test_stdlib_prelude_fold_left_curried`, `test_stdlib_iterable_fold_curried`, `test_stdlib_ordered_map_cmp_curried`, `test_stdlib_sorted_set_cmp_curried`, `test_stdlib_range_reduce_curried`): each typechecks the named stdlib file COMPLETELY STANDALONE (`load_stdlib_file_for_test` + `check_module_core`, no other stdlib siblings in the merge, mirroring `bin/main.ml`'s `get_stdlib_tc_env`) and asserts zero errors — the same mode of failure the original bug hid in, made a first-class assertion instead of a silently-filtered diagnostic. The originally-requested test shape (two synthetic sibling modules with a same-named bare function, to catch a module-scoping leak) was NOT added since that bug does not exist.
- ✅ **Standard gates, all green:** `run_compiler`/`run_eval`/`run_codegen`/`run_stdlib`/`test_stdlib_march`/`run_snapshots` all exit 0, zero `[FAIL]`, zero `.expected` diffs (full run, not `-q`).
