- ✅ **`Csv.read_all`/`Csv.each_row_with_header` silently returned zero rows compiled (2026-07-21).** Found auditing `docs/cookbook/files.md`'s CSV example: interpreted printed the correct row count and the docs' `Sales.sum_column`-style aggregation summed correctly, but compiled silently returned 0 rows / a wrong total with no error, and `each_row_with_header`'s per-row callback never fired. Root cause: `stdlib/csv.march`'s `CsvRow = CsvEof | Row(List(String))` is niche-shaped (one nullary ctor + one single-payload ctor whose payload is heap-pointer-shaped, i.e. niche-safe), and the C runtime (`runtime/march_runtime.c`'s `march_csv_next_row`) already encoded it as Niche (`NULL` for `CsvEof`) — but `lib/typecheck/typecheck.ml`'s hardcoded builtin signature for `csv_next_row` declared its return type as the **bare** `TCon("CsvRow", [])`, while the TIR registers user `ptype`s under their **module-qualified** name (`"Csv.CsvRow"`, per `lib/tir/lower_decls.ml`'s `qtname`). That name mismatch made `Repr.niche_repr_of_concrete`'s `find_variant` (`lib/tir/repr.ml`) miss the type definition at the `match csv_next_row(handle) do ...` call site and silently fall back to `Boxed` (confirmed via a temporary `MARCH_REPR_AUDIT=1` instrumentation showing `family=Boxed` for this site) — under `Boxed`, the compiled match reads a tag byte from the heap object, but a raw `NULL` (the runtime's EOF convention) can only be decoded under `Niche`, so every real row was misread as the nullary `CsvEof` immediately. A pre-existing SEPARATE bug in the same function (`csv_row_result` wrapped the row's fields list in an extra un-tagged `march_alloc(24)` box) was also fixed — that wrapper is now redundant/wrong once `Niche` decoding is correctly selected: `Row(fields)`'s value under Niche IS the fields-list pointer directly, no wrapper. Fix: (1) `typecheck.ml:1640` — `TCon("CsvRow", [])` → `TCon("Csv.CsvRow", [])`; (2) `runtime/march_runtime.c`'s `csv_row_result` returns the fields-list pointer directly instead of allocating a wrapper box. Verified interpreted/compiled parity on the reported repro (row count 4, `Sales`-style sum 35, `each_row_with_header` callback fires for all 3 data rows) and confirmed via a baseline diff (reverting just these two files) that the pre-existing `llvm_ir_validity_gate` corpus failures (`Unknown module CRDT`/`IO` — a `test/test_ir_verify.ml` environment gap, unrelated) are NOT caused by this change. New compiled/native regression test `test/native/csv_niche_row.march` + `.expected` + `test/dune` rule (there was previously zero compiled/native coverage for `Csv` — only the interpreted-only `test/stdlib/test_csv.march`).
