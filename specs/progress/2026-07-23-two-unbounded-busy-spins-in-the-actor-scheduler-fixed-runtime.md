- ✅ **Two unbounded busy-spins in the actor scheduler fixed (`runtime/march_runtime.c`, `runtime/march_scheduler.c`, 2026-07-23).** `task_wait_done`'s in-scheduler branch (`task_await`/`task_await_unwrap`'s wait path) and `march_sched_wake`'s `PROC_PARKED`-wait spin had no deadline/fallback — either could peg an OS thread at ~100% CPU forever if the proc it waited on never made progress in bounded time (suspected cause of multi-hour CPU-pegged compiled-test hangs under host oversubscription; see `project_scheduler_unbounded_spin_hangs` memory for the full investigation). Both now spin-yield for a generous grace period, then fall back to a cheap `nanosleep(1ms)`-based poll instead of a tight spin — `task_await`'s wait-forever semantics are unchanged, only how the wait is performed. `task_wait_done`'s grace period is wall-clock (`CLOCK_MONOTONIC`, 5s), not an iteration count — an iteration-count version was tried first and A/B-benchmarked to silently collapse legitimate heavy-parallelism throughput (`bench/par_fib.march`-shaped workload: ~390% CPU → ~15% CPU) because each `march_sched_yield()` round trip takes longer when the scheduler is genuinely busy, so a fixed iteration count elapses in far less wall-clock time than intended. `march_sched_wake`'s spin stays iteration-count-based (its transition is a bounded, wait-free-ish critical section independent of arbitrary user-code progress, confirmed safe via the same A/B benchmark). Verified: full suite (`run_compiler` 538 / `run_eval` 240 / `run_codegen` 444 / `run_stdlib` 816, one pre-existing unrelated failure — a 100%-reproducible macOS/ASAN dyld-init livelock confirmed independent of March via a bare `clang -fsanitize=address` hello-world reproducing it identically), `bench/list_ops.march` + `bench/parallel.march` no regression, `par_fib`-shaped fork-join workload below its scaling limits restored to full parallel throughput. **Known follow-up (not fixed here, tracked separately):** profiling a fork-join workload that crosses March's task-count scaling cliff (~14K→22K concurrent `task_spawn`s) found this CPU-backoff patch alone does not fix that cliff — it cuts CPU usage as designed but the workload still doesn't complete, revealing a separate, deeper LIFO-starvation bug in `sched_loop`'s local-deque dispatch policy (an awaiter re-queuing itself starves its own not-yet-run sibling task). See `project_scheduler_unbounded_spin_hangs` memory, "second follow-up" section, for the live-profiled evidence and candidate fix directions.
