- ✅ **`march check`'s multi-file combined typecheck re-embedded shared/auto-discovered modules once per input file — confirmed superlinear blowup on a real ~85-file project, fixed (`bin/main.ml`'s `run_check_cmd`, `forge/test/test_build_check.ml`, 2026-07-06).** Found immediately after landing the `forge build`/`forge check` batching entry below, by measuring real compile/typecheck time on an external ~85-file project (`~/code/bastion`): the combined `march check f1 f2 ... fn` never finished in 4+ minutes, versus the old per-file behavior completing the whole project in seconds. **Root cause:** `run_check_cmd` called `resolve_imports` once per input file, and each call's `auto_discover` step unconditionally re-walks and re-parses the ENTIRE library search path with dedup tables scoped to that one call only — but the resulting `extra_decls` were then merged INTO that file's own wrapper `DMod`'s body instead of emitted as flat top-level siblings, hiding any cross-file duplicate from a name-based dedup pass and (independently) giving auto-discovered modules the wrong qualified name (`EntryFile.Module.name` instead of `Module.name` — the exact hazard `resolve_imports`'s own doc comment warns nesting causes). Confirmed empirically before the fix: checking N files together, the SAME diagnostic (same file/line/message) appeared exactly N times, and total time compounded far worse than linearly (1 file: 0.97s, 2: 2.10s, 5: 23.71s). **Fix:** `extra_decls` are now returned as flat siblings (`extra_decls @ [own DMod]` instead of merged into the own DMod's `mod_decls`), plus a dedup-by-module-name pass over the combined top-level decl list (first occurrence wins — safe since one-mod-per-file means a shared module name is always the same file). Post-fix: error/warning counts stay flat regardless of file count, time scales roughly linearly (1→20 files: 1.0–1.7s, no blowup), and the full 85-file bastion project completes in ~4.3s (previously never finished). New regression test `test_check_does_not_duplicate_shared_module_diagnostics` in `forge/test/test_build_check.ml` asserts a shared warning is counted exactly once across a 4-file combined check, calling `Cmd_build.check_all` directly to inspect its returned warning count. **Unrelated finding surfaced along the way (not fixed, out of scope):** bastion's own code used `write(path)(content)`-style curried calls (~36 call sites across 3 files) that the recently-landed `f(1)(2)`-is-a-parse-error change now rejects — fixed in bastion itself (a separate project), not in this repo.
