- ✅ **Cross-module qualified-record function signatures — nominal/structural unify reconciliation** — Sibling of the two entries above, but for function *signatures* rather than typeclass impls. In a whole-program build (`march --check <entry>` with siblings via `MARCH_LIB_PATH`), a sibling annotating a param with the entry module's record type under its **qualified** name (`s : Cfg.Site`) and then calling one of that module's functions (`Cfg.site_title(s)`) failed with the baffling "expected `Site` but got `Site`". Root cause: `surface_ty` expands a record annotation to its structural `TRecord`, but the whole-program forward-reference pre-pass `prebind_fn_scheme` (`lib/typecheck/typecheck.ml`) — which pre-binds cross-module function schemes in Pass 1 so siblings can typecheck against each other — is a lightweight *env-free* converter that maps every `TyCon "Site"` to a **nominal** `TCon "Site"` and never consults `env.records`. So `Cfg.site_title`'s pre-bound param stayed `TCon "Site"` while the argument's type was the structural `TRecord`, and `unify` had no `TCon`↔`TRecord` case (it fell straight to `report_mismatch`). Variant signatures were unaffected (both paths produce `TCon`) — the exact same nominal-vs-structural asymmetry as the `register_impl_shape` record-impl bug above. Fix (`lib/typecheck/typecheck.ml`): a new `unify` case reconciles a nominal record `TCon` with a structural `TRecord` by expanding the `TCon` side via `expand_record` (routed through a forward-ref hook, since `expand_record` is defined later — it depends on `surface_ty`) and retrying. This subsumes *all* nominal-record sources, not just `prebind_fn_scheme`, and is order-independent. Guarded with `name_is_variant` exactly as `surface_ty`'s own record-expansion is: in a global-namespace collision a variant and a record can share a printed name (the record leaks into `env.records` under the bare name), so a `TCon` naming the *variant* must not expand into the colliding record's structure — else the "two distinct types share the name" diagnostic would be silently swallowed (regression-covered by the existing `same-name type collision` test). The new arm is only reachable in states that previously always errored, so it can only convert spurious errors to successes, never regress a passing unification. Regression test: the existing `test/dune` whole-program rule (`--check whole_program/cfg.march`, exit 0) now actually passes on a fresh build. A separate, pre-existing whole-program leak remains out of scope: a **variant** constructor of the entry module used by a sibling under a qualified result type (`Zoo.Lion` → `TCon "Zoo.Beast"` vs bare `Beast`) still mismatches when *that* file is the entry — a `TCon`↔`TCon` qualified/bare issue, not `TCon`↔`TRecord`.
