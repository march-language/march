# Tuples have no `Eq` (or `Ord`) impl

**Logged:** 2026-10-01

`(1, ["x"]) == (1, ["x"])` is rejected: "`(Int, List(String))` does not
implement interface `Eq`", even though every component type is `Eq` and the
runtime compares tuples structurally. `List(a)` and `Option(a)` get `Eq` from
`impl Eq(List(a)) when Eq(a)` in stdlib; there is no tuple counterpart, and a
user cannot write one for an arbitrary arity.

Found while fixing test-body constraint discharge
(`progress/2026-10-01-test-body-constraint-discharge.md`): two asserts in
`test/stdlib/test_control.march` compared `(Int, List(String))` tuples and had
to destructure instead.

Options: discharge `CInterface ("Eq"|"Ord", TTuple ts)` structurally in
`discharge_constraints` (`lib/typecheck/typecheck.ml`) when every component
satisfies the interface, and check that every backend's `==` handles tuples.
Specify the result in `specs/lang/`.

Related shallowness, same function: a conditional impl
(`impl Eq(Option(a)) when Eq(a)`) is matched by `impl_matches_ty` without
re-checking its `when` bound, so `Some(x) == Some(y)` is accepted for an `x`
whose type has no `Eq`.

## Eq landed 2026-10-06; Ord split out

`discharge_constraints` (`lib/typecheck/typecheck.ml`) now discharges
`CInterface ("Eq", (τ₁, …, τₙ))` when every component is `Eq`, recursively. A
component that is still a type variable is skipped, like a top-level one.
`(1, ["x"]) == (1, ["x"])` typechecks, and `(1, Rood) == (1, Bloo)` on an ADT
without `derive Eq` is still rejected (naming the tuple type).

Checking every backend's `==` on tuples turned up a compiled miscompile.
`__march_eq_Tup_*` (`lib/tir/llvm_eq.ml`) loaded a Float component as a raw
`double`, but a tuple stores every slot uniformly (`Llvm_emit_data.emit_tuple`:
Int tagged, Float BOXED). It compared the two box pointers, so
`(1, 2.5) == (1, 2.5)` was `false` compiled and `true` interpreted (before
this change that was reachable only from generic code such as
`List.member`). A tuple's Float slot is now unboxed and compared by value. A
generic (type-variable) slot now goes through `march_poly_eq` instead of
pointer identity, as the ADT path already did. Records keep their inline
`double` slot.

Specified in `specs/lang/interfaces.md` (Standard Interfaces → Eq) and
`specs/lang/core-march-types.md` §2.1b.

Tests: `test_compiler` `generic_when_constraints`, "tuple of Eq components is
Eq" (red before) and "tuple with a non-Eq component is not Eq".
`test/native/tuple_eq.march`: the expected output is the interpreter's, and
compiled matches it.

Not done, filed as
[../todos/2026-10-06-tuple-ord.md](../todos/2026-10-06-tuple-ord.md): tuple
`Ord`, which needs backend work (interpreted `<` on tuples panics "no `Ord`
implementation for this type", compiled `compare` on tuples has no impl), and
the `when`-bound re-check of conditional impls.
