- ✅ **`char_from_int` returned different bytes interpreted vs compiled — silent data corruption in `Uri.decode`, msgpack and `Http` (2026-07-31, `lib/eval/eval.ml`, `test/test_stdlib_suite.ml`).** The C runtime's `march_char_from_int` is `(char)(n & 0xFF)` — a byte constructor over 0–255 — while the interpreter clamped to ASCII and returned `VString ""` for `n > 127`, with no error. Every caller feeding it a real byte was correct compiled and corrupt interpreted: percent-decode in `stdlib/uri.march`, the msgpack raw-byte walk, `Http` header decoding, `Gen`'s char-list builder. Measured against a pre-fix control, `Uri.decode("caf%C3%A9")` gave `"caf"` (3 bytes) interpreted vs `"café"` (5 bytes) compiled. **Fixed** by moving the interpreter to the runtime's semantics (`n land 0xFF`), not the reverse: ASCII-only is not what the runtime, the JS backend or the docs describe, and would have broken URI/msgpack decoding that works today compiled. The mask rather than a range check is load-bearing for parity — the runtime wraps, so `256` must yield byte 0, not raise. `byte_to_char` keeps its out-of-range **error** deliberately: same payload and same C function once compiled, but its name denotes a byte, so out-of-range there is a caller bug. This is the trap noted in passing in the `Json.parse \uXXXX` entry below, now fixed at the source; `utf8_encode` still uses `byte_to_char` (the better name for a byte builder), with its stale "they disagree" comment corrected, and the `Char.from_int`/`Char.to_int` docstrings no longer claim "code point". **Known remaining divergence, out of scope:** the JS backend implements `char_from_int` as `String.fromCodePoint(n)` — a third semantics, differing above 255 and throwing on negatives — which is a question about the JS UTF-16 string model versus March's byte strings, not about this builtin. **Pinned by** one `run_stdlib` case round-tripping all 256 values through `char_to_int` with a byte-length check, plus four wraparound cases (256→0, 511→255, -1→255, -256→0), asserted against a literal so it cannot go green if both backends drift together or pass vacuously without clang; confirmed RED before the fix (the pre-fix interpreter *died* at n=128 rather than scoring 128, since `char_to_int` rejects the empty string).
