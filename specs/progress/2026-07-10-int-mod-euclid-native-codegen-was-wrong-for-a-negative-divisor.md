- ✅ **`int_mod_euclid` native codegen was wrong for a negative divisor — fixed + renamed `march_checked_umod` → `march_checked_emod` (2026-07-10).** The runtime helper lowered `int_mod_euclid` to genuinely-*unsigned* `%` (`(uint64_t)a % (uint64_t)b`), which agrees with the interpreter's Euclidean remainder only when the divisor is positive; for a **negative** divisor it diverged silently — e.g. `int_mod_euclid(-7, -3)` gave `-7` compiled vs. `2` interpreted (unsigned `%` returns a huge value cast back to a negative int64). Replaced with signed Euclidean semantics mirroring `eval.ml` byte-for-byte (`r = a % b; if r < 0 then r + abs b else r`) and renamed the symbol to `march_checked_emod` so it reads as the mod-side pair of the new `march_checked_ediv` (the old "u"-for-unsigned prefix was actively misleading once the body became signed). Touched the same multi-site set as the `_ediv` add: `runtime/march_runtime.c` (impl + the shared comment block), both `llvm_emit.ml` mapping sites, the `llvm_builtins.ml` preamble (string table + `PDeclare`), and the `test_codegen.ml` preamble golden. New parity test `test_compiled_int_mod_euclid_parity` covers all four sign quadrants (`[1, 2, 2, 1]`), with the `(-7, -3) → 2` case pinning the regression. Manually confirmed interpreter and compiled now agree. (The `INT64_MIN` divisor edge — `abs(INT64_MIN)` unrepresentable — is left undefended, matching `eval.ml`'s own OCaml `abs min_int` behaviour; no caller reaches it.)
