- ✅ **`Json.parse` rejected `\uXXXX` escapes — valid RFC 8259 §7 JSON failed to parse (2026-07-30, `stdlib/json.march`, `test/stdlib/test_json.march`).** `unescape` decoded the eight two-byte escapes (`\" \\ \/ \n \r \t \b \f`) and returned `Err("unknown escape sequence")` for everything else, so `Json.parse("\"\\u0041\"")` failed on input that most serializers emit for any non-ASCII character. Fixed by adding `hex_val`/`hex4`/`utf8_encode`/`unescape_u` and a `\u` branch in `scan_string`. `\u` is the only JSON escape whose length is not fixed at two bytes, so `unescape_u` returns the decoded text *and* the index just past the escape and `scan_string` resumes there, preserving the existing run-slicing discipline (one `string_slice` per unescaped run). Surrogate pairs decode to one astral code point; a lone surrogate is rejected rather than emitted, since it is not a Unicode scalar value. **Trap found in passing:** `char_from_int` is documented as single-byte `n & 0xFF` — true of `march_char_from_int` in the C runtime, but the *interpreter* returns `VString ""` above 127 (`lib/eval/eval.ml`), so the first `utf8_encode` silently produced the empty string for every multi-byte code point while the ASCII case passed. `byte_to_char` is the builtin that covers 0–255 in both backends (same C implementation when compiled) and is what the encoder uses; the two builtins diverge only in the interpreter, with no error. Output verified identical interpreted and compiled for 1-, 2-, 3- and 4-byte results. **Pinned by** 11 cases in `test/stdlib/test_json.march` — the four encoder widths, an escape adjacent to literal runs, an escape in an object key, and five rejections (lone high surrogate, high surrogate followed by a non-surrogate, lone low surrogate, short escape, non-hex digit, truncated at end of input); the six accept cases confirmed RED before the fix. Suites unchanged at `run_stdlib` 826 with only the pre-existing environmental `MARCH_SANITIZE` failure.
