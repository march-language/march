# No CI job verifies --cap-sandbox actually enforces anything at runtime

Found 2026-08-10, investigating Tier 5 of
`specs/2026-08-09-cap-loose-ends-plan.md` (`specs/2026-08-10-cap-tier5-
investigation.md`). Independent of that investigation's other findings —
worth its own todo regardless of what happens with `IO.NetListen`/Landlock.

## The gap

`test/test_cap_sandbox_profile.ml` and `test/test_cap_strip.ml` verify the
embedded SBPL (macOS) / seccomp `-D` flag (Linux) STRINGS are correct and
agree between `bin/main.ml`'s embedded profile and `forge`'s
`Cap_sandbox.profile_for`. **Nothing verifies the runtime behavior these
strings are supposed to produce.** The `IO.Network`/`IO.Process`/
`IO.FileWrite` seccomp-bpf deny classes in `runtime/march_runtime.c`'s
`march_sandbox_install` (~line 1782) have never had a test that actually:
- compiles a program holding capability X but not Y
- runs it under the real sandbox
- asserts a syscall Y would need fails with `EPERM` (or the March-level
  `Err` it should surface as)
- asserts a syscall X needs still succeeds

The BPF program is hand-assembled (`sock_filter`/`BPF_JUMP`/`BPF_STMT`
macros with fixed jump offsets), not generated by a library — a future
refactor that gets an offset wrong would silently allow or deny the wrong
syscall, and nothing in CI would notice. This is the same class of blind
spot `test_cap_attrib_agreement.ml` and `test_cap_sandbox_profile.ml`
(#221, #234) closed for the capability-table/SBPL-string agreement
problems — this is the equivalent gap one level down, at actual enforcement.

## Fix shape

A Linux-only CI job (the `ubuntu-24.04` runner already exists in
`.github/workflows/ci.yml`'s matrix). For each deny class currently shipped
(NET/EXEC/WRITE), compile a minimal program that:
1. Holds every OTHER capability but the one under test
2. Attempts the syscall that capability class gates (a `socket()` call for
   NET, `execve` for EXEC, an `openat` with a write flag for WRITE)
3. Asserts the attempt fails (EPERM, surfaced through whatever March-level
   error the runtime maps it to — check what `march_sandbox_install`'s
   comment says: "so a withheld capability surfaces as a March `Err` the
   program can handle instead of a crash")
4. As a companion positive case, holds the capability and asserts the same
   syscall succeeds — a test that only checks the DENY direction would pass
   trivially if the sandbox failed to install at all.

Extend this test as `IO.NetListen`/Landlock work lands (see the Tier 5
investigation doc) rather than only after — ideally this CI job exists
BEFORE either of those ships, so they land with real proof rather than a
plausible-looking diff.
