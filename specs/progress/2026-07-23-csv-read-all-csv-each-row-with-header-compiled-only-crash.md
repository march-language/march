The report hypothesized a reoccurrence of the niche/Boxed misclassification (via the large "same-short-name colliding types" FQN-dispatch-identity work landed 2026-07-21) — investigated and RULED OUT: `MARCH_REPR_AUDIT`-style direct instrumentation confirmed `Csv.CsvRow`'s match sites still classify correctly as `Niche(tagged=false)`, not colliding, at every `case` site. **Actual root cause, found by bisecting `git log -- lib/tir/llvm_emit.ml lib/tir/llvm_builtins.ml` between the 2026-07-21 fix and current `main`:** commit `646f895d` ("fix(codegen): coerce builtin call args to declared param types", 2026-07-22 — see the entry below) added a fallback that coerces a builtin call's arguments to the callee's declared C parameter type (via `Llvm_builtins.builtin_param_llvm_tys`, parsed from `declare_sig`) whenever `top_fn_param_tys` has no entry. `csv_open`'s returned "handle" is a raw native `FILE*` pointer smuggled through March's type system as a plain `Int` (an established, pre-existing convention shared by `file_open`, TCP handles, etc.) — `csv_open`/`csv_next_row`/`csv_close`'s C `declare_sig`s all type this parameter as `ptr`. The new fallback saw the LLVM-level mismatch (`handle`'s TIR type `Int` lowers to `"i64"`, the declared param is `"ptr"`) and applied `Llvm_ctx.coerce`'s `("i64","ptr")` case — the boxing convention for a genuine `Int` value entering a generic/erased slot, `(v<<1)|1` then `inttoptr` — corrupting the handle's real heap address before every `csv_next_row`/`csv_close` call. Confirmed via `--emit-llvm`: `%cv9 = shl i64 %ld8, 1 / %cv10 = or i64 %cv9, 1 / %cv11 = inttoptr i64 %cv10 to ptr / call ptr @march_csv_next_row(ptr %cv11)`. Explains every symptom: the tagged/shifted address is garbage, so each call reads whatever happens to live at `(h*2)+1` — sometimes decoding as a plausible-looking immediate EOF (`row count: 0`, no crash), sometimes a wild pointer (SIGBUS/SIGSEGV), depending on what's mapped there. A scratch `git worktree` bisect at `646f895d~1` vs `646f895d` reproduced clean-pass-every-time vs. crash-most-of-the-time deterministically. **Fix:** restricted the new fallback (`lib/tir/llvm_emit.ml`, the `EApp` builtin-arg-coercion match) to the ONE direction the original bug actually needed — `"ptr"` (generic/erased slot) → `"i64"`/`"double"` (native scalar param), i.e. unboxing a tagged/boxed value for a builtin's native scalar C parameter. The reverse direction (a concrete `"i64"`/`"double"` argument flowing into a declared `"ptr"` param — the opaque-handle case) now passes through with its own representation unchanged, matching the pre-regression behavior exactly: LLVM's opaque-pointer calls don't require the call-site argument types to textually match the callee's declared prototype (confirmed both by re-extracting the pre-regression `.ll` — `call ptr @march_csv_next_row(i64 %ld5)` against a `declare ptr @march_csv_next_row(ptr %handle)` — and by the 2026-07-22 entry below's own note that clang/LLVM accepts this since `i64`/`ptr` share the same register class). Verified: `test/native/csv_niche_row.march` produces the correct 5-line output across 5+ repeated runs (previously nondeterministic); the ORIGINAL bug `646f895d` fixed (`Some((top, _)) -> int_to_string(top)` printing `7` instead of `3`) still prints `3`, confirming the fix doesn't regress the case it was protecting.
