- ✅ **Typechecker soundness gap: I/O builtins registered with an unconstrained polymorphic `Result` error type instead of their real concrete error type (`lib/typecheck/typecheck.ml`, 2026-07-22)** — `file_read`'s signature was `poly1 (fun e -> TArrow (t_string, t_result t_string e))`: the error type `e` was a free type variable, so a function declared `Result(_, String)` doing `let? content = File.read(path)` typechecked with **zero diagnostics** and then panicked at runtime (`builtin ++: expected two strings`) the moment the bound error was used as a `String` — its real runtime value is always a `File.FileError` constructor (`NotFound`/`Permission`/`IsDirectory`/`NotEmpty`/`IoError`, per `eval.ml`'s `file_error_of_unix`/`file_error_of_sys`), never an arbitrary caller-chosen type. Swept `typecheck.ml` for the same `poly1 (fun e -> ...)`-around-`t_result` shape and found it was a **repeated pattern**, not a one-off: fixed 8 File builtins (`file_read/write/append/delete/copy/rename/stat/open`), 5 Dir builtins (`dir_list/mkdir/mkdir_p/rmdir/rm_rf` — same `FileError`), `csv_open` (concrete `Csv.CsvError` — confirmed not niche-shaped, so the bare name is fine, unlike `CsvRow` which needs the `Csv.`-qualified name for niche-repr lookup), and — after confirming via `eval.ml` and the runtime C (`runtime/march_tls.c`'s `make_err`, `runtime/march_http.c`, `runtime/march_runtime.c`'s process/tcp builtins) that their real error is always a bare `String` in both interpreted and compiled backends — tightened `tcp_connect/send_all/recv_all/recv_http/recv_http_headers/recv_chunk/recv_chunked_frame`, `http_parse_response`, `process_spawn_sync/lines/async`, and `tls_client_ctx/server_ctx/connect/accept/read/write` from unconstrained `e` to `Mono t_string`, matching the precedent already set by `tcp_listen`/`tcp_accept`/`dns_resolve`/`tcp_recv_exact` (already `Mono`). Verified via the real compiler CLI that the reported repro (`Result(_, String)` + `let? = File.read`) now produces a labeled type-mismatch diagnostic instead of compiling, and that normal usage (unannotated return type, or `Err(e) -> to_string(e)`) still compiles and runs correctly. **A pre-existing test encoded the exact bug and had to be fixed, not the other way around:** `test_cap_deterministic_file_read_ok` (`cap_pure_no_extern_det` suite) declared `fn load(path : String) : Result(String, String) do file_read(path) end` — annotating the very type mismatch this fix now (correctly) rejects. Removed the now-invalid `Result(String, String)` annotation (the test's actual point is the `cap deterministic` capability check, not `file_read`'s error shape); left the return type to inference. **Noteworthy side-finding, NOT fixed here (separate, pre-existing bug):** `stdlib/dns.march`'s `DnsError` shares the bare constructor name `NotFound` with `File.FileError` — before this fix, `Err(NotFound(p))` against a `file_read` result "worked" (typechecked) only because the free `e` absorbed whichever type the ambiguous ctor happened to resolve to — with `e` now concrete, that same code correctly fails to typecheck (`expected DnsError but got FileError`) since it's a genuinely ambiguous global-namespace ctor collision that should be qualified. **Also confirmed a deeper, separate divergence while investigating (not fixed — out of scope for this signature fix):** the *compiled* backend's runtime C for `file_read`/`file_write`/`dir_list` etc. (`runtime/march_runtime.c`'s `mk_err_errno`/`mk_err_cstr`) always returns a **bare String** error, never a `FileError`-tagged constructor — `lib/tir/llvm_emit.ml`'s hardcoded `native_result_ty` table independently pins these to `Result(_, String)` for codegen/ABI purposes. So `File.FileError`'s structured-constructor error is currently an **interpreter-only** behavior; a compiled program pattern-matching `Err(NotFound(path))` would typecheck (correctly, per this fix) but get the wrong runtime shape if compiled. No test or benchmark currently exercises File/Dir/Csv compiled (`grep` across `test/native/*.march` and `bench/*.march` confirms), so this fix introduces no new compiled-mode regression, but the interpreter/compiled parity gap itself remains unaddressed. Regression test: `test_letq_file_read_wrong_error_type` in `test/test_compiler.ml`'s `let?` suite (written test-first, confirmed RED against the original `poly1` signature, GREEN after the fix). **Full suite green: 527 compiler (was 526, +1 regression test) / 238 eval / 438 codegen / 780 stdlib / 53 stdlib_march.**
