- ✅ **Refinement Tier 2: structural induction over recursive functions (`lib/refinecheck/refine_check.ml`, 2026-07-26).** A relational postcondition on a structurally recursive function — `fn insert(t : Tree, x : Int) : {Tree | size(_) == size(t) + 1}` — is now PROVEN at its definition and therefore propagates. Probed against the built compiler beforehand and confirmed skipped, not proven: the definition exited 0 (ambiguous under definite-failure) but `needs_empty(insert(Leaf, 5))` where `needs_empty(t : {Tree | size(t) < 1})` ALSO exited 0, so nothing travelled. Under definite-failure only a PROPAGATION test distinguishes proved from skipped, and every "now proven" claim below is backed by one. **Mechanism.** Z3 does no induction, but full induction is not needed: `check_post_induction` mints a fresh opaque constant for each self-recursive call, assumes the function's own postcondition about that constant *iff* the argument at the MATCHED parameter's position is a variable certified by `structural_subvars`, asserts the arm's pattern equation (`t = Node(l, v, r)` — without it even the BASE case is unprovable, since `size(t)` is otherwise arbitrary), and discharges each `match` arm separately against the `@[measure]` recursion equations. The induction is on the matched parameter alone, so only that argument must shrink and the hypothesis is universally quantified over the rest — a growing accumulator is fine. **Soundness.** The gate is `structural_subvars`, unwidened — the same one that makes `@[measure]` axiomatisation sound. A proven postcondition is ADDED to the assumption set call-site checks prove `¬goal` against, and adding assumptions makes a violation EASIER to prove, so an unsound hypothesis manufactures FALSE POSITIVES on correct code rather than merely failing to help; the non-structural case is pinned by a test asserting silence on a program that would be reported under a looser gate. **Containment.** The path occupies the previously-inert variant-ADT-return case (`return_refine_ext` returns `None` for it, so nothing happened there at all), and is VERDICT-ONLY — it never emits a diagnostic, so `check_post` remains the single reporting site and a Tier 2 definition is silent whatever the solver says. Its only observable effect is enabling propagation through `gate_unverified_posts`. `fn_sig` gained `ret_sort`, so an ADT-sorted postcondition is carried only by `reflect_dt` (which knows the datatype sort) and never by the `Int` consumers `reflect_scalar`/`scope_add_binding`, which would declare one symbol at two sorts — the z3 `(error …)` that desynchronises the shared solver channel. A per-VC `declare` guard abandons any VC that would do so anyway. `Int`/record postconditions go down the unchanged Tier 0/1 path. `--no-measure-axioms` disables the path (it empties `measure_preamble_sorts`, which the VCs require), pinned by a test. **16 new tests** in a `tier2-induction` group (184 → 200), 12 of them asserting SILENCE. Newly proven and propagating: the canonical tree `insert`; a user `@[measure]` over the built-in `List`; recursion into the SECOND recursive component; a closed (non-relational) ADT postcondition. Pinned as silent with the reason recorded at each: the built-in `len` (not an axiomatised measure, so no recursion equations), mutual recursion (the hypothesis is minted only for the function's own name), a recursive call inside a lambda or behind a nested `match` (only the top-level pattern equation is built), a true-but-unprovable postcondition, a recursive function with no postcondition, and a closed `Int` postcondition. Adversarial sweep (4 programs — a true-but-unprovable postcondition, lambda- and nested-match-hidden recursion, a growing accumulator, and a module combining Tier 2 with records, strings, ADT testers, callbacks and Tier 1 relational propagation) all exit 0 cold-cache; `test_refine`, `run_compiler`, `run_eval`, `scripts/check-docs.sh` and ten stdlib-using example/bench programs all clean. **HAMT frontier.** A local reduced model of `stdlib/map.march` (the stdlib was not modified) shows THREE stacked obstacles: (1) the built-in `List` is modelled with an OPAQUE element sort (`Elem`), so a count measure that must recurse into a list element is ill-sorted and never axiomatised at all — swapping in a user-defined child list, changing nothing else, makes the same postcondition prove and propagate, which pins this as the first blocker, *before* induction is even reached; (2) with that worked around, `node_insert` reaches its child through a NESTED match whose pattern equation is not built; (3) the real code fetches the child by INDEX (`list_nth_safe(children, idx)`), which `structural_subvars` cannot certify and which would need a length/termination lemma — on top of `HEntry` being generic, wrapped in a `ptype`, and carrying an `eq` callback and a `level` counter. So the plan's question "does the structural test recognise a child fetched from a `List` by index?" is answered **no**, and obstacle (1) precedes it.
