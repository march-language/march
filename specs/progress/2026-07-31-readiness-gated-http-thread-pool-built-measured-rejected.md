- ❌ **Readiness-gated HTTP thread pool — built, measured, REJECTED (2026-07-31, see `specs/benchmarks.md` "Run 4").** Hypothesis: the default pool's ~36 CPU-µs/request against the event loop's ~28 was caused by parking a thread per open connection (blocking in `recv` between keep-alive requests) rather than per in-flight request. Built in full — poller thread, `poll()` + self-pipe, `MSG_DONTWAIT` one-dispatch-cycle workers, poller idle sweep, drain-based growth — and functionally correct: 256 connections on 34 threads instead of 262, zero persistently-unread Recv-Q, pipelining/keep-alive/shutdown intact, blocking handlers still get concurrency. **But 66–69% MORE CPU per request** (61.5/60.8 vs 37.0/36.1 author-measured; 62.0/62.9 vs 36.6/36.9 independently reproduced on a second harness). The penalty does **not** grow with polled-descriptor count — it is larger at c=32 than c=256 — so it is not the `poll()` O(n) scan and kqueue/epoll would not recover it; the cost is the per-request cross-thread handoff, which is structural to the design. **Corollary worth more than the change: the event loop's ~8 µs advantage is NOT the parked threads** — that hypothesis is refuted. The parked-thread path is already near-minimal (kernel wakes the thread already blocked in `recv` and copies straight into its buffer: one wakeup, no queue, no lock, no readiness syscall). Remaining candidates for the gap are the evloop running the handler directly on the loop thread with zero handoff, and `SO_REUSEPORT` sharding. Branch preserved: `claude/http-readiness-gated-pool-rejected`. **Do not rebuild this without reading the attribution table first.**
