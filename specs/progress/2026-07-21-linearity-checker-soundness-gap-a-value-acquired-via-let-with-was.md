- ✅ **Linearity checker soundness gap: a value acquired via `let?`/`with` was never tracked as linear, so double-consuming it went unflagged — FIXED (`lib/typecheck/typecheck.ml`'s `bind_pattern_bindings`, 2026-07-21).** Found while auditing `docs/cookbook/linear-types.md`: the doc claimed reusing a `let?`-chained linear value after it was consumed "would be a compile error (linear value used twice)" — empirically false. Minimal repro: `always_linear type Res = Res(Int); fn acquire(): Result(Res, String) do Ok(Res(1)) end; fn consume(r: Res): Result(Int, String) do ... end; fn f(): Result(Int, String) do let? r = acquire(); let? a = consume(r); let? b = consume(r); Ok(a + b) end` typechecked with **zero errors**, while the identical double-use of a plain-`let`-bound or function-parameter-bound linear value IS correctly rejected ("The linear value `r` is used more than once here."). Same gap reproduces through `with Ok(r) <- acquire() do ... end`. **Root cause:** `bind_pattern_bindings` — the one binding path shared by `let?` (`ELetQ`), `with`'s desugared nested `match`, and ordinary `match` arms — only promotes a binding to `Linear` when its type already carries a `TLin` wrapper or its scrutinee is itself a pre-tracked linear variable; unlike `ELet`'s `auto_lin` and `bind_lam_param`'s `effective_lin`, it never consulted `env.always_linear_types` to auto-promote a binding whose *resolved type name* is declared `always_linear type` — so a handle acquired straight from a fresh call's `Result` (not a pre-tracked variable, not `TLin`-annotated) was bound as an ordinary, untracked variable. **Fix:** added the same `always_linear_types` lookup to `bind_pattern_bindings`'s `Mono` and `Poly` cases (mirroring the existing `ELet`/`bind_lam_param` logic exactly), a single-site, non-behavior-changing addition for every path that already worked. Three new regression tests in `test/test_compiler.ml` (`test_linear_letq_acquire_double_use`, `test_linear_letq_acquire_single_use_ok`, `test_linear_with_acquire_double_use`). **Known related gap, deliberately NOT fixed here (separate, larger issue — filed below):** `check_linear_all_consumed` (the "dropped without being consumed" check) is never invoked for a `let?`/`with`/match-arm binding's continuation at all (only at an `ELet`'s own scope exit and a function body's exit), so a `let?`-acquired linear value that is silently never used slips through regardless of this fix — would need a real scope-exit hook on the CPS-shaped `ELetQ`/`EMatch` continuation, not a one-line change. See `specs/progress.md`'s matching "Current State" entry for the full writeup, including the cookbook doc rewrite this bug was found auditing.
