# Wave 2 — Task 1: interface-impl monomorphization fix (2026-07-02, `.superpowers/sdd/sortby-diagnosis.md`)


- ✅ **Historic "`List.sort_by` 100+ element compiled crash" formally closed — root cause was never sort_by.** Diagnosis (`.superpowers/sdd/sortby-diagnosis.md`, 95% confidence, evidence chain): compiled `println`/`show` of ANY generic container (`List`, `Option`, `Result`) whose `Show` goes through prelude's constrained impls (`impl Show(List(a)) when Show(a)`) was type-confused and had **never worked in compiled mode**, since the feature's introduction (`df3b1e44`, 2026-04-20). `lib/tir/mono.ml`'s three interface-impl-resolution enqueue sites (EApp direct-dispatch, EApp name-collision branch, ECallPtr twin) rewrote a call like `show(xs : List(Int))` to the mangled impl `Show$List.show`, but enqueued that impl with an **empty substitution** — so the impl body stayed generic, and its nested element-level `show(x : a)` call survived to `llvm_emit.ml` as an unresolved bare reference. `llvm_emit.ml`'s `unqualified_fns` dot-suffix fallback (built for legitimate cross-module unqualified refs like `base64_encode` → `Crypto.base64_encode`) then resolved the bare `show` to whatever `*.show`-suffixed impl was registered first — typically `Show$List.show` itself, applying the LIST impl to a raw element. Symptom varied by element type and impl-registration order (Int → SIGSEGV on a match-tag load against an erased-int treated as a heap pointer; String → non-exhaustive-match panic; Option → SIGSEGV/SIGBUS) — explaining the years of shifting "sort_by crash" symptom reports. sort_by itself is and was bit-for-bit correct compiled (1000-int checksum parity, 500-tuple stability parity, heap-capturing-comparator parity, all confirmed identical interpreter vs. compiled in the diagnosis). Fix (`lib/tir/mono.ml`): all three enqueue sites now compute a substitution from the resolved call's concrete argument types (`build_subst`, reusing the exact machinery the ordinary generic-fn EApp branch already used) and enqueue the impl specialized under it — mangling a further-specialized name (e.g. `Show$List.show` + `List(Int)` → `Show$List.show$List_Int`) when the substitution is non-empty, so the nested `show(x)` resolves through mono's normal rewrite-calls machinery to the concrete element impl. Recursion (`List(List(Int))` etc.) terminates via the existing worklist `done_set` dedup — verified explicitly: a 2-level and 3-level nested-list `println` both compile in ~2s with no runaway specialization loop. Defense-in-depth (`lib/tir/llvm_emit.ml`): `unqualified_fns` population now EXCLUDES interface-impl-mangled names (detected as "contains `$` before the last `.`", e.g. `Show$List.show$List_Int` — ordinary qualified names like `Crypto.base64_encode` are unaffected since they never contain `$`), so a bare interface-method name recurring unresolved can never again be silently rebound to an arbitrary same-named impl; the ECallPtr catch-all fallback additionally `failwith`s by name (listing candidate impls) if it ever sees an unresolved bare name matching a registered impl's suffix, converting any future regression into a loud compile-time failure instead of a silent miscompile. Four RED/GREEN regression tests added in `test/test_codegen.ml` (`iface_impl_mono_codegen`): `println([1,2,3,4,5])` (pre-fix: SIGSEGV 139), `println(["a","b"])` (pre-fix: non-exhaustive-match panic, exit 1), `println([Some(42), None])` (pre-fix: SIGSEGV 139), `println([[1,2],[3]])` (pre-fix: SIGSEGV 139, also the mono-termination/recursion-guard check) — all assert compiled stdout == interpreter stdout AND exit 0. The original 150-element `List.sort_by` + `println(List.take(sorted, 10))` repro (`/tmp/sortby-kapitsa-baseline.march`) now produces byte-identical output in interpreter and compiled mode, exit 0 both — closing the saga end-to-end. **384 compiler / 227 eval / 341 codegen (+4 new, 337 pre-existing) / 791 stdlib / 53 stdlib_march all pass, all exit 0.** RC benchmarks (compiled, `--opt 2`): `tree_transform` = `104857600`, `list_ops` = `333333666666`, `binary_trees` standard Benchmarks-Game output, `bench/mutual_recursion.march` (even/odd, 3-state machine, collatz) all correct — no regressions.
