✅ **Typed JSON decoding plan, Task 5 — variant `from_json` reports the tag and argument index (2026-07-31, `lib/desugar/desugar.ml`, `test/stdlib/test_json_typed.march`).** Extends Task 4's path-carrying record decode errors to enum/variant-with-args types. Replaced the `TDVariant` branch of the generated `from_json` (previously: `Json.get(v, "tag")` matched against each `Str(Ctor)` literal directly on the raw `JsonValue`, with a generic `Err("invalid JSON for T")`/`Err("invalid JSON for T.Ctor")` fallback for an unrecognized tag or wrong-shaped args, and an unconditional `panic` on a nested derive-Json argument's decode failure) with a per-tag dispatch mirroring the record decoder's structure: `match v do Object(kvs) -> match Json.get_field(kvs, "tag") do None -> Err(missing field, [JPathField("tag")]) | Some(tagv) -> match tagv do Str("Ctor0") -> Ok(Ctor0) | ... | Str(tagstr) -> Err("unknown variant \`" ++ tagstr ++ "\`", [JPathField("tag")]) | _ -> Err(expected String, [JPathField("tag")]) end end | _ -> Err(expected an object, Nil) end`. For a variant with args, each argument is looked up positionally via `Json.get_field(kvs, "0")`, `Json.get_field(kvs, "1")`, ... (the same object as `"tag"`, not a separate array) and a wrong-typed or missing argument reports `Json.JPathIndex(i)` instead of `JPathField` — e.g. `"$[0]: expected Int"` — and a nested derive-Json argument composes a path across the boundary via `Json.decode_error_under`, exactly like the record case, instead of panicking. Factored the per-value decode logic shared between record fields and variant arguments into one `decode_value_at` helper parameterized on the path step (`JPathField` vs `JPathIndex`); `decode_field_value` and a new `decode_arg_value` are now one-line specializations of it. Removed the now-dead `decoder_pat_for_ty` helper (only used by the old variant decoder; confirmed no remaining callers via repo-wide grep — `dune build` fails on an unused-variable warning otherwise). **Wire format note, matched the existing encoder exactly, no invention:** `to_json`'s `TDVariant` branch (fixed earlier in Task 2, unchanged here) emits a flat `Json.encode_object([("tag", ...), ("0", ...), ("1", ...), ...])` — there is no `"values"` array — confirmed against the passing `test/stdlib/test_derive_json.march` encoder tests and the pre-existing `test_json_typed.march` variant round-trip fixture (`{"tag":"Rect","0":3,"1":4}`); the brief's illustrative Step-1 test sketch assumed a `"values"` array and was adapted to this actual shape. **What this task explicitly did NOT fix, confirmed still present:** the same pre-existing `from_json` cross-type dispatch bug Task 4 documented (every `derive Json for T` unconditionally rebinds the bare `from_json` name in the module env) is untouched; the two new tests exercise only scalar (`Int`) argument decoding, so they don't trip it.
