# Tuples have no `Ord`

**Logged:** 2026-10-06, split from
[../progress/2026-10-01-tuple-eq.md](../progress/2026-10-01-tuple-eq.md) (tuple
`Eq` landed there).

**Tuple `Ord`.** `(1, 2) < (1, 3)` is rejected by the `COrd` check, and
`compare((1, 2), (1, 3))` by the `Ord` interface check. Discharging both
structurally (every component `Ord`) is a few lines in `discharge_constraints`.
It was tried and backed out, because neither backend can run the result yet:

- interpreted, `<` on two tuples panics `builtin <: no 'Ord' implementation for
  this type` (`compare` works);
- compiled, `compare((1, 2), (1, 3))` is `ambiguous interface-method call to
  'compare': 3 implementations are in scope (Ord$String.compare,
  Ord$Float.compare, Ord$Int.compare)`. There is no tuple row to dispatch to.

So tuple `Ord` needs a lexicographic `<`/`compare` in the interpreter and a
generated per-shape compare in codegen (the `Eq` analogue is
`ensure_adt_eq_fn`'s tuple arm in `lib/tir/llvm_eq.ml`), then the typecheck
discharge.

The independent conditional-impl `when`-bound issue is fixed in
[conditional impl bounds](../progress/2026-10-08-conditional-impl-bounds.md).
