# `[P2]` Compiler: Session types (protocols/channels)

- [ ] **F6 — SEMANTICS (scope boundary, not a bug to fix): the channel runtime has no scheduler, so a `recv` called before its matching `send` in program order typechecks cleanly but deadlocks/aborts at runtime on BOTH backends.** Found and pinned by `specs/lang/core-march.md` §4.11 and §4.1 finding 23 (session-types widening, Task 4, 2026-07-06). The channel runtime is synchronous, single-threaded, non-blocking: `chan_recv` (`eval.ml:2655`) does not suspend when its `ce_in_q` queue is empty — it raises a hard error immediately (`eval.ml:2660`, `"Chan.recv: channel %s#%d has no pending value — did you run the sender first?"`); there is no coroutine/actor-mailbox integration for channels, so both endpoints of a session must run in the same straight-line thread with every `send` textually ordered before its matching `recv`. Verified live (this task): a program calling a `server_side` function (whose FIRST op is `Chan.recv`) before a `client_side` function (whose `Chan.send` would have satisfied it) — a protocol that typechecks (`--check` exit 0, session-state advancement is purely a static per-op check, oblivious to call order) — dies at runtime on both backends: interpreted, `Chan.recv: channel Echo#0 has no pending value — did you run the sender first?` (exit 1); compiled, `march: Chan.recv on empty channel queue (role 1)` then abort (exit 134). Neither the type system nor any runtime scheduler prevents the ordering mistake; both backends simply agree it is a fatal error once it happens. **This is a documented scope boundary, not a defect to fix:** session types here are a linear protocol-*conformance* checker layered over a same-thread mailbox, not a concurrent-session / coroutine system — the type system guarantees "the protocol steps you take advance a valid session state," not "your calls into that protocol are scheduled in the order the protocol requires." Filed here for reference-completeness (no fix proposed; a scheduler/coroutine integration would be a substantial feature, out of scope for a docs-widening task). See `specs/lang/core-march.md` §4.11 for the full writeup and both live-verified backend error messages.
- [ ] **Session types: make "awaiting `offer` refinement" a session STATE rather than a side table (durable form of the Finding 1 fix above, OPEN).** Today `env.offer_unrefined` is a physical-identity list guarded at two chokepoints. The structural fix is a new `session_ty` constructor — `SOfferPending of (string * session_ty) list` — that `Chan.offer` puts the returned ref at when the branches diverge, and that only `with_offer_refinement` strips. It would then survive unification, annotations, and function boundaries BY CONSTRUCTION rather than by a checked invariant, and would need no `unify` special case at all. Deferred because it touches `pp_session_ty`, `session_ty_equal`, `session_ty_exact_equal`, `dual_session_ty`, `unfold_srec`, `subst_svar`, and every `match` over `session_ty` — many of which have `_` fallbacks, so OCaml's exhaustiveness warnings would NOT enumerate the sites for you. Do it with a survey of every `session_ty` match first, not by chasing compiler errors.
