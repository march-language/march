# What March tells you when something is wrong

A compiler error is the part of a language you read most. March tries to make each one
answer three questions: *what* is wrong, *where* (the exact piece of code, not just the
line), and *what to do about it*. This page walks through real errors, from the syntax
slips of your first hour to a protocol that one role breaks. Every output below is what
`march --check` prints for the program above it today, generated from the compiler
rather than pasted by hand.

The playground just below has most of them loaded. Pick one, edit it, and check it again
to see how the message changes. It runs the real parser and typechecker in your
browser.

{% include error-playground.html %}

## How to read a March error

Here is the output for [a `String` where an `Int` is](#a-string-where-an-int-is), shortened
and annotated:

```text
-- TYPE MISMATCH --------------------- string-plus-int.march    ← the kind of problem, and the file

expected `String` but got `Int`. [type_mismatch]              ← the message, and its code

5 |     "item " ++ n                                            ← the source, with a caret
                   ^                                              on the exact subterm

    This is argument #2 of a function call.                   ← notes: context, then a fix
    Use `int_to_string(x)` to convert an Int to a String.

    `n` was bound here as `Int`:                              ← labels: other code that matters

4 |   fn label(n : Int) : String do
               ^
    run `march --explain type_mismatch`                       ← a longer page about this code
```

- **The code** in brackets (`[type_mismatch]`) is stable. `march --explain <code>` prints a
  page about it: what causes it, a program that triggers it, and how to fix it. The same
  pages are on this site, listed under [Error reference](#error-reference).
- **One mistake, one error.** When a mistake would cause others downstream, March reports
  the mistake and holds back the errors that only follow from it.
- **Fixes as edits.** Many errors also carry a machine-applicable fix. `march --check-json`
  includes it as a text edit, the [language server](lsp.md) offers it as a quick fix, and
  `forge fix` applies it.

## 1. Syntax

The first errors most people meet come from habits other languages taught: `then`,
`elif`, semicolons, curried calls. March names the habit and shows the March form.

<a id="then"></a>

### `then` instead of `do`

<!-- error-tour: 01-then -->
```march
mod Main do
  needs IO.Console

  fn sign(n : Int) : Int do
    if n > 0 then 1 else 0 end
  end

  fn main(_console : Cap(IO.Console)) do
    println(int_to_string(sign(3)))
  end
end
```

```text
-- SYNTAX ------------------------------------ then.march

I don't recognize `then` here — March uses do/end blocks instead. [then_keyword]

5 |     if n > 0 then 1 else 0 end
                 ^^^^

    if cond do
        expr1
    else
        expr2
    end
    run `march --explain then_keyword`
```
<!-- /error-tour -->

It recognises the keyword from another language and shows the whole `if` shape to copy.
<button class="ep-try" data-error-example="01-then">Try it</button>

<a id="if-without-else"></a>

### An `if` without an `else`

<!-- error-tour: 02-if-without-else -->
```march
mod Main do
  fn clamp(x : Int) : Int do
    if x > 0 do
      x
    end
  end

  fn main() do
    clamp(5)
  end
end
```

```text
-- SYNTAX ------------------------- if-without-else.march

March `if` expressions always need an `else` branch: [parse_error]

5 |     end
        ^^^

    if cond do
        expr1
    else
        expr2
    end
    run `march --explain parse_error`
```
<!-- /error-tour -->

`if` is an expression in March, so it always produces a value. The message states that
rule rather than "unexpected token `end`".
<button class="ep-try" data-error-example="02-if-without-else">Try it</button>

<a id="else-if-chain"></a>

### An `else if` chain one `end` short

<!-- error-tour: 03-else-if-chain -->
```march
mod Main do
  fn pick(a : Bool, b : Bool) : Int do
    if a do 1 else if b do 2 else 3 end
  end

  fn main() do
    pick(false, true)
  end
end
```

```text
-- SYNTAX --------------------------- else-if-chain.march

This `if` (line 3) needs its own `end`: the `end` on line 4 belongs to an outer block. [parse_error]

3 |     if a do 1 else if b do 2 else 3 end
        ^^

    I only noticed at the end of the file.
    `else if` is a nested `if` in the else position, so each `if` needs its own `end`: a two-branch chain ends `end end`, a three-branch chain `end end end`.
    run `march --explain parse_error`
```
<!-- /error-tour -->

A missing `end` is usually noticed far from where it belongs. This message points at the
`if` that is missing it, says it only noticed at the end of the file, and says how many
`end`s a chain needs.
<button class="ep-try" data-error-example="03-else-if-chain">Try it</button>

<a id="semicolon"></a>

### Semicolons

<!-- error-tour: 04-semicolon -->
```march
mod Main do
  needs IO.Console

  fn total() : Int do
    let x = 1; let y = 2
    x + y
  end

  fn main(_console : Cap(IO.Console)) do
    println(int_to_string(total()))
  end
end
```

```text
-- SYNTAX ------------------------------- semicolon.march

Unexpected `;`: March separates expressions with newlines, not semicolons. [semicolon_separator]

5 |     let x = 1; let y = 2
                 ^

    Put each expression on its own line.
    run `march --explain semicolon_separator`
```
<!-- /error-tour -->

The caret is on the `;` itself, and the note says what to write instead.
<button class="ep-try" data-error-example="04-semicolon">Try it</button>

<a id="curried-call"></a>

### A curried call

<!-- error-tour: 05-curried-call -->
```march
mod Main do
  fn adder(x : Int) do
    fn (y) -> x + y
  end

  fn main() do
    adder(1)(2)
  end
end
```

```text
-- SYNTAX ---------------------------- curried-call.march

`f(...)(...)` is not a chained call — March functions are not curried. [parse_error]

7 |     adder(1)(2)
                ^

    Write `f(a, b)` for a multi-argument call, or put the second call on its own line if you meant two separate statements.
    run `march --explain parse_error`
```
<!-- /error-tour -->

`adder(1)(2)` parses in many languages. March explains why it isn't a chained call here,
and gives the two things you probably meant.
<button class="ep-try" data-error-example="05-curried-call">Try it</button>

## 2. Names and "did you mean"

A misspelling gets a suggestion, and the suggestion is chosen by what fits, not only by
spelling.

<a id="misspelled-module"></a>

### A misspelled module

<!-- error-tour: 06-misspelled-module -->
```march
mod Main do
  needs IO.Console

  fn count() : Int do
    Lsit.length([1, 2])
  end

  fn main(_console : Cap(IO.Console)) do
    println(int_to_string(count()))
  end
end
```

```text
-- NAMING ----------------------- misspelled-module.march

Unknown module `Lsit`. Did you mean `List`? [unknown_qualified_name]

5 |     Lsit.length([1, 2])
        ^^^^^^^^^^^

    run `march --explain unknown_qualified_name`
```
<!-- /error-tour -->

The suggestion comes from the standard library's modules. (The playground can't show
this one: it suggests from the module files on disk, which a browser doesn't have.)

<a id="field-by-type"></a>

### A misspelled record field

<!-- error-tour: 07-field-by-type -->
```march
mod Main do
  fn main() do
    let r = { count: 1, cont: "x" }
    let n : Int = r.conut
    n
  end
end
```

```text
-- NAMING --------------------------- field-by-type.march

This record does not have a field called `conut`. Did you mean `count`? [unknown_record_field]
The fields I see are: cont, count

4 |     let n : Int = r.conut
                      ^^^^^^^
```
<!-- /error-tour -->

`cont` is the closer spelling, but it holds a `String` and the annotation wants an `Int`,
so March suggests `count`. It also lists the fields the record does have.
<button class="ep-try" data-error-example="07-field-by-type">Try it</button>

<a id="constructor-by-type"></a>

### A misspelled constructor

<!-- error-tour: 08-constructor-by-type -->
```march
mod Main do
  type Mail = Postal(Int) | Email(String)
  type Tag = Poss(Int)

  fn main() do
    let m : Mail = Posts(1)
    m
  end
end
```

```text
-- NAMING --------------------- constructor-by-type.march

I don't know a constructor called `Posts`. [unknown_constructor]
Did you mean `Postal` (from type `Mail`)?

6 |     let m : Mail = Posts(1)
                       ^^^^^^^^
```
<!-- /error-tour -->

`Poss` and the standard library's `Post` are each one letter from `Posts`, but only
`Postal` builds a `Mail`, which the annotation asks for. The suggestion says which type it
comes from.
<button class="ep-try" data-error-example="08-constructor-by-type">Try it</button>

## 3. Types

A type error puts its caret on the subterm whose type is wrong, says where the expected
type came from, and, when the two types share a structure, shows only the part that
differs.

<a id="string-plus-int"></a>

### A `String` where an `Int` is

<!-- error-tour: 09-string-plus-int -->
```march
mod Main do
  needs IO.Console

  fn label(n : Int) : String do
    "item " ++ n
  end

  fn main(_console : Cap(IO.Console)) do
    println(label(3))
  end
end
```

```text
-- TYPE MISMATCH ------------------ string-plus-int.march

expected `String` but got `Int`. [type_mismatch]

5 |     "item " ++ n
                   ^

    This is the right side of `++`, which joins two `String`s.
    Use `int_to_string(x)` to convert an Int to a String.

    the expected type comes from here:

5 |     "item " ++ n
        ^^^^^^^

    `n` was bound here as `Int`:

4 |   fn label(n : Int) : String do
               ^
    run `march --explain type_mismatch`
```
<!-- /error-tour -->

The caret is on `n`, not on the whole `++`. Two labels show where `String` is required
and where `n` got its type, and the note names the conversion function.
<button class="ep-try" data-error-example="09-string-plus-int">Try it</button>

<a id="structural-diff"></a>

### Two types that differ in one place

<!-- error-tour: 10-structural-diff -->
```march
mod Main do
  needs IO.Console

  fn count(xs : List(Int)) : Int do
    List.length(xs)
  end

  fn main(_console : Cap(IO.Console)) do
    let names = ["a", "b"]
    println(int_to_string(count(names)))
  end
end
```

```text
-- TYPE MISMATCH ------------------ structural-diff.march

expected `List(Int)` but got `List(String)`. [type_mismatch]

10 |     println(int_to_string(count(names)))
                                     ^^^^^

    This is argument #1 of a function call.
    The types differ here:
        List(String)
             ^^^^^^ expected `Int`

    the expected type comes from here:

10 |     println(int_to_string(count(names)))
                               ^^^^^^^^^^^^

    `names` was bound here as `List(String)`:

9 |     let names = ["a", "b"]
            ^^^^^
    run `march --explain type_mismatch`
```
<!-- /error-tour -->

`List(String)` and `List(Int)` share everything but the element type, so the diff
underlines just `String`. With a large record or nested type, this saves comparing both in
full.
<button class="ep-try" data-error-example="10-structural-diff">Try it</button>

<a id="no-partial-application"></a>

### Too few arguments

<!-- error-tour: 11-no-partial-application -->
```march
mod Main do
  needs IO.Console

  fn main(_console : Cap(IO.Console)) do
    let add = fn (a, b) -> a + b
    println(int_to_string(add(1)))
  end
end
```

```text
-- TYPE MISMATCH ----------- no-partial-application.march

`add` is a lambda with 2 parameters, but is called with 1 argument. [arity_mismatch]
March has no partial application — a call must supply all arguments.

6 |     println(int_to_string(add(1)))
                              ^^^^^^


    bound here with 2 parameters:

5 |     let add = fn (a, b) -> a + b
                  ^^^^^^^^^^^^^^^^^^
```
<!-- /error-tour -->

Coming from a curried language, `add(1)` looks like partial application. The message says
March has none, and shows where `add` got its two parameters.
<button class="ep-try" data-error-example="11-no-partial-application">Try it</button>

<a id="let-question"></a>

### A `let?` whose body is not a `Result`

<!-- error-tour: 12-let-question -->
```march
mod Main do
  fn parse() : Result(Int, String) do Ok(1) end

  fn next() : Result(Int, String) do
    let? x = parse()
    x + 1
  end

  fn main() do
    next()
  end
end
```

```text
-- TYPE MISMATCH --------------------- let-question.march

expected `Result(Int, String)` but got `Int`. [type_mismatch]

5 |     let? x = parse()
        ^^^^^^^^^^^^^^^^

    This is the declared return type of `next`.
    The code after `let?` must produce a Result with the same error type.

    the expected type comes from here:

4 |   fn next() : Result(Int, String) do
      ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
    run `march --explain type_mismatch`
```
<!-- /error-tour -->

`let?` returns early on `Err`, so the rest of the function must produce a `Result` too.
The note explains that rule instead of reporting a bare `Int` vs `Result` clash.
<button class="ep-try" data-error-example="12-let-question">Try it</button>

<a id="missing-impl"></a>

### Comparing a type that has no ordering

<!-- error-tour: 13-missing-impl -->
```march
mod Main do
  needs IO.Console

  type Hue = Red | Blue

  fn main(_console : Cap(IO.Console)) do
    let a = Red
    let b = Blue
    println(if a < b do "less" else "not less" end)
  end
end
```

```text
-- INTERFACE ------------------------- missing-impl.march

`Hue` does not implement interface `Ord`. [missing_impl]
`<` needs it here.

9 |     println(if a < b do "less" else "not less" end)
                   ^^^^^

    Add `derive Ord for Hue` after the type to get the structural one, or write `impl Ord(Hue) do ... end`.
```
<!-- /error-tour -->

The message names the operator that needs `Ord` and gives both fixes: derive the
structural ordering in one line, or write your own `impl`.
<button class="ep-try" data-error-example="13-missing-impl">Try it</button>

## 4. Capabilities

In March, a program can only do the IO it was granted. `main` receives its capabilities
as parameters, and each module declares the ones it uses with `needs` (see
[Capabilities](capabilities.md)). The errors talk about access in plain terms: "writes a
file", "the console capability".

<a id="main-no-grant"></a>

### `main` with no grant

<!-- error-tour: 14-main-no-grant -->
```march
mod Main do
  needs IO.Console

  fn main() do
    println("hello")
  end
end
```

```text
-- CAPABILITY ----------------------- main-no-grant.march

`main` performs IO but declares no grant. The program reaches `IO.Console`; a `main` with no capability parameter is granted nothing. [cap_grant]
help: declare the grant `main` actually needs —
        fn main(_cap_console : Cap(IO.Console)) : ()
or grant everything with `fn main(cap : Cap(IO))`.
`forge fix` can apply this.

4 |   fn main() do
      ^^^^^^^^^^^^

    run `march --explain cap_grant`
```
<!-- /error-tour -->

It works out which capability the program actually reaches and writes the narrowest
signature for `main`. `forge fix` applies it.
<button class="ep-try" data-error-example="14-main-no-grant">Try it</button>

<a id="missing-needs"></a>

### Writing a file without saying so

<!-- error-tour: 15-missing-needs -->
```march
mod Main do
  needs IO.Console

  fn save(n : Int) : () do
    let _ = file_write("/tmp/n", int_to_string(n))
    ()
  end

  fn main(c : Cap(IO.Console)) do
    save(1)
    println("saved")
  end
end
```

```text
-- CAPABILITY ----------------------- missing-needs.march

`save` writes a file, but module `Main` declares no `needs IO.FileWrite`, and `main` is granted only `Cap(IO.Console)`. [cap_needs]
hint: add this to the module body —
        needs IO.FileWrite
and give `main` a `Cap(IO.FileWrite)` parameter: `fn main(…, _cap_filewrite : Cap(IO.FileWrite))`.

5 |     let _ = file_write("/tmp/n", int_to_string(n))
                ^^^^^^^^^^


    `main` calls `save` here:

10 |     save(1)
         ^^^^

    `main` is granted only `Cap(IO.Console)` here:

9 |   fn main(c : Cap(IO.Console)) do
             ^^^^^^^^^^^^^^^^^^^^^
    run `march --explain cap_needs`
```
<!-- /error-tour -->

Two things are missing: the module's `needs IO.FileWrite` line, and a grant on `main`.
They are reported as one error, with the call chain from `main` and both edits in the
hint.
<button class="ep-try" data-error-example="15-missing-needs">Try it</button>

<a id="wrong-capability"></a>

### Passing the wrong capability

<!-- error-tour: 16-wrong-capability -->
```march
mod Main do
  needs IO.Console

  fn read(c : Cap(IO.FileRead)) : String do "x" end

  fn main(c : Cap(IO.Console)) do println(read(c)) end
end
```

```text
-- CAPABILITY -------------------- wrong-capability.march

`read` needs file-read access, but `c` is the console capability. [cap_mismatch]

6 |   fn main(c : Cap(IO.Console)) do println(read(c)) end
                                                   ^

    `IO.Console` and `IO.FileRead` are both parts of `IO`; neither contains the other.
    help: give `main` a `Cap(IO.FileRead)` parameter and pass it to `read`.
    and add `needs IO.FileRead` to the module.

    `read` needs `Cap(IO.FileRead)`:

6 |   fn main(c : Cap(IO.Console)) do println(read(c)) end
                                              ^^^^^^^

    `c` was bound here as `Cap(IO.Console)`:

6 |   fn main(c : Cap(IO.Console)) do println(read(c)) end
              ^

    `Cap(IO.FileRead)` is named here, and the module declares no `needs IO.FileRead`:

4 |   fn read(c : Cap(IO.FileRead)) : String do "x" end
      ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^

    `main` is granted only `Cap(IO.Console)` here:

6 |   fn main(c : Cap(IO.Console)) do println(read(c)) end
             ^^^^^^^^^^^^^^^^^^^^^
```
<!-- /error-tour -->

Underneath this is a type mismatch, but the message says what it means: `read` needs
file-read access, and `c` is the console. It explains why neither capability covers the
other, then shows every place the fix touches.
<button class="ep-try" data-error-example="16-wrong-capability">Try it</button>

## 5. Linearity

A linear value must be used exactly once: not copied, not dropped (see
[Linear types](linear-types.md)). Each error points at both uses, or at the place the
value was lost.

<a id="linear-used-twice"></a>

### Used twice

<!-- error-tour: 17-linear-used-twice -->
```march
mod Main do
  needs IO.Console

  always_linear type Token = Token(Int)

  fn consume(t : Token) : Int do
    match t do Token(n) -> n end
  end

  fn main(_console : Cap(IO.Console)) do
    let t = Token(1)
    println(int_to_string(consume(t) + consume(t)))
  end
end
```

```text
-- LINEARITY -------------------- linear-used-twice.march

The linear value `t` is used more than once here. [linear_used_twice]
Linear values must be consumed exactly once — they cannot be copied or ignored.

12 |     println(int_to_string(consume(t) + consume(t)))
                                                    ^


    `t` was already consumed here:

12 |     println(int_to_string(consume(t) + consume(t)))
                                       ^
    run `march --explain linear_used_twice`
```
<!-- /error-tour -->

The caret is on the second use and a label marks the first, even though both are on the
same line.
<button class="ep-try" data-error-example="17-linear-used-twice">Try it</button>

<a id="linear-some-branches"></a>

### Consumed on some branches only

<!-- error-tour: 18-linear-some-branches -->
```march
mod Main do
  needs IO.Console

  always_linear type Token = Token(Int)

  fn consume(t : Token) : Int do
    match t do Token(n) -> n end
  end

  fn main(_console : Cap(IO.Console)) do
    let t = Token(1)
    let n = match 2 do
      1 -> consume(t)
      2 -> consume(t) + 1
      _ -> 0
    end
    println(int_to_string(n))
  end
end
```

```text
-- LINEARITY ----------------- linear-some-branches.march

The linear value `t` is consumed on some branches but not others. [linear_mixed_consumption]
On a branch that doesn't consume it, the value is dropped. Consume it on every branch, or end that branch with `panic(…)` if it never returns.

12 |     let n = match 2 do
                       ^^^^


    `t` is consumed on this branch:

13 |       1 -> consume(t)
                        ^

    but not on this one, where it is dropped:

15 |       _ -> 0
                ^
```
<!-- /error-tour -->

It names a branch that consumes the token and one that silently drops it, and suggests
`panic(…)` for a branch that never returns.
<button class="ep-try" data-error-example="18-linear-some-branches">Try it</button>

<a id="linear-captured"></a>

### Captured by a closure

<!-- error-tour: 19-linear-captured -->
```march
mod Main do
  needs IO.Console

  always_linear type Token = Token(Int)

  fn consume(t : Token) : Int do
    match t do Token(n) -> n end
  end

  fn twice(k : () -> Int) : Int do k() + k() end

  fn main(_console : Cap(IO.Console)) do
    let t = Token(1)
    println(int_to_string(twice(fn () -> consume(t))))
  end
end
```

```text
-- LINEARITY ---------------------- linear-captured.march

The linear value `t` cannot be captured by a closure. [linear_captured]
A closure may be called multiple times, which would violate the exactly-once guarantee.
Pass `t` as a parameter to the closure instead.

14 |     println(int_to_string(twice(fn () -> consume(t))))
                                     ^^^^^^^^^^^^^^^^^^^
```
<!-- /error-tour -->

The message gives the reason (a closure can be called more than once) and the fix (take
the value as a parameter).
<button class="ep-try" data-error-example="19-linear-captured">Try it</button>

## 6. Actors

Actor errors use the actor's own words: its messages, its state, the pid you spawned (see
[Actors](actors.md)).

<a id="misspelled-actor"></a>

### A misspelled actor

<!-- error-tour: 20-misspelled-actor -->
```march
mod Main do
  needs IO.Console

  actor Counter do
    state { n : Int }
    init { n: 0 }
    on Bump(k : Int) do { state with n: state.n + k } end
  end

  fn main(_console : Cap(IO.Console)) do
    let p = spawn(Countr)
    send(p, Bump(1))
  end
end
```

```text
-- NAMING ------------------------ misspelled-actor.march

I don't know an actor called `Countr`. [unknown_constructor]
Did you mean `Counter`?

11 |     let p = spawn(Countr)
                       ^^^^^^
```
<!-- /error-tour -->

Inside `spawn(…)` March is looking for an actor, so it calls `Countr` an actor and
suggests one.
<button class="ep-try" data-error-example="20-misspelled-actor">Try it</button>

<a id="message-argument"></a>

### The wrong argument in a message

<!-- error-tour: 21-message-argument -->
```march
mod Main do
  needs IO.Console

  actor Counter do
    state { n : Int }
    init { n: 0 }
    on Bump(k : Int) do { state with n: state.n + k } end
  end

  fn main(_console : Cap(IO.Console)) do
    let c = spawn(Counter)
    send(c, Bump("one"))
  end
end
```

```text
-- TYPE MISMATCH ----------------- message-argument.march

expected `Int` but got `String`. [type_mismatch]

12 |     send(c, Bump("one"))
                      ^^^^^

    `Bump` is a message of actor `Counter`, and its handler declares this argument's type.

    the expected type comes from here:

7 |     on Bump(k : Int) do { state with n: state.n + k } end
                ^
    run `march --explain type_mismatch`
```
<!-- /error-tour -->

The expected type comes from the handler's parameter, so the label points into the actor
at `k : Int`, not at a generated message type.
<button class="ep-try" data-error-example="21-message-argument">Try it</button>

<a id="handler-returns-state"></a>

### A handler that forgets to return the state

## 9. Refinements

A refinement type adds a condition to a type, like `{Int | _ >= 0}` or
`{List(Int) | len(_) > 0}`, and March proves those conditions at compile time with the z3
solver (see [Refinement types](refinement-types.md)). When a proof fails, the error gives
a concrete counterexample. These need z3, so the playground can't run them; install March
to try them.

<a id="index-out-of-range"></a>

### An index that is out of range

<!-- error-tour: 30-index-out-of-range -->
```march
mod Main do
  fn third() : Int do
    List.nth([1, 2, 3], 7)
  end

  fn main() : Int do
    third()
  end
end
```

```text
-- REFINEMENT ------------------ index-out-of-range.march

refinement violation: index must be less than the list's length [refinement_violated]
argument `n` of `List.nth` does not satisfy precondition `_ < len(xs)`
note: this value never satisfies it; pass one that does

3 |     List.nth([1, 2, 3], 7)
        ^^^^^^^^^^^^^^^^^^^^^^

    `List.nth_opt` is `List.nth` without the requirement: it returns `Option` instead of panicking.
        match List.nth_opt([1, 2, 3], 7) do
          Some(v) -> …
          None -> …
        end

    this argument must satisfy `_ >= 0 && _ < len(xs)`:

3 |     List.nth([1, 2, 3], 7)
                            ^
    run `march --explain refinement_violated`
```
<!-- /error-tour -->

`List.nth` requires an index below the list's length. The solver knows the literal list
has three elements, so this call can never succeed, and the note says so.

## 10. Performance: why a copy happens

March updates a list or a tree in place when the function rebuilding it holds the only
reference to it. When something else still holds the value, the function allocates a new
copy instead: the program is still correct, only slower. Nothing in an ordinary check
says so, because nothing is wrong. `march --why-copies` is the report you ask for when
you want to know. The playground only checks programs, so it can't show this one.

<a id="copy-shared"></a>

### A list that is used again after `List.map`

<!-- error-tour: 35-copy-shared --why-copies -->
```march
mod Main do
  needs IO.Console

  fn inc_all(xs : List(Int)) : List(Int) do
    let ys = List.map(xs, fn x -> x + 1)
    let n = List.length(xs)
    List.append(ys, [n])
  end

  fn main(_console : Cap(IO.Console)) do
    println(int_to_string(List.length(inc_all([1, 2, 3]))))
  end
end
```

```text
-- WARNING: COPY ---------------------- copy-shared.march

`List.map` builds a new copy instead of reusing `xs` in place, because `xs` is used again afterwards. [copy_shared]
A function can update a value in place only when it holds the only reference to it; make this call the last use of `xs` and `List.map` reuses its memory instead of allocating.
help: move `let n = List.length(xs)` above the call.

5 |     let ys = List.map(xs, fn x -> x + 1)
                          ^^


    `xs` is used again here, so it is still shared when `List.map` runs:

6 |     let n = List.length(xs)
                            ^^
    run `march --explain copy_shared`
```
<!-- /error-tour -->

`List.map` could have rewritten `xs`'s cells in place, but `List.length(xs)` on the next
line still needs the old list, so it built a new one. The warning points at both lines and
offers the fix: take the length first. The fix appears only when moving the later line is
safe (it is the value's only later use and has no side effects); `forge fix` can apply it.
The same report names two other reasons a value stays shared: it is also passed to the
enclosing call, or a closure captured it. See the
[memory model]({{ site.baseurl }}/docs/memory-model/#when-reuse-fires-vs-falls-back).
